## 1. 先定义要验证的假设

沿用官方技术文档问答：

> 在授权、指定版本的文档上，检索系统是否能找到必要资料，并让模型正确回答、引用和处理不足？

分别验证：

- 混合检索是否比单一路提高证据覆盖。
- Re-rank 是否在相同候选输入下改善最终证据选择。
- 查询改写是否改善指代 / 改写问题而不改变约束。
- 压缩是否在减少 token 的同时保留必要事实。

不要同时更换模型、切块、召回、重排和 Prompt 后，将总分提升全部归因于一个模块。

## 2. 三组数据与一个明确的知识库范围

| 对象 | 用途 |
|---|---|
| 授权知识库快照 | 本实验允许检索的文档、版本、权限与原文 |
| 开发 / 验证查询 | 选择切块、召回、重排与 Prompt 配置 |
| 留出测试查询 | 配置选定后最终比较 |
| 回归 / 高风险查询 | 检查已知问题与罕见风险，单独报告 |

若训练 embedding / reranker，还需独立训练数据，并控制 query、文档组与近重复泄露。

**测试问题的答案资料在知识库中，通常正是 RAG 的任务条件，不自动等于泄露。** 但不能把测试问答、参考答案或其近重复用于训练和调参。声明评测的是固定知识库上的新查询，还是未参与训练的文档 / 领域泛化，两者不同。

知识库版本固定。遇到文档更新，另建新版本对照，不静默换资料后沿用旧结果。

## 3. 评测样本要标什么？

至少记录：

- 原问题、必要历史与约束。
- 是否可答、部分可答、冲突或不可答。
- 必要事实与支持原文位置。
- 一个或多个有效证据集合。
- 不允许编造的事实、引用评分规范。

多个文档可能提供等价支持，不假定唯一 chunk ID 是正确答案。评测最好保留源位置，在新切块配置上重新映射。

虚构例子：

```json
{
  "id": "q_timing_01",
  "question": "材料周一补齐后，能保证周四完成吗？",
  "answerability": "partially_answerable",
  "support_facts": [
    {"id": "F1", "text": "补齐材料后开始计时", "valid_sources": ["policy_v2:start"]},
    {"id": "F2", "text": "通常需要三个工作日", "valid_sources": ["policy_v2:duration"]}
  ],
  "required_boundary": "未给出起算日计入规则等条件，不能保证具体完成日",
  "forbidden_claims": ["保证周四完成"]
}
```

这些参考字段保留给评分，不作为提供给待测模型的答案提示。

## 4. 实验矩阵：逐步增加组件

| 编号 | 方案 | 固定什么 / 观察什么 |
|---|---|---|
| A | 人工确认充分证据 + 固定生成器 | 生成与引用的诊断参照，不是自动检索系统 |
| B | BM25 + 同生成器 | 关键词基线 |
| C | 向量 + 同生成器 | 表示检索基线 |
| D | 两路融合 + 同生成器 | 保持文档 / 最终证据预算，报告总召回预算 |
| E | D 的候选 + reranker | 尽量复用同一候选，隔离重排 |
| F | 选定基线 + 查询改写 | 固定后续模块，保留原问题与改写日志 |
| G | 选定基线 + 压缩 | 对相同原证据比较，不同时改召回 |

“人工充分证据”不是预先保证一定能答对的上限；有证据仍可能生成失败，标注也可能错误。

按任务可先运行 B 与 D 等少量方案，不必全部实现。增加复杂度应对应已观察到的瓶颈。

## 5. 三种预算分别记录

```text
初步召回预算：每路取多少候选
       ↓
重排预算：实际评分多少 query-document 对
       ↓
生成预算：最终证据 token + 其他输入 + 输出预留
```

匹配预算的示例：BM25 最多 20 个候选、向量最多 20 个候选，而混合各取 10 个再合并；这只是对照设计，不保证候选数恰好相等，去重与过滤还会改变数量。

也可比较“允许混合使用更多候选”的实用方案，但明确它包含额外计算预算。相同证据条数也不等于相同 token 数。

多查询、父段展开、重试等都计入总成本，不只记录最后一次模型调用。

## 6. 运行日志：保存每个阶段实际发生了什么

一个 run 至少保存：

| 信息 | 用于什么归因 |
|---|---|
| run ID、数据与模块版本 | 重现对照 |
| 原查询、改写与各召回查询 | 需求是否被改变 |
| 过滤范围、候选 ID / 排名 / 各路分数 | 召回与权限检查 |
| 重排分数、截断与丢弃原因 | 必要证据是否被排除 |
| 实际提供的原文 / 摘要与引用映射 | 上下文是否完整、压缩是否失真 |
| 原始模型响应、结束原因与最终答案 | 截断、解析与生成问题 |
| 各项评分、评分器错误 / 不适用 | 不把评分失败当成功 |
| 阶段耗时、token、调用与重试 | 质量与成本取舍 |

日志中的资料和用户信息需要遵循授权、去标识化与保留规则，不为了可观测性无限保存敏感全文。

## 7. 怎样分类失败？

按链路逐层检查，而不是所有坏回答都贴“幻觉”：

| 检查点 | 失败类型 | 优先行动 |
|---|---|---|
| 原资料没有答案 | 知识缺失 / 任务不可答 | 补数据源或正确报告不足 |
| 原文有，解析文本没有 | 解析损失 | 修 OCR、阅读顺序、表格等 |
| 片段不完整 | 切块 / 条件关联问题 | 调整边界、标题、父段或回取 |
| 允许资料中有证据，候选没返回 | 召回遗漏 | 检查 query、分词、向量与索引 |
| 候选有，重排后没了 | 重排 / 筛选损失 | 分析标签、排序与证据集合选择 |
| 保留后，最终输入没了 | 预算 / 上下文构造错误 | 检查截断、展开和模板 |
| 原证据正确，摘要失真 | 压缩损失 | 回看原文、减少不可靠改写 |
| 输入充分，但答案错误 | 生成 / 指令问题 | 固定证据做对照、检查模型与 Prompt |
| 回答正确但评分失败 | 评分问题 | 修 rubric、解析与 judge |
| 超时 / 检索服务失败 | 系统运行失败 | 显式报错、有限重试，不伪装成资料不足 |

一题可能同时有多种问题。例如召回漏条件，生成器又无依据保证日期。记录多标签与先发生的瓶颈，不强行分配一个唯一原因。

修复测试可以替换一个阶段：人工补入必要候选、恢复原始证据、修正模板等。但输入变化可能有其他影响，诊断对照是线索，不自动证明严格因果。

## 8. 结果表怎么报告？

至少分开：

1. 候选层的必要证据覆盖。
2. 最终证据层的事实覆盖与重复 / 干扰。
3. 生成层的正确性、引用支持与不足处理。
4. 端到端成功与运行失败。
5. 总延迟、token 与成本。

检索命中一个片段不等于所有条件齐全；含多个可选支持集合时，标注定义“完整覆盖”到底指哪一种。

按可答、不可答、多证据、精确实体与长度分层。低频高风险单独报告，不被平均值掩盖。

同题比较基线和新方案，报告样本量与不确定性。不因几题提升宣布显著，不忽略相关文档 / 会话的聚类效应。

## 9. 闭环与下一步

```text
固定评测 → 发现瓶颈 → 修改一个主要因素
                         ↓
                     验证对照
                         ↓
             加入关键回归场景 + 留出测试
```

先修被证实的问题，而不是每次增加一个新模型。线上需要有限灰度、授权与监测；离线完成不等于生产可直接上线。
