## 1. 先分清三种对象

| 对象 | 含义 |
|---|---|
| 原始文档 | PDF、网页、Markdown、工单等源资料 |
| 解析结果 | 正文、标题、表格等结构化内容与原文定位 |
| Chunk | 按规则组织的检索片段，含文本与元数据 |

```text
原始文档
   ↓ 解析、清洗、保留结构
结构化内容
   ↓ 切块、关联上下文、记录来源
可检索片段
   ↓
Embedding / BM25 索引 → 检索 / 重排 → 生成证据
```

解析不是切块，切块也不是 embedding。一个阶段出错，不应默认由后面更大的模型修复。

## 2. 解析：不仅是把文件变成字符串

### 2.1 不同资料的难点

| 类型 | 需要保留什么 | 常见错误 |
|---|---|---|
| Markdown / HTML | 标题层级、正文、列表、代码、链接 | 导航与正文混杂，代码缩进丢失 |
| 文本 PDF | 阅读顺序、页码、段落、表格 | 双栏交叉拼接、断词、页眉重复 |
| 扫描 PDF / 图片 | OCR 文本与位置、置信度线索 | 数字、负号、单位与型号识别错 |
| 表格 | 表头、行列、单位、脚注 | 只留单元格值，失去列含义 |
| 工单 / 对话 | 角色、时间、状态与最新结论 | 把历史猜测当最终确认 |

例如表格单元格只有“7”，没有“工作日”列名与适用产品，无法可靠回答处理时长。解析后的文本看起来通顺，也可能已经丢了语义。

### 2.2 清洗不能误删重要条件

可以处理重复导航、无意义页眉等，但要检查：

- “仅限”“不包括”“通常”等限定词。
- 生效日期、版本和废止说明。
- 表格脚注与例外条款。
- 源文件位置与文档关系。

遇到 OCR 或格式错误，应明确记录、修复或将文档标为不可用，不悄悄把错误文字作为权威证据入库。

## 3. 为什么要切块？越小越好吗？

切块主要在检索粒度和上下文完整性之间取舍。

| 片段较小 | 片段较大 |
|---|---|
| 容易定位具体主题，返回内容更精简 | 条件、定义与例外更容易保留 |
| 条件可能被切断，单独读不完整 | 无关内容可能稀释检索或占据上下文 |
| 片段数量增加、边界重复可能增多 | 可能超过 embedding / reranker 输入限制 |

不能把“片段相似度高”当作“片段足以支持答案”。最终要看所需证据是否能被检索并完整交给生成器。

## 4. 用同一文档比较几种切法

虚构源资料：

```text
# 申请政策
## 标准申请
标准申请通常需要三个工作日处理。
工作日不包括周末和法定节假日。
材料不完整时，补齐材料后才开始计时。
## 加急申请
加急申请适用条件与处理方式另行规定。
```

### 4.1 固定长度切块

按 token 或字符长度切。例如第一块只包含“三个工作日”，第二块包含“补齐材料后才开始计时”。

优点是简单；问题是可能切断条件、句子或表格。字符长度与模型 token 数不是同一指标，应明确使用哪种单位。

### 4.2 递归 / 分层切分

优先按标题、段落、句子等边界分割，超长段落再按更细规则处理。

不是“递归”这个词就保证语义正确：如果文档结构不可靠，或一句跨表格引用了其他条件，仍需检查。

### 4.3 结构感知切块

把“标准申请”正文与必要标题关联，不把加急条款混进标准申请片段。

可将标题路径作为检索文本的一部分：

```text
申请政策 > 标准申请
标准申请通常需要三个工作日处理。
工作日不包括周末和法定节假日。
材料不完整时，补齐材料后才开始计时。
```

此例中整段保留最容易检查；真实长段可能仍需拆分，并关联父段或相邻证据。

标题拼接是可追溯的内容组织；模型生成的摘要或标签则需要额外验证，不能把推测标题当作源文档事实。

### 4.4 语义切块

利用句子表示、主题变化等信号判断边界。它可能有帮助，但增加成本，阈值和语言会影响结果，不保证优于简单结构规则。

首轮先做可解释基线，再用固定查询集比较，不一开始就堆复杂切块模型。

## 5. Overlap：边界重复，能解决多少问题？

相邻片段保留部分重复内容，可以减少句子或局部条件在边界处丢失。

但它不保证保存相隔多页的定义与例外，还可能：

- 增加索引量与重复候选。
- 让 top-k 被同一段的多个近重复块占据。
- 让评测中跨集合的片段发生内容泄露。

小块间加入较大 overlap 不等于自动获得完整上下文。检索后去重或多样性处理要保留必要证据，而不是只按字符串相同率盲删。

## 6. 父子片段：检索单位与生成单位可以不同

```text
父段：标准申请完整规则
    ├→ 子块 A：处理时长
    ├→ 子块 B：工作日定义
    └→ 子块 C：材料补齐条件

检索匹配子块 C
         ↓
按 parent_id 回取父段或必要相邻片段
         ↓
将完整条件提供给生成模型
```

子块有较精确的检索表示；父段提供上下文。缺点是回取内容增大，仍需预算、权限和版本检查。

重排也要明确评分的是子块还是展开后的父段。**训练样本、线上重排输入与最终证据不一致，可能导致数据分布不匹配。**

不是每个任务都要父子结构。短、完整的自然段可能直接作为检索和生成单位。

## 7. Chunk 数据结构与引用

以下仅为 schema 示意：

```json
{
  "chunk_id": "policy_v2_standard_01",
  "document_id": "policy",
  "document_version": "v2",
  "title_path": ["申请政策", "标准申请"],
  "source_uri": "knowledge-base://policy/v2",
  "section_id": "standard",
  "parent_id": "policy_v2_standard",
  "text": "标准申请通常需要三个工作日处理。工作日不包括周末和法定节假日。材料不完整时，补齐材料后才开始计时。",
  "access_groups": ["support"],
  "parser_version": "parser-config-01",
  "chunking_version": "structure-config-01"
}
```

- `chunk_id` 用于索引定位；回答里的 `[D1]` 可以是本次请求的临时证据编号。
- 应保存 `[D1] → chunk_id → 源文档版本与位置` 的映射。
- 偏移、页码等只在确实可回查时记录；OCR 清洗后字符位置不一定等于原文位置。
- `access_groups` 只是元数据，不自动实现授权，后端仍需执行限制。

文档变化后重新解析 / 切块，需要清理旧索引和相关缓存，防止同时返回已废止的规则。版本策略要明确，不简单认为“修改时间最近的任何片段”都最权威。

## 8. Chunk size 怎么选？

没有通用最优长度，至少考虑：

1. 文档类型与段落语义。
2. 问题需要单个事实还是多个条件组合。
3. embedding 与 reranker 的最大输入长度和实际 tokenizer。
4. 生成模型上下文、证据数量与输出预留。
5. 返回内容质量、索引规模、延迟与成本。

embedding 输入太长可能被截断，reranker 常还需为 query 留空间；生成模型窗口很大，不代表前两者就能处理同样长的片段。

如要做实验，可选择几个结构与长度不同的候选配置，记录实际 token 分布。不要只写“size=512”却不说明是字符、token、哪种 tokenizer，也不要把某个框架默认值当行业标准。

### 8.1 最适合作为默认起点的方案

2026-10-12 查询的官方资料支持以下基线思路，但没有行业使用率统计证明某种方案“使用最多”：

- [LangChain](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)明确推荐递归分割器用于通用文本，优先段落等边界；该页面默认用字符计长度，并提醒中文等语言补充分隔符。
- [Unstructured](https://docs.unstructured.io/open-source/core-functionality/chunking)基于解析后的文档元素组块，只有超长元素才退回文本切分。它的 overlap 默认 0，正常结构块不必全部重叠。
- [Azure AI Search](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)讨论固定长度、结构边界与重叠等方案，不提供一个所有文档均最优的切法。

因此对我们的 **Hugging Face 技术文档**，建议默认：

```text
按标题划分章节，保留标题路径
          ↓
在同一章节内合并完整段落 / 列表等结构元素
          ↓
遇到超过预算的内容：
按段落 → 句子 → 更细边界递归切分
          ↓
保存来源、版本、章节与父段 ID
```

这是“结构优先 + 有界递归切分”，不要求先用 embedding 做语义切块。

首轮可选择约 512 token 作为文本预算实验起点，同时对比 256 / 1024 等配置；这些数是教学实验候选，不是行业最优值。标题、前缀和 query 等开销需核对，并服从 embedding / reranker 的实际输入限制。按目标 tokenizer 计数，不将框架的 512 个字符误读成 512 token。

Overlap 的起点：

- 完整、语义独立的结构段可以先不重叠，保留标题和父段关联。
- 被迫切断超长连续正文时，可以试少量重叠，例如约 10% 的预算，再检查重复召回与条件覆盖。
- 表格、代码与跨章节条件单独处理，不为达到长度目标任意切断；过长时设计带表头 / 定义的子块，或父段回取。

只有发现简单基线的明确问题，再考虑语义切块、父子展开或其他复杂方案，并用同一查询集验证收益。默认方案追求可解释、易检查与易迭代，不承诺一次就最佳。

## 9. 怎样评测解析与切块？

先准备独立的查询与必要证据标注，区分训练用途与测量用途：

| 对照 | 要观察什么 |
|---|---|
| 原始资料 → 解析文本 | 事实、表格与条件有没有丢失 |
| 解析文本 → chunk | 必要信息是否被拆散，能否回查 |
| 固定检索器，改变 chunk 配置 | 必要证据覆盖、重复候选、截断与成本 |
| 固定生成器与评分，使用不同检索结果 | 答案正确、条件完整、引用支持 |

多片段问题应检查联合证据覆盖，不能只标一个“最相似片段”就宣称完整召回。

重新切块后 chunk ID 会变化，评测最好同时保留源文档级的证据位置，再按新配置映射，而不是沿用已失效的旧 chunk ID。

先按文档 / 实体等分组划分，再切块或生成问答，避免同一文档的重叠块跨训练与测试。在线搜索通常允许检索测试问题对应的授权知识文档；这与将测试问答、答案或它们的近重复用于训练是两回事。实验要声明允许的知识库范围与泛化目标。

## 10. 为 Re-rank 训练打基础

后续专门讲以下内容，不在本节直接训练：

- 数据单位：query + candidate chunk，以及相关性 / 答案支持标注。
- 来源：人工证据、实际召回候选、业务日志或合成数据；点击不直接等于正确支持。
- 正例与 hard negatives：主题相似但不适用、同词不同实体、旧版本、缺少必要条件等。
- 标注等级：相关、部分支持、充分支持；多片段协作不能错误地将所有单片段都标为充分支持。
- 划分与防泄露：按 query / 文档组和近重复关系隔离。
- 目标函数：pointwise BCE / 回归，pairwise logistic / margin ranking，listwise softmax 等。
- 模型形式：cross-encoder、基于 LLM 的评分与其他排序方法；是否需要 full logits 依方法而定。
- 评测：排序指标、证据覆盖与端到端效果，不以训练损失代替收益。

这些损失是不同任务定义的候选，不是所有 reranker 同时使用的固定流程。Embedding 的对比训练与 reranker 的排序训练会分开解释。
