# 查询优化与上下文压缩：找全证据，保留关键条件

- 前置阅读：[混合检索](2026-10-12_04_bm25_and_hybrid_retrieval.md)、[Re-rank](2026-10-12_05_reranker_data_and_objectives.md)。

先看第 1～4 节的查询侧，再看证据侧。本篇的业务规则均为教学示意，不是实际政策。

## 1. 两个不同的优化位置

```text
用户问题与必要历史
        ↓ 查询优化
一个或多个检索查询
        ↓ 检索、融合与重排
候选原文
        ↓ 证据筛选、展开与可选压缩
实际给生成模型的上下文
        ↓
有依据的回答
```

- 查询优化：提高找到必要证据的机会。
- 上下文优化：在预算内提供充分、可追溯的证据。

两者都不是必选模块。基线已足够时，增加模型调用可能只增加成本和错误。

## 2. Query rewrite：让隐含问题变得可检索

历史：

```text
用户：标准申请需要多久处理？
用户：那材料不全呢？
```

直接检索“那材料不全呢”可能缺少实体与任务。可改写成：

> 标准申请材料不完整时，处理时长如何计算，从何时开始计时？

改写输入只需必要历史与确认状态，不必把整段旧对话无条件带入。

检查不得丢失或编造：

- 产品、版本、时间范围与否定条件。
- 用户问的是规则、实时状态还是具体操作。
- 历史里哪些是确认事实，哪些只是模型猜测。

例如用户问“旧版是否不支持”，不能改成“最新版支持方式”。指代不明确时请求澄清，不猜一个实体并悄悄搜索。

实用基线：保留原查询，同时将改写作为额外召回路，记录来源。重排或生成仍应知道原始问题，防止仅忠实于错误改写。

## 3. Multi-query：不同表达找互补候选

例如问题：

> 材料没齐会影响三个工作日的处理时长吗？

可以构造：

1. 标准申请材料不完整的处理规则。
2. 标准申请处理时长的起算条件。
3. 补齐材料后如何计算工作日。

各查询独立召回，合并、去重，再围绕原始需求重排。可以复用 RRF 等融合方式，但需记录路数与预算。

同义改写用于覆盖不同措辞；多方面查询用于覆盖不同证据需求。二者不同，多方面需求下一节可以显式分解。

风险：改写越多不保证覆盖越好，相近查询可能重复强化同一偏向，也会增加延迟与候选量。限定数量，以独立查询集验证增益。

## 4. Query decomposition：把复杂问题拆成证据需求

问题：

> 周五提交标准申请，材料周一才补齐，预计什么时候处理完？

需要的证据可能包括：

- 材料不全是否影响起算点。
- 标准申请通常需要几个工作日。
- 工作日定义与适用节假日。
- 起算日是否计入，若资料未给出则无法确定。

拆问题不是提前猜出答案。必要条件缺失时，即使前三项找到，也不能保证给出精确日期。

有依赖的查询可能需要先取事实再继续检索；独立子问题可以并行。这是与 Agent 主动检索的衔接，但本节不实现规划循环。

## 5. HyDE：假设文档用于检索，不用于证明

HyDE 是 Hypothetical Document Embeddings。一种典型思路：

```text
问题
 ↓
模型生成一段假设性的答案 / 文档
 ↓
将假设文档编码为向量
 ↓
检索真实语料
 ↓
用取得的真实证据回答
```

例如短查询与文档风格差异较大时，假设文本可提供更接近文档形式的检索表示。

关键边界：

- 假设文档可能错误，它不是事实、标签或引用证据。
- 如果假设“收到材料即计时”是错的，可能将检索带向不适用规则。
- 实体、版本与权限仍需可靠处理。
- 不是所有 embedding 模型都适合把生成文本直接代替 query 编码；遵循模型协议并验证。

可以保留原查询检索作为对照或补充，不将 HyDE 当默认必胜方案。原论文见 [HyDE](https://arxiv.org/abs/2212.10496)。

## 6. 上下文优化：先筛选，再考虑摘要

候选不应全塞进上下文，但“只保留第一名”也可能遗漏组合证据。

一个可解释起点：

1. 执行权限与版本规则，排除不允许的资料。
2. 重排并检查相关候选，去除明显无关内容。
3. 去重，防止同一信息占满预算；不误删互补条件。
4. 必要时按父段或相邻片段回取定义、例外和表头。
5. 保留来源、位置与本次引用 ID。
6. 确认总 token 预算，并为生成预留空间。

重排分数不是支持度的绝对保证。原文必须可回查，资料读取失败与确实无答案是不同状态，不静默合并。

## 7. 三种压缩方式

| 方法 | 做什么 | 风险 |
|---|---|---|
| 抽取式压缩 | 选原文句子、段落或表格行 | 可能漏掉上下文、脚注与例外 |
| 生成式摘要 | 模型改写、缩短证据 | 可能编造、改数值或把限定说成保证 |
| 表示 / token 压缩等专用方法 | 改变传入表示或文本组织 | 依赖具体模型与实现，解释和引用可能复杂 |

首轮优先可回查的原文筛选与结构展开，不必先加摘要模型。

例如：

```text
原文：通常需要三个工作日；材料不齐时，补齐后才开始计时。
错误摘要：申请三个工作日内完成。
```

错误摘要同时丢失“通常”和起算条件。压缩 token 更少，但任务信息更差。

抽取式也不是天然安全：只抽第一分句，同样会漏条件。保留“这一句适用谁、在什么条件下”的必要上下文。

## 8. 摘要的引用应该指向哪里？

摘要是派生内容，需记录它来自哪些源片段，以及压缩配置 / 模型版本。

如果摘要涉及 D1、D2 两份资料，应保留原始片段供校验，不让生成器引用一个无法回查原文的新编号就声称有依据。

可选择：

- 原文直接提供给生成器，摘要只用于筛选或导航。
- 摘要与必要原文同时提供，明确它不是独立权威。
- 只提供摘要的路线需单独验证压缩失真与来源支持，报告限制。

原始证据的矛盾不能被摘要“自动统一”为新结论；有版本规则按规则处理，没有规则则保留不确定性。

## 9. 如何评测这些模块的真实收益？

固定语料、查询与证据标注，逐项对照：

| 对照 | 检查 |
|---|---|
| 原查询 vs 改写 | 需求是否保真，必要证据覆盖是否提高 |
| 单查询 vs multi-query | 互补覆盖、重复率、总召回预算与延迟 |
| 原查询检索 vs HyDE | 查询类型分层收益与错误假设带来的偏移 |
| 原证据 vs 压缩证据 | 条件、数字与出处保留，最终正确性 |

多查询用更大候选预算，不能把收益全部归因于表达改写；报告预算差异，必要时增加匹配预算的对照。

压缩可以改善成本，但若降低关键事实支持，不是无条件收益。评测至少包含可答、多片段、不足、矛盾、精确实体与长资料类型。

校准与调参用验证集，最终测试集留出。不要只看模型生成摘要是否通顺，也不把平均 token 减少率当成任务质量。
