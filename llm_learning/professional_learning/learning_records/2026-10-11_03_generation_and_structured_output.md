本专题开始应用层主线。先看第 1～4 节的生成流程，再看结构化输出与校验。具体参数名、支持的 schema 和默认值随模型、API 与版本变化；本篇不声称所有服务实现一致。

## 1. 整体流程：模型分数不等于最终选择

模型根据当前上下文输出词表 logits。解码策略决定如何选择下一 token：

```text
上下文 → 模型 → 下一 token 的 logits
                       ↓
             约束 / 惩罚 / 分数处理
                       ↓
               贪心选择或采样
                       ↓
                 追加新 token
                       ↓
          检查 EOS、停止条件、生成预算
                       ↓
              继续生成或返回结果
```

具体处理顺序由实现决定。生成参数通常不更新模型权重，只改变本次解码行为。

## 2. 贪心与采样

### 2.1 贪心：选分数最高的 token

$$
y_t=\operatorname{argmax}_v z_v
$$

这是逐步的局部选择，不保证整段回答概率最大，也不保证回答正确。通常适合建立稳定的抽取、分类或问答基线。

即使不采样，也不能承诺跨硬件、版本、并行实现的结果逐字一致。

### 2.2 采样：按概率随机选择

例如概率为：

| token | 概率 |
|---|---:|
| A | 0.6 |
| B | 0.3 |
| C | 0.1 |

采样可能选择 A、B 或 C。一次没选到 A 不是错误；多样性可以用于写作、候选探索和 best-of-N，但也增加输出波动。

离散采样是推理选择，不等于我们前面学习的策略梯度更新。

## 3. Temperature、top-p 与 top-k

### 3.1 Temperature：调整概率分布的尖锐程度

$$
p_i(T)=\frac{\exp(z_i/T)}{\sum_j\exp(z_j/T)},\qquad T>0
$$

- T 较小：更加集中于高分 token。
- T 较大：更加平缓，低分 token 更有机会被选中。
- T=1：不进行这种温度缩放。

例如 logits 为 $[2,1,0]$：

| T | 概率（约） |
|---:|---|
| 0.5 | [0.867, 0.117, 0.016] |
| 1 | [0.665, 0.245, 0.090] |
| 2 | [0.506, 0.307, 0.186] |

“温度低就一定准确”是误解：模型若最偏好错误答案，低温度可能更稳定地输出错误答案。

公式不能直接代入 T=0。某些 API 用 `temperature=0` 表示近似贪心或特殊模式；本地框架也可能要求用 `do_sample=False`。按接口说明设置，不默认等价。

### 3.2 Top-p：保留累计概率达到阈值的高概率候选

将候选按概率降序排列，保留累计概率达到 p 的最小前缀，再重新归一化采样。

例如概率为 $[0.6,0.3,0.1]$，top-p=0.8：

```text
只保留 A：累计 0.6，不够
加入 B：累计 0.9，达到阈值
因此保留 A、B，排除 C
```

重新归一化后 A、B 的概率为 $2/3$、$1/3$。候选数量由当前分布决定，不固定。

### 3.3 Top-k：固定保留最多 k 个高分候选

例如 top-k=2，保留 A、B。它与 top-p 的区别是数量阈值与累计概率阈值。

API 不一定支持 top-k。temperature、top-p 和 top-k 可以共同作用，但顺序依实现；初次对照先改变一个因素，避免难以归因。贪心模式下，采样参数可能不生效或被拒绝。

### 3.4 主流供应商是否都允许配置这些参数？

不一定。解码原理与 API 暴露的控制项是两回事。必须按供应商、模型版本、端点和思考模式核对；SDK 字段存在不保证服务端支持。

## 4. 长度、结束与重复控制

| 参数 / 条件 | 作用 | 常见误解 |
|---|---|---|
| 最大新 token 数 | 限制本次生成的 token 预算 | 不保证回答在此之前完成 |
| 总序列长度限制 | 可能包含输入与输出 | 不等于最大新 token 数 |
| EOS | 模型的结束标记 | 不一定是普通可见文本 |
| stop 字符串 / token | 命中约定条件后停止 | 可能误切文本，返回方式依接口 |
| repetition penalty 等 | 修改重复 token 的分数 | 不保证消除循环，过强会破坏正常重复 |
| frequency / presence penalty | 某些 API 按出现次数或是否出现处理分数 | 不与所有本地 repetition penalty 等价 |

生成预算耗尽，可能得到不完整 JSON 或未完成的回答。读取结束原因、拒绝状态与错误，不能把任何返回文本都当作成功。

对于思考模型，还需核对思考与最终回答如何计入预算；不是所有接口都接受相同生成参数。

### 4.1 Messages API 能配置 beam search 吗？

常见的 OpenAI Responses / Chat Completions、Anthropic Messages、Gemini generateContent 公共生成接口通常不提供像 Transformers `num_beams` 这样的通用 beam search 控制项；具体端点可能有扩展，不能由 messages 请求结构或 OpenAI-compatible 名称判断支持。

本地 Transformers 可用 `num_beams>1`、`do_sample=False` 执行普通 beam search。每步保留若干较优候选前缀，扩展后按序列评分剪枝；最终选保留下来的较优序列，不保证找到所有可能序列中的全局最优答案，也不保证事实正确。

一次返回多个候选或 best-of-N 通常不等同于 beam search：前者可以是独立完整采样后选择，后者是在各生成步维护和剪枝候选前缀。

来源：[Transformers 解码策略](https://huggingface.co/docs/transformers/generation_strategies)。本节介绍公共接口的常见范围，不推测供应商内部是否使用 beam search。

### 4.2 Repetition penalty 怎么工作？

它用于减少不希望出现的 token 重复。以 Transformers 常见实现为例，对已出现 token 的 logit z，惩罚系数 p>0：

$$
z'=
\begin{cases}
z/p,&z\ge0\\
pz,&z<0
\end{cases}
$$

当 p>1 时，正分数降低，负分数变得更负，降低这些 token 相对于未受惩罚候选的吸引力。p=1 不改变分数；0<p<1 则通常鼓励重复。

例如 p=1.2，已出现 token 的分数 6 变为 5，-2 变为 -2.4。不能对负数也一律除以 p，否则会反而提高它。

这是针对 token 的启发式处理，不是理解“这句话是否重复”。某些实现会包含 prompt 中出现的 token、只看局部窗口，或每个已出现 token 只处理一次；按具体实现核对。它不等同于按次数递增的 frequency penalty。

过强惩罚会伤害正常重复，例如实体名、代码变量、JSON 字段或引用编号；不能保证消除语义循环或幻觉。不要在事实抽取和代码任务中默认使用很强的重复惩罚。

### 4.3 Stop 的作用是什么？

stop 指定遇到某个字符串或 token 序列时停止生成，具体匹配方式由接口决定。例子：

```text
约定模型格式：
回答正文
<END_ANSWER>

stop 设置为 <END_ANSWER>
```

命中后服务停止返回后续生成内容。某些 API 会从返回文本中去掉停止字符串，另一些实现可能保留；跨多个 token 的匹配也应由支持的解码接口处理。

它不同于：

- EOS：模型使用的结束 token。
- 最大输出 token 数：数量上限，不要求出现某个字符串。
- 格式约束：stop 不保证输出 JSON 完整或符合 schema。
- 语义判断：stop 不知道问题是否答完。

不应随意用 `}` 停止 JSON：嵌套对象的第一个结束括号可能就会触发，得到截断对象。换行、标点和常见词作为 stop 也可能过早截断正常答案。使用不容易与正文混淆的协议标记，确认模型会输出它，并检查接口支持及结束原因。

## 5. 结构化输出：三种层次

希望模型提取订单编号和金额：

```json
{"order_id": "A123", "amount": 99}
```

| 做法 | 能解决什么 | 不能保证什么 |
|---|---|---|
| Prompt 要求“只输出 JSON” | 通过指令改善格式 | JSON 永远可解析、符合 schema |
| JSON 模式 | 支持接口通常约束 JSON 语法 | 必然符合你的业务字段 schema |
| Schema / grammar 约束解码 | 在所支持规则下限制合法输出 | 字段事实正确、引用正确、操作有权限 |

这些名称在不同供应商中可能不同，需检查实际契约，而不是只看营销名称。

## 6. 约束解码是什么？

在下一 token 选择时，根据当前输出前缀和语法 / schema，屏蔽不允许的候选，继续选择合法 token。

```text
当前已输出：{"amount":
       ↓
语法与 schema 决定接下来允许什么
       ↓
屏蔽不合法候选 → 模型从合法候选中生成
```

例如 schema 规定 amount 是数值，严格支持的实现可以限制它不输出普通字符串。但 tokenizer 的 token 可能包含多个字符，具体允许集合由解码器处理，不是简单每次选一个字符。

约束改变可选输出，不自动解决语义。例如合法 JSON：

```json
{"order_id": "A123", "amount": 999}
```

如果原文金额为 99，这仍是错误答案。

此外，schema 子集、拒绝响应、截断和运行失败都可能影响最终结果。不能声称任何请求在任何情况下都一定返回完整合法对象。

## 7. 后端校验：结构化输出不是业务安全边界

建议按顺序处理：

```text
检查调用状态 / 结束原因
          ↓
解析 JSON
          ↓
校验 schema：字段、类型、必填、允许值
          ↓
校验业务语义：与原文 / 数据库是否一致
          ↓
权限、确认、幂等与事务检查
          ↓
执行或返回显式错误 / 请求澄清
```

金额缺失时，协议应明确用 null、返回不足状态还是请求澄清，不应默认填 0。引用了存在的 `[D1]` 也不代表证据支持正确。

失败处理：

- 截断：明确输出未完成，再评估是否增加预算或重试。
- schema 错误：报告具体失败，有限修复 / 重试并重新验证。
- 事实不确定：保留不足状态，不通过格式修复“补出”事实。
- 有副作用的操作：避免解析重试导致重复执行，校验与执行分开。

不要无限重试直到某次输出能解析，也不要把失败对象静默转为空对象、默认值或成功结果。

## 8. Function Calling 与结构化输出的关系

Function Calling 通常让模型生成工具名称与结构化参数。例如：

```json
{"name": "get_order", "arguments": {"order_id": "A123"}}
```

具体 API 可能返回不同字段结构，arguments 也可能是 JSON 字符串；示例不是所有 SDK 的实际返回类型。

模型提出调用不等于已经执行。后端负责检查工具是否存在、参数是否有效、调用是否授权，再执行并将结果回填。

工具 schema 可以利用结构化生成机制，但工具选择正确性和多步任务完成仍要评测；工具调用专题后续再深入。

## 9. 如何做一个小对照？

以给定资料问答或 JSON 抽取为例，在同一组独立问题上比较：

1. 合理 prompt + 贪心基线。
2. 同模型低温采样，多次运行看波动。
3. 支持时使用 schema 约束，保持任务与校验相同。

记录：

- 任务正确率，而不只看格式。
- JSON 可解析率、schema 合规率。
- 截断率、拒绝 / 不足率，区分合理拒绝与错误拒绝。
- 引用支持或字段证据正确性。
- 输出长度、延迟、token 成本与重试次数。

固定模型版本、prompt、schema、tokenizer / SDK 与参数；跨模型时遵守各自模板和支持规则。保留不支持或报错的配置，不悄悄改成默认值后声称对照成功。
