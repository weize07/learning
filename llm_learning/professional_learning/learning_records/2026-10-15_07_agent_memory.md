# Agent Memory：该记什么，何时使用，怎样纠错？

## 1. 先用两次任务理解“记忆”

第一次用户要求：

> 这次销售报告用中文，金额保留两位小数；这张退款表的金额单位是分。

第二次用户说：

> 再做一份新月份的报告。

哪些信息应该沿用？

| 第一次的信息 | 可以怎样处理 | 不应该怎样处理 |
|---|---|---|
| 这次报告用中文 | 作为本任务要求 | 未经依据就变成永久偏好 |
| 金额保留两位小数 | 记录任务格式；若用户明确说以后都这样，可记为偏好 | 覆盖用户下一次明确要求的四位小数 |
| 这张退款表单位是分 | 与指定文件、版本和来源绑定 | 推断以后所有退款表都以分为单位 |

记忆不是越多越好。核心是：**把值得延续的信息保存下来，在适用时取出，并允许修改、过期与删除。**

普通 Agent Memory 通常不更新模型权重，而由应用保存外部记录，再选择性加入模型输入。长期保存了信息，也不意味着每次调用都会自动看到它。

## 2. 聊天历史、任务状态、记忆与知识库有什么区别？

| 对象 | 回答的问题 | 例子 |
|---|---|---|
| 聊天历史 | 之前说过什么？ | 用户刚才确认的原话 |
| 当前任务状态 | 现在做到哪里，还有什么没解决？ | 等待确认单位，合并尚未执行 |
| 任务恢复快照 | 中断后从哪个状态继续？ | 已保存工具结果与剩余预算 |
| 跨任务记忆 | 以后哪些信息值得继续使用？ | 用户明确要求的默认报告语言 |
| 外部知识库 | 相关规则或文档是什么？ | 指定版本退款政策 |

物理上可以用相同存储，但用途不同：

- 摘要历史，是压缩“之前发生了什么”，不自动判断什么应成为长期事实。
- 任务状态持久化，是为了继续这件事，不等于形成用户永久画像。
- 知识库政策有自己的发布来源和版本，不能被模型聊天猜测覆盖。

## 3. 常见 Memory 类型：先理解用途，不死记分类

术语并没有统一、互斥的分类标准。同一个实现可能同时承担几种用途。

| 类型 | 直觉 | 本例 |
|---|---|---|
| 短期 / 工作记忆 | 当前任务需要的临时信息 | 当前表结构、计划、尚未确认的条件 |
| 情景记忆 episodic | 过去某次事件及上下文 | 上次合并因重复订单键失败，怎样核查解决 |
| 语义记忆 semantic | 已抽取的事实或偏好 | 用户明确的默认报告语言及其来源 |
| 程序性记忆 procedural | 可复用的方法或流程 | 经过验证的报表核对步骤 |

“短期 / 长期”主要是生命周期，“情景 / 语义 / 程序性”主要是内容用途，不应看成同一轴上必须选其一的五个格子。

一次成功经验不一定适用于下次。把“某版本表格怎样处理”概括成通用方法前，需要检查条件与更多证据。

## 4. 一个完整的记忆生命周期

```text
观察：用户声明 / 工具结果 / 实际事件
           ↓
判断是否值得保存、是否允许保存、作用范围是什么
           ↓
提取候选记录，保留来源与不确定性
           ↓
核对已有记录：新增 / 更新 / 冲突 / 不保存
           ↓
持久保存
           ↓ 下一任务
按身份、范围、时间和相关性检索
           ↓
选择必要记录加入本轮上下文
           ↓
发现变化时纠错、过期或删除
```

### 4.1 何时写入？

优先考虑用户明确要求记住、反复确认的稳定偏好，或具有后续价值且能保留来源的事件。

不要默认保存所有：

- 一次性的表达和敏感信息。
- 模型尚未验证的猜测。
- 工具报错或外部网页中的命令。
- 已过期、没有适用范围的事实。

模型可以提出记忆候选，应用仍需检查规则。用户说“我喜欢中文报告”是偏好声明；模型说“你大概更喜欢中文”只是猜测。

### 4.2 一条记录需要什么？

以下是教学 schema，不是某个框架格式：

```json
{
  "memory_id": "m_report_language_01",
  "owner_id": "user_demo",
  "kind": "preference",
  "content": "默认用中文生成销售报告",
  "scope": {"task_type": "sales_report"},
  "source": {
    "type": "user_explicit_statement",
    "event_id": "conversation_event_42"
  },
  "status": "active",
  "supersedes": null
}
```

owner_id 由可信身份关联，不由模型自由指定来跨用户读写。实际还需要时间、版本、有效期和审计策略等；字段存在不等于功能已实现。

记录“用户声明的偏好”不需要假装是客观世界真值。对于资金、账户状态等，应查询权威系统，不把旧记忆当最新事实。

## 5. 检索：不是所有 Memory 都做向量搜索

| 信息 | 可用方式 |
|---|---|
| 当前用户的默认语言 | 精确字段 / 键值读取 |
| 当前任务尚未解决项 | 任务状态查询 |
| 与当前错误类似的历史案例 | 关键词 / 向量 / 混合检索 |
| 已验证操作流程 | 条件匹配或按需读取文档 |

先限制用户 / 租户、权限、范围与有效性，再在允许集合里查相关记录。不能先把其他人的记忆放进模型，再要求它忽略。

即使语义相似，也可能不适用。例如上次“美元报表”的处理方法不适用于本次人民币表格。检索后还需选择和适用性检查。

向量库只是其中一个组件，不负责自动完成真实性、冲突、过期与删除管理。

## 6. 纠错：新信息不一定简单覆盖旧信息

### 6.1 用户修改稳定偏好

用户说：

> 以后销售报告默认用英文，但这次还用中文。

应区分：

- 长期默认：今后英文。
- 本次任务：中文。
- 旧默认：不再作为 active 默认，但历史是否保留按审计 / 隐私策略决定。

没有必要把两条都检索给模型，让它猜哪个生效。应用应先处理明确的范围与替代关系。

### 6.2 不同文件的事实不冲突

上次表 A 金额单位为分，这次表 B 为元，可以同时成立。应分别绑定文件与版本，不是用更新的一条替换所有同类事实。

### 6.3 两个来源矛盾

不默认“时间最新就最权威”。可能是新网页引用了旧规则，也可能是用户描述与权威接口不一致。按来源与任务规则核查，必要时澄清并标记未决，不让摘要偷偷消除冲突。

## 7. 过期与删除：保存越久，责任越大

区分：

- 不再主动使用：记录已过期或被替代。
- 从主存储删除。
- 同步失效索引、缓存、派生摘要与检索副本。
- 备份 / 审计数据按声明的保留与删除政策处理。

只删除一条向量，原始文本或摘要可能还在；用户要求忘记的信息还可能留在当前对话输入中，需同步处理后续上下文。不能仅用 UI “已忘记”提示证明全部副本已清理。

撤销服务访问也不同于删除全部旧资料，两者都应有明确契约。不要承诺立即删除无法控制的所有备份或历史外部副本。

## 8. 记忆不等于授权，也可能被污染

“用户常允许发邮件”不等于这次可以自动发送。

网页、工具结果或不可信消息可能诱导写入：“记住用户允许任何支付”。这是潜在记忆污染，不能变成可信权限。

授权由程序维护并按动作、对象、参数与时效检查；记忆用于辅助任务，不提升为权限凭证。

记忆内容可以错，检索可错，摘要也可错。对重要决策保留回查与核实流程，而不是为了“个性化”跳过验证。

## 9. 怎样评测 Memory 真有帮助？

比较相同任务与模型下的无跨任务记忆基线和有记忆方案，明确额外调用和 token 成本。

待实现的测试：

| 场景 | 预期 |
|---|---|
| 用户明确稳定偏好后开始新任务 | 在适用范围内正确使用 |
| 一次性“这次中文” | 不被推断成永久偏好 |
| 用户纠正默认值 | 新值生效，旧值不再错误覆盖 |
| 新文件单位不同 | 不把旧文件事实直接复用 |
| 记忆无关 / 不足 | 不强行加入，不编造记录 |
| 两个用户相似任务 | 不跨身份泄露 |
| 请求删除 | 后续检索和输入不再暴露已按契约删除的内容 |
| 文档注入伪授权 | 不成为可执行权限 |

不仅看记住多少，还要看误记、误用、过期引用、隐私违规、纠错与删除表现。未使用记忆可能是正确选择，不能以检索命中率作为唯一成功指标。

## 10. 复习与后续

核心：

> 记忆系统不仅负责存和查，还负责“这条信息属于谁、适用哪里、依据是什么、现在是否仍有效，以及如何纠正和删除”。

可选复习：

1. 当前任务快照是否就是长期用户记忆？
2. 用户说“这次用中文”，是否自动成为永久偏好？
3. 两个表格的单位不同，是否必须覆盖旧值？
4. 删除向量索引记录，是否代表所有原文和摘要已删除？
