## 1. 是什么：Skill 是方法包，渐进式披露是加载策略

用户要求：“把销售表格整理好，按公司模板输出报告，并转成 PDF。”

Agent 不必一开始就读完全部办公、数据库、编程与设计手册。可以先看到技能目录，发现相关技能，随后获取具体操作方法，再按需读取模板或运行工具。

**Skill 是可复用的任务方法包；渐进式披露（progressive disclosure）是先给少量索引、需要时再给详细内容的策略。**

采用 Agent Skills 格式时，一个示意目录是：

```text
quarterly-report
  SKILL.md
  references
    metric-definitions.md
  scripts
    validate_report.py
  assets
    report-template.docx
```

这是示意，不是在本工作区安装技能。核心文件包含 frontmatter 元数据与正文，例如：

```markdown
---
name: quarterly-report
description: 根据已确认的季度口径整理业务报告，包含数据核验和模板交付。
---

先确认时间范围与金额单位；输出前核验合计与引用。
需要计算口径时读取 references/metric-definitions.md。
```

| 部分 | 告诉 Agent 什么 |
|---|---|
| name / description | 我是什么、什么时候该用 |
| 指令正文 | 该怎么做、注意什么、怎样验收 |
| references | 某个步骤需要的详细知识 |
| scripts | 可由执行工具运行的程序 |
| assets | 模板、示例或其他产物资源 |

Skill 不修改模型权重，不是一个独立运行的 Agent，也不保证正文已经执行。加载后仍由原来的 Agent 继续决策。

## 2. 为什么要做：既不能全部塞入，也不能完全不告诉模型

两种极端都有问题：

- **全量注入**：把所有方法正文塞进每次请求，浪费上下文，增加无关指令冲突。
- **完全隐藏**：方法虽然在磁盘上，但模型不知道它存在，也不知道怎样找到。

折中是“可发现的小目录 + 按需加载的大正文”。

教学估算：100 个技能，每个正文约 2,000 tokens，全量为约 200,000 tokens；若每个摘要约 50 tokens，目录约 5,000 tokens，再加载一个正文约 2,000 tokens。这个比较只说明数量级，不含模板、工具定义、历史、格式开销与重复内容，也不是任何框架的实测收益。

目录本身仍随技能数增长。技能数很多时，还要考虑分组、筛选或检索，不能把“有目录”理解为无限扩展。

## 3. 怎么做：目录 → 正文 → 具体资源

### 3.1 三层披露

| 层次 | 何时提供 | 示例 |
|---|---|---|
| 第一层：元数据 | 开始时或目录刷新时 | 季报技能的名称与适用描述 |
| 第二层：操作指令 | 请求匹配后 | 先确认口径、再统计、最后核验 |
| 第三层：资源 | 具体步骤需要时 | 某项指标定义、模板、校验脚本 |

目录放在 system、user 消息还是其他上下文位置，由框架决定。**标准化技能格式，不等于标准化所有框架的 request payload。**

一种教学信息流：

```text
Request 1: user task + skill summaries + tool definitions
Model: request loading the relevant skill
Runtime: resolve skill and return instructions
Request 2: history + loaded instructions
Model: read the needed reference or invoke an execution tool
Runtime: enforce permissions and report the actual result
```

也可以由用户显式选择技能，或宿主确定性加载；不要求每次都由模型先发起工具调用。

### 3.2 加载、执行与权限是三件事

- **加载**：把正文或资源内容提供给模型。
- **执行**：某个工具真实运行程序、修改文件或访问服务。
- **授权**：系统判断该动作、目录、身份与副作用是否允许。

脚本可由工具运行而不把整个源码塞给模型；但工具、解释器、依赖和权限必须实际存在。加载一个“导出 PDF”技能，既不代表已经导出，也不表示渲染引擎已安装。

技能中的“可以访问所有文件”没有授予系统权限的效力。规范中的实验性 `allowed-tools` 字段也不能被当成所有实现都强制执行的安全边界。

### 3.3 渐进式披露不等于自动遗忘

正文一旦以消息形式进入历史，后续可能继续携带，直到上下文构造、裁剪或压缩机制改变它。

因此要分别回答：

1. 当前目录暴露了哪些技能？
2. 当前请求实际包含了哪些正文？
3. 历史里还留着哪些旧版本？
4. 新任务是否复用了不该复用的旧任务上下文？

“只加载过一个技能”不代表下一步只付一个技能的 tokens；历史、工具输出与其他上下文都要计入。

### 3.4 如何写好触发描述与正文

| 部分 | 建议 | 避免 |
|---|---|---|
| 描述 | 明确适用任务与关键边界 | “万能助手，所有问题都适用” |
| 正文 | 先给步骤、决策条件与验收 | 把所有参考资料原样拼进去 |
| 资源引用 | 标明何时需要、怎样定位 | 要求每次读完全部资源 |
| 脚本 | 明确输入、输出、失败与副作用 | 把执行成功当成业务成功 |
| 版本与来源 | 可追溯、可更新、可信来源 | 未审查的外部包自动获得执行权 |

“不用读完整参考手册”不等于可以跳过与当前动作有关的安全规则。

## 4. 为什么这么做：方法复用，不增加不必要的执行主体

| 与谁比较 | 关键差别 |
|---|---|
| 普通 prompt | Skill 将可复用方法、资源与适用范围打包；不是独立于 prompt 的魔法能力 |
| Tool | Tool 执行动作；Skill 解释什么时候、怎样组合动作 |
| MCP | MCP 连接外部能力；Skill 可以教 Agent 怎样使用这些能力，两者可组合 |
| RAG | RAG 常取任务事实；Skill 常取操作方法，但检索机制可以共享 |
| Memory | Memory 记录用户 / 任务中形成的状态与经验；Skill 通常是主动维护的方法包 |
| Multi-Agent | 多 Agent 划分执行主体；多个 Skills 可以由同一个主体使用 |
| MoE | MoE 在模型内部选择参数；Skill 在应用侧选择上下文 |

**分析**：若问题只是“不同任务需要不同操作手册”，先考虑单 Agent + Skills，而非直接拆出多个 Agent。只有出现独立上下文、并行探索或不同执行责任等需求，才进一步评估多 Agent。

代价与失败模式：描述可能误触发或漏触发；分层读取增加往返；多个技能可能冲突；旧正文留在历史中；外来指令或脚本可能不可信。渐进式披露优化信息供给，不消除模型错误和运行时风险。

## 5. 可测的验收与后续阅读

以下是待实施的验收设计，不是已有运行结果：

| 测试 | 直接观察什么 |
|---|---|
| 表格请求与无关问答混合 | 正确技能加载率、误加载率、漏加载率 |
| 第一请求 | 只有摘要，没有未选技能的正文 |
| 加载技能但未调用执行工具 | 文件和外部系统无变化 |
| 引用资源 | 路径可解析，未自动读入全部资源 |
| 禁止写文件的任务加载写作技能 | 写操作仍被执行策略拒绝 |
| 多轮加载后继续对话 | 实际 payload 与 tokens，而非只统计初始目录 |
| 与全量正文 / 无技能基线比较 | 同任务成功率、成本、延迟和错误类型 |
