# 1. 预训练数据管线与数据契约

> 2026-10-21 补充；待阅读。本文为设计讲义，未采集数据或执行训练。
> [专题入口](README.md) · 下一章：[分布式处理与去重](2026-10-21_02_distributed_processing_and_dedup.md)

## 1. 是什么：把“资料”变成可追溯、可训练的数据版本

预训练数据管线不只是下载文本再 tokenize。它把不同来源的数据转换为训练输入，并回答：来源能否使用、内容是否保真、哪些记录被筛掉、训练实际看到什么、如何复现。

| 阶段 | 典型训练单元 | 数据工作的重点 |
|---|---|---|
| 预训练 / 继续预训练 | 文档、代码、结构化内容及其 token 序列 | 覆盖、质量、重复、域 / 语言配比、长度与边界 |
| SFT | 给定上下文的正确回答或动作 | 条件与答案一致、模板、监督位置、任务覆盖 |
| 偏好学习 | 同一条件下可比较的候选与偏好 | 比较条件一致、标注规则、偏好可信度 |
| 环境 RL | 任务、初始环境、rollout 与反馈 | 可执行性、奖励可信度、环境版本与数据时效 |

后训练仍依赖数据生产，但不能把预训练网页机械改成问答，也不能把全部日志当作 SFT 正例。已有 [SFT 教材](../2026-10-10_01_sft_and_training_data.md)负责训练目标，本章负责其上游数据交付。

## 2. 为什么要做：输入“干净”不等于训练有效

一份 HTML 可能同时包含正文、导航和代码；正文抽取若丢掉标题、表格列名或缩进，格式通过也可能语义错误。一次过滤升级若把少数语言大量排除，总体通过率上升反而会损害覆盖。

因此需要保留每个阶段的质量和分布变化，而非只保存最终文件。

## 3. 怎么做：先定义层次，再定义处理步骤

### 3.1 一条教学管线

```text
Source registry + permitted-use decision
  -> Authorized ingestion
  -> Restricted source snapshot
  -> Parse and normalize
  -> Privacy / eligibility / quality gates
  -> Global deduplication + split grouping
  -> Evaluation-overlap audit
  -> Tokenize and mix
  -> Pack and validate
  -> Versioned manifest
  -> Training consumption report
```

这是逻辑顺序，不是所有系统的唯一执行顺序。重复簇和划分可联动计算；高风险记录应尽早隔离，后续变换还需复检。原始快照也必须遵守许可、访问控制和保留期限，不能以“可复现”为由无限保存。

| 层 | 保存什么 | 不应做什么 |
|---|---|---|
| 来源登记 | 来源、取得方式、使用范围、保留和删除约束 | 用“网上公开”代替可训练授权 |
| 原始层 | 获准保存的原始内容、获取时间、内容哈希 | 覆盖旧内容后仍沿用相同版本 |
| 规范层 | 正文 / 结构、语言、父记录、处理器版本 | 丢掉出处后只留一列 text |
| 筛选层 | 通过 / 拒绝 / 隔离状态、命中规则与分数 | 无记录地删除，或把未知状态当通过 |
| 训练层 | token、长度、划分、配方与 packing 信息 | 只保存权重，不保存训练数据版本 |

正文抽取要按来源类型处理：网页去导航但保留标题层次；代码保留缩进与文件上下文；PDF / OCR 保存页码和阅读顺序；对话保留角色和回合。统一 schema 不意味着统一破坏性清洗。

### 3.2 最小数据契约

| 字段组 | 示例字段 | 用途 |
|---|---|---|
| 身份 | `record_id`, `source_id`, `content_hash` | 区分记录身份、来源身份和内容相同 |
| 血缘 | `parent_ids`, `transform_version` | 找到清洗、翻译、合成后的派生关系 |
| 使用限制 | `usage_policy_id`, `retention_policy_id` | 可用范围可审计，不能仅放一个“合规”布尔值 |
| 内容 | `text`, `language`, `domain`, `document_group` | 支持处理、分层抽样和集合隔离 |
| 决策 | `decision`, `reason_codes`, `quality_scores` | 区分通过、拒绝、需人工复核 |
| 训练派生 | `split`, `tokenizer_version`, `token_count` | 固定划分与 token 统计口径 |

`record_id` 不宜直接用会随清洗变化的正文哈希替代。内容相同可能来自不同许可的来源；正文改变也不应失去原始血缘。

交付 manifest 至少包含输入快照、处理代码 / 配置版本、输出分片及校验和、记录 / token 数、划分规则、配方、tokenizer 和质量报告。随机过程记录种子；远程模型服务还要记录可获得的模型版本，但种子不保证远程生成完全可重现。

### 3.3 Tokenization 与 packing 也是数据质量问题

Tokenization 将内容变成模型词表中的 ID；packing 将多条内容组织成训练序列。它们都可能改变模型实际学到的分布。

- 使用与目标模型相容的 tokenizer，固定特殊 token 和版本。
- 统计过滤后、截断后、实际参与损失的 token，不能只报原文件字节数。
- Packing 不得混入 dev / test，不得因切片丢失数据身份和边界记录。
- 文档间插入 EOS 不等于 attention 隔离；是否允许读取前一文档、是否重置位置，取决于训练目标和实现。
- 对 SFT 还要核对监督 mask；更高的 packing 利用率不保证标签仍正确。

例如两篇文档各有 5、7 个 token，序列长度为 8。如果方案允许连续拼接再切片，就要明确分隔符是否计数、第二篇能否被拆开、剩余片段如何处理。不能一边宣称“文档完整保留”，一边静默截断溢出部分。

## 4. 为什么这么做：可复现与成本的取舍

| 选择 | 收益 | 代价 / 边界 |
|---|---|---|
| 保留合规的分层中间产物 | 规则升级不必重新获取全部来源 | 存储与访问治理成本，保留期限仍有效 |
| 仅存最终 token | 存储结构简单 | 难以追查清洗错误、换 tokenizer 或执行删除 |
| 在训练时动态混合 | 容易改变采样策略 | 必须记录实际消费量和恢复后的采样状态 |
| 离线固定混合版本 | 易审计与复现 | 改配方通常要重建或重新引用分片 |

本专题不要求把所有中间层永久落盘；先识别昂贵步骤、审计需求和删除约束，再决定保留范围。

## 5. 可选练习：交付一个可解释的数据版本

用自拟的网页正文、代码、对话各两条，手工画出管线并填写契约。另加一条解析失败记录和一条使用权限未知记录。

通过条件：

- 每个输出能追到父记录和处理版本。
- 解析失败显式隔离，权限未知不进入可训练集合。
- 训练、开发、测试之间没有同组派生记录。
- 能分别解释原始记录数、保留记录数、可训练 token 数。
- 给定某个 `source_id`，能列出受影响的派生数据和发布版本。
