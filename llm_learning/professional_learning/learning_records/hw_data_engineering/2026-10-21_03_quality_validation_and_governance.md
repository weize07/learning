# 3. 数据质量验证与安全治理

> 2026-10-21 补充；待阅读。这里只提供工程框架，不替代法务或组织合规审批。
> [专题入口](README.md) · 前一章：[去重](2026-10-21_02_distributed_processing_and_dedup.md) · 下一章：[配比与多语言](2026-10-21_04_data_mixture_and_multilingual_balance.md)

## 1. 是什么：三类证据必须分开

| 层次 | 回答的问题 | 不能推出什么 |
|---|---|---|
| 数据检查 | 能解析、标签有依据、无已知重复 / 敏感信息问题吗？ | 通过检查不等于内容绝对正确 |
| 模型效用验证 | 同预算下，目标能力改善且其他能力不退化吗？ | 数据分数高不保证模型更好 |
| 使用治理 | 获取、训练、保存、分享与删除是否符合适用要求？ | 模型效果好不能豁免使用限制 |

质量不是一个可以掩盖所有问题的总分。明确禁用的来源、敏感泄露和测试集污染，应进入硬门禁；可读性、信息密度、难度则可用于排序、抽样或复核。

## 2. 为什么要做：质检器本身也会犯错

格式检查能确认 JSON 合法，却不能确认答案正确。毒性分类器可能误判讨论敏感议题的正常文本；语言识别器可能排斥混合语言；以流畅度筛选可能误删代码和数学。

因此要分别审查通过集与拒绝集，并按语言、领域、来源、长度和难度分层。只看整体保留率，无法发现少数群体被系统性过滤。

## 3. 怎么做：建立规则、抽样和发布门禁

### 3.1 最小质量卡

| 维度 | 可检查内容 | 处置 |
|---|---|---|
| 完整性 | 缺失字段、截断、解码错误、引用失效 | 隔离，修复后重新检查 |
| 内容保真 | 标题 / 表格关系、OCR 顺序、代码缩进 | 分来源抽查，不仅检查字符数 |
| 正确性 | 答案依据、计算结果、工具执行结果 | 结合规则、执行与人工证据 |
| 多样性 | 来源、语言、主题、难度和模板分布 | 比较过滤前后分布与覆盖 |
| 重复 / 泄漏 | 重复簇、派生关系、评测重叠 | 去重、分组隔离、污染事件处理 |
| 隐私 / 使用限制 | 个人信息、凭据、授权、使用范围 | 硬门禁、限制访问或人工复核 |

每条规则记录版本、适用范围、输入、分数 / 结论和原因码；无法判断的记录进入 `quarantine`，不能作为默认通过。解析失败与低质量拒绝也应分开，否则会误读产能瓶颈。

### 3.2 指标必须有分母

设某阶段输入为 $N$ 条，通过 $A$ 条、拒绝 $R$ 条、隔离 $Q$ 条，应能核对：

$$
N=A+R+Q
$$

这要求状态互斥且覆盖所有输入。若一条记录命中多个规则，可以保留所有原因，但按规则汇总时不能把多次命中相加当作总删除量。

- 记录保留率：通过记录数 / 输入记录数。
- Token 保留率：同一 tokenizer 口径下，通过 token / 输入 token。
- 通过集缺陷率：抽查通过样本中的缺陷数 / 抽查通过样本数。
- 拒绝集误删率：抽查拒绝样本中本应保留的数量 / 抽查拒绝样本数。
- 来源可追溯率：具有完整所需血缘的发布记录数 / 发布记录数。

若按层等量抽查，但真实层大小不同，总体缺陷率需按目标权重还原：

$$
\hat p=\sum_k w_k\hat p_k
$$

这里的 $w_k$ 是目标总体中第 $k$ 层的占比，不是抽样条数占比，也不是训练配比。

“抽查 100 条未见缺陷”不代表缺陷率为零。独立、代表性伯努利样本零缺陷时，95% 单侧上界可粗略用 $3/n$ 估计；模板相关、分层或有偏抽样不能直接套用。稀有高风险问题还需要专项用例。

### 3.3 治理贯穿数据生命周期

| 时点 | 必须明确的决策 |
|---|---|
| 获取前 | 来源许可 / 合同、采集方式、训练用途、地域和转授权限制 |
| 处理时 | 个人信息与秘密识别、最小访问权限、敏感原文是否允许保留 |
| 合成时 | 原资料能否发送给教师服务，输出能否用于目标训练 / 蒸馏 |
| 发布时 | 数据用途、访问人群、保留期限、来源声明、残余风险 |
| 删除 / 撤回时 | 原文、缓存、索引、派生样本、数据版本和训练产物的影响范围 |

`robots.txt`、网页可访问和数据集卡片中的一个许可字段，都不能独立回答所有使用问题。具体义务取决于来源、合同、适用法律和组织政策；不确定时走审批，不以脱敏替代授权。

去标识化要保持同一实体的引用一致，同时避免映射表泄漏。简单哈希姓名 / 邮箱不保证匿名；映射表和原文应按敏感资产管理。

数据删除不等于已训练模型忘记内容。血缘应帮助定位受影响 checkpoint；是否撤回、重训或采取其他处置，由风险评估决定，不能承诺删库即完成遗忘。

### 3.4 发布与协作

数据工程负责处理与版本；算法团队负责训练可消费性和效果；领域标注人员负责语义标准；合规 / 隐私负责人确认使用边界。一个负责人协调放行，不意味着所有风险由数据团队自行批准。

发布记录至少附：检查结果、未解决问题、适用范围、批准依据、消费方、回退版本。失败要能定位到来源和处理阶段，而不只是“数据不好”。

## 4. 为什么这么做：硬约束与软评分分开

把所有维度加权求和，可能使“高信息密度”抵消“来源禁用”。正确方式是先满足不可交易的约束，再在合格候选中优化质量、覆盖与成本。

但软指标也不应全部变为严格删除规则。低置信度或困难样本可以进入复核、修复和定向采集，避免训练集最终只剩容易判断的内容。

## 5. 可选练习：审查一条规则升级

假设新规则提高整体保留质量，却使某语言保留量大幅减少。写一份放行决策，至少包含：

- 过滤前后各语言 / 领域的记录与 token 数。
- 通过集和拒绝集的独立人工抽查。
- 旧规则与新规则的同预算模型对照设计。
- 哪些条件阻止发布，哪些不确定性需要补证据。
- 一条来源撤回时，如何查找派生记录和受影响版本。

没有实际抽样或训练结果时，保留“待验证”，不能先写成新规则有效。
