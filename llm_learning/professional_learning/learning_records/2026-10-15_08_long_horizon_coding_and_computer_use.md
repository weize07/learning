本篇不依赖任何具体项目。先用一个代码任务讲清完整轨迹，再比较界面操作；项目全貌与源码在下一阶段集中学习。

## 1. “长程”不是输出很长，而是行动之间存在持续依赖

用户要求：

> 给现有销售汇总程序增加退款处理，输出各地区净销售额。保留原有不传退款数据的用法，增加测试；不要发布或提交代码。

一次文本生成可以给出建议，但真实完成需要：

```text
理解需求 → 找实现与调用 → 检查现有测试和数据规则
     → 修改代码 → 运行测试 → 根据结果修复 → 核对并交付
```

后一步依赖前一步得到的信息和环境变化。第一次读代码前，未必知道改哪里；运行测试前，也未必知道错误是什么。

没有统一规定“超过多少步才算 long-horizon”。任务跨度可能来自多次工具调用、状态变化、长时间等待、跨系统依赖或复杂验证，不只来自 token 数。

## 2. 先定义“完成”，不要先写实现

对上述教学任务，先确认以下条件：

| 验收项 | 需要什么证据 |
|---|---|
| 原有调用兼容 | 不传退款数据时，原行为与相关回归测试保持 |
| 新的净额正确 | 根据明确口径计算，并用独立预期值核对 |
| 边界行为明确 | 无退款、部分退款、重复退款、未知订单等按规范处理 |
| 变更范围受控 | 没有无关改动，没有发布、提交或外部写入 |
| 结果可复现 | 记录运行命令、环境、测试结果与剩余限制 |

这里还缺金额单位、退款关联键、时间归属与异常规则。先查看现有项目约定；仍无法确定时澄清，不让 Agent 自由发明财务政策。

验收可以包括自动测试、静态检查与人工复核。用户可见的完成说明不能超出实际验证范围。

## 3. 一次完整的代码任务轨迹

### 3.1 定位与理解

先在授权仓库里搜索汇总入口，读取实现、调用方和相关测试，而不是把所有文件都放进模型。

记录：

- 实际入口和数据结构。
- 已存在的兼容要求。
- 哪些规则已证实，哪些仍是假设。
- 允许修改的范围与测试命令。

读取注释提供线索，但不证明代码实际按注释运行。能通过调用、测试或运行观察确认的，逐项确认。

### 3.2 建立基线

运行与任务相关的现有检查，明确运行前已有失败和环境问题：

- 测试通过：可作为后续比较的起点。
- 测试失败：先区分已有问题、缺依赖、执行方式错误与业务失败。
- 无法运行：如实记录，不把“没测”写成“通过”。

代码、测试与文档内容也可能不可信。执行命令前仍需检查范围与权限，不因为命令出现在仓库里就自动运行。

### 3.3 做可验证的小步修改

为新行为补测试并修改实现，尽量让每一步都有清楚假设与检查。

例如教学数据：订单销售额 100 元，唯一有效退款 20 元，预期净额 80 元。这个预期应来自任务规则与独立计算，而不是直接读取待测函数输出作为标准答案。

测试也可能写错。Agent 同时修改实现与测试，不能仅以“自己的新测试绿了”证明正确。

### 3.4 看失败，决定下一步

```text
测试失败
   ├→ 环境 / 依赖问题：修正执行条件或明确阻塞
   ├→ 测试预期错误：核对独立规范后修测试，保留理由
   ├→ 实现错误：定位并修实现
   └→ 需求不明：请求澄清，不反复试到偶然通过
```

不要通过删除失败测试、弱化断言、硬编码样例或吞掉异常来制造“成功”。

### 3.5 验证与交付

先运行覆盖变化的相关测试，再按风险扩展到调用方、回归和类型 / 静态检查。不是每次都无条件跑全项目，也不是永远只跑新增样例。

交付说明包含做了什么、实际检查了什么、哪些检查没运行或仍失败，以及产物位置。生成补丁不等于测试通过，测试通过也不等于已经发布。

## 4. 为什么多步任务容易累积错误？

每一步可能引入错误假设，后续动作再基于它展开：

```text
误认金额单位 → 写出错误换算 → 测试也沿用同一错误预期
             → 全绿但业务数值错误
```

因此不只需要更多思考，还需要外部反馈和独立验证。

一个理想化例子：若完成任务需要连续 20 个步骤全成功，并假设每步独立且成功率恒为 95%，则总成功率为：

$$
0.95^{20}\approx35.85\%
$$

这不是对实际 Agent 的预测。真实步骤相关，难度不同，有的错误可恢复，有的步骤非必要。例子只说明“单步看起来可靠”不自动变成长任务可靠。

可验证里程碑、早期发现错误、受限修复和状态保存，是降低错误传播风险的方法，不是保证成功。

## 5. Computer-use：同样的循环，不同的观察与动作

界面操作 Agent 可能用截图、页面结构或可访问性信息观察，用点击、键盘、滚动等行动。Coding Agent 也可能操作 UI，两类不是完全互斥。

| | 代码 / API 工具 | 界面操作 |
|---|---|---|
| 定位 | 函数、文件、结构化对象 ID | 元素、文本、界面状态，必要时坐标 |
| 执行 | 调用命令或接口 | 点击、输入、上传、拖动等 |
| 常见变化 | 文件版本、进程、服务状态 | 弹窗、加载、页面重排、焦点与登录状态 |
| 验证 | 测试结果、返回对象、文件内容 | 页面确认、下载产物、后端可查状态 |

例子：在表格软件里筛选季度、生成图表并导出报告：

```text
观察当前文件和窗口
 → 找到目标工作表
 → 设置并核对筛选
 → 生成图表
 → 导出到允许位置
 → 打开或读取导出结果检查
```

点击“导出”按钮，不等于文件已生成。需要等待、检查完成状态与实际产物；页面显示的名称也不证明内容正确。

## 6. 界面操作特别要注意哪些问题？

### 6.1 观察会过期

截图后页面可能加载、移动或出现弹窗。之前的坐标可能指向另一个按钮。

关键动作前更新观察、核对目标；可用稳定元素信息时优先考虑，但元素标识也不保证永远有效。

### 6.2 点击失败后能不能重试？

只读导航可能可受限重试；提交、发送、支付等动作出现超时时，结果可能已经生效。先查实际状态，不盲目再点一次。

这与 [外部操作恢复](2026-10-15_04_state_persistence_and_recovery.md)相同：未收到成功反馈，不代表没执行。

### 6.3 屏幕上的文字也可能是不可信输入

网页、文档、弹窗可能诱导 Agent 泄露资料或越界操作。它们是环境观察，不是应用权限的来源。

真实账号、凭据和生产文件不能作为初次练习环境。使用假数据、可丢弃文件或受控模拟服务，操作仍遵守任务授权。

## 7. 长程任务要记住什么，又不必保留什么？

需要延续：

- 目标、禁止事项、验收条件与确认过的规则。
- 当前计划、已验证结果、未知项与失败原因。
- 文件版本、有效产物和执行结果。
- 未确认的外部动作、等待状态和累计预算。

不必每轮塞入全部日志或全部文件。工具结果可以落盘、统计和有界回查；但不能在压缩时把“推测”写成“已验证”。

暂停再恢复时，先重新确认外部状态与结果有效性，不要求恢复模型隐藏的每一步思考。

## 8. 评测：看最终结果，也看过程风险

### 8.1 结果

代码任务可检查功能测试、兼容性、代码质量与变更范围；界面任务可检查最终业务状态、文件内容与格式。

独立验收测试与隐藏测试可以提高可信度，但它们也可能覆盖不足或有错误，不能当作绝对证明。调试时不将隐藏答案直接提供给 Agent 再声称独立通过。

### 8.2 过程

检查越权、未获批准的写入、无进展循环、重复副作用、取消处理和错误报告。偶然完成目标但过程违规，不应不加说明计为可靠成功。

### 8.3 成本

报告总模型调用、工具次数、任务耗时、token、预算与恢复次数。不同 Agent 若用不同工具、网络权限或多次尝试，不能把成绩差异全归因于模型。

模拟工具可稳定测试控制流，真实执行可暴露文件、服务和界面的复杂性，两者互补。

## 9. 什么时候不需要这么复杂？

- 规则清晰的固定批处理，优先程序或 workflow。
- 提供建议但不要求实际执行，可能一次模型调用就足够。
- 有可靠 API 的操作，可优先使用可验证接口，不必为了“像人”而改用 GUI。
- 需要严格规则的高风险流程，让 Agent 承担获准子任务，不放开完整自主行动。

更多步骤、多 Agent、更长思考不是天然更优。先定义需求与基线，再决定自主性范围。

## 10. A＋B 概念之后：怎样进入项目阅读？

A＋B 的概念教材已提供，不代表实现、故障测试或全面掌握已完成。

接下来的项目课先专门看 DeepSeek Harness，不从某个插件的局部代码开始：

```text
项目解决什么问题，整体由哪些部分组成？
              ↓
怎样运行，模型和工具在哪里接入？
              ↓
核心术语、目录、一次完整任务生命周期
              ↓
追一条模型 → 工具 → 结果 → 下一轮的调用链
              ↓
再对应规划、上下文、记忆与恢复
```

其他开源项目按既定计划作为后续精读 / 对照候选，不同时引入五套项目术语。实际克隆、运行和模型调用需明确环境、范围与预算；当前不自动执行。
