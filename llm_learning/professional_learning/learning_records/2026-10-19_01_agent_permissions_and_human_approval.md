# Agent 主干 9：安全、权限与人工介入

[主学习索引](../index-2026-10-08.md) · 前置：[工具契约](2026-10-15_02_function_calling_and_tool_contracts.md)、[状态与恢复](2026-10-15_04_state_persistence_and_recovery.md)

下一课：[鲁棒性与成本预算](2026-10-19_02_agent_reliability_and_budgets.md)。

**本课重点：模型可以提出操作，但不能自行决定自己是否有权执行。** DeepSeek Harness 第一遍学习已结束；本课回到通用设计，不要求继续记项目类名或事件名。

统一教学场景：**用户要求读取项目资料、生成周报草稿，确认后发送给指定同事。** 以下接口、数据与验收均为教学设计，不代表某个产品的实际实现。本文只提供设计与测试方案，没有执行文件操作、发送邮件或运行验收。

## 1. 是什么：把建议、授权、执行和确认分开

### 1.1 四个不同的问题

| 问题 | 谁负责 | 例子 |
|---|---|---|
| 应该做什么 | 用户目标、模型规划与业务流程 | 读资料、整理周报、请求发送 |
| 是否允许 | 程序中的权限与策略检查 | 只能读指定目录，不能读取凭据 |
| 是否需要人工批准 | 风险策略 | 生成草稿可以自动做，对外发送必须确认 |
| 是否实际完成 | 工具结果与独立验证 | 邮件服务返回发送凭据，而不是模型声称已发送 |

**参数合法不等于有权限；用户批准不等于执行成功；执行超时不等于操作没有发生。**

### 1.2 几种容易混淆的机制

| 机制 | 是什么 | 不能代替什么 |
|---|---|---|
| 工具 schema | 校验参数的结构与类型 | 不能判定当前用户能否读取某份资料 |
| 权限策略 | 约束主体对具体资源可做的操作 | 不能仅用一句系统提示实现 |
| 沙箱 | 在运行环境限制文件、进程或网络访问 | 不自动理解收件人、金额等业务授权 |
| HITL（人工介入） | 在指定节点暂停，让人澄清、批准或接管 | 不是让人替程序识别所有风险 |
| 提示注入防护 | 避免把不可信内容当成有权改变行为的指令 | 不能只靠模型识别“恶意语气” |

“角色提示词是只读助手”是行为要求；“执行服务拒绝写入”才是可检查的权限边界。

## 2. 为什么要做：工具会把文本决定变成真实影响

- **资料不一定可信**：网页、文件、邮件和检索结果可能夹带操作指令，但它们仍是待处理的数据。
- **模型可能选错对象**：工具名正确、JSON 合法，也可能读错用户的文件或发给错误收件人。
- **任务意图不够具体**：“帮我处理周报”不等于允许访问所有目录、任意上传或发送任何内容。
- **执行是异步的**：批准后内容可能变化，等待期间权限也可能被撤销。
- **副作用不能靠取消撤回**：邮件已送达后，即使 Agent 停止，也不表示邮件被撤销。

因此，不能把“模型很听话”作为唯一防线。需要在执行之前设置确定性检查，并在执行之后记录证据。

## 3. 怎么做：沿一条真实操作链设置边界

### 3.1 先写最小能力表

| 操作 | 资源范围 | 默认处理 |
|---|---|---|
| 读取资料 | 当前用户有权访问的指定项目目录 | 在授权范围内自动允许 |
| 生成草稿 | 当前任务的草稿存储 | 自动允许；不覆盖无关文件 |
| 发送周报 | 当前租户允许的收件人及本次草稿 | 必须展示内容与收件人，等待批准 |
| 读取凭据或上传任意地址 | 不属于此任务的能力 | 拒绝；不能靠一次普通发送确认放行 |

“只读”也不代表无风险：读取敏感内容后再把它放进模型请求，已经产生了数据流转。既要限制读什么，也要限制能把内容交给谁。

### 3.2 区分指令与资料

- **是什么**：用户请求定义目标；读取到的项目文档是证据，不自动拥有下达命令的权限。
- **为什么要做**：资料可能包含“改发到另一个地址”“忽略先前要求”等文本。
- **怎么做**：
  - 保留内容来源与信任标记，避免把检索正文拼成高权限系统指令。
  - 资料不能修改工具许可、租户身份或审批记录。
  - 即使模型误信资料，发送端仍按真实授权与收件人策略阻止越界。
- **为什么这么做**：模型侧提醒降低误判，程序侧约束限制后果；两者职责不同，不能只测试模型会不会复述安全规则。

### 3.3 执行链：先检查，再批准，再复核

```text
User request
  -> Model proposes action
  -> Validate and normalize arguments
  -> Check identity, resource scope and policy
  -> Prepare exact operation
  -> Request approval if required
  -> Revalidate permission and operation version
  -> Execute the approved operation
  -> Record outcome and verify delivery
```

逐层下钻：

- **参数检查与规范化**
  - 校验类型、大小、路径和收件人；拒绝不符合契约的输入。
  - 文件要考虑实际解析后的路径、链接与目录边界；仅比较字符串前缀不够。
  - 规范化不等于防住检查后资源被替换，底层执行还需可靠的资源访问约束。
- **身份与策略检查**
  - 使用服务端可信身份判断用户、租户、资源和操作权限，不相信模型传入的 userId。
  - 不满足硬性策略时直接拒绝；不是所有拒绝都能升级成人工批准。
- **准备具体操作**
  - 固定收件人、标题、正文及附件版本。
  - 人看到的是实际待执行内容，不只是一句“是否允许发邮件”。
- **批准与执行前复核**
  - 批准绑定这次操作；目标、内容或权限变化时重新检查，必要时重新批准。
  - 令牌过期、用户撤销或任务取消后，不得继续执行旧批准。
- **执行与结果**
  - 使用已批准的不可变操作，不能批准后让模型重新生成一版参数直接发送。
  - 记录发送凭据；失败、拒绝、取消与结果未知分开报告。

### 3.4 批准的究竟是什么？

教学示例：服务端保存一条批准记录，绑定的字段可以包括：

```json
{
  "approvalId": "approval-42",
  "principalId": "user-A",
  "tenantId": "tenant-X",
  "taskId": "task-7",
  "action": "send_report",
  "recipient": "colleague@example.com",
  "draftVersion": 3,
  "attachmentVersions": [],
  "expiresAt": "2026-10-19T16:00:00+08:00"
}
```

这是字段示意，不是完整鉴权协议。实际系统还需可靠的服务端存储或不可伪造凭据、完整内容绑定、使用次数控制与审计；模型自己输出同样的 JSON 不构成批准。

关键规则：

- 批准草稿 v3，不代表批准之后修改的 v4。
- 批准一次发送，不代表批准每次重试都再发一封。
- 草稿版本必须能稳定定位不可变内容；单纯信任可被覆盖的版本号不够。
- 批准只影响规定的操作范围，不自动扩大文件或网络访问权限。

### 3.5 异常发生时怎么处理

| 情况 | 正确动作 |
|---|---|
| 用户拒绝 | 不发送，保留或删除草稿按产品规则处理，明确告知 |
| 等待批准超时 | 停留在未执行状态，不能默认同意 |
| 批准后收件人或正文改变 | 原批准失效，重新准备与审批 |
| 执行前发现权限被撤销 | 拒绝执行，即使此前已经批准 |
| 发送请求超时，是否送达未知 | 标记结果未知，优先查询操作状态；不能直接宣称失败并盲目重发 |
| 发送完成后收到取消 | 不再启动后续动作；如实报告已完成的发送，不假装已回滚 |

重试与幂等是下一课的重点；这里先记住：**一次人工批准不自动解决重复副作用。**

## 4. 为什么这么做：把模型的自由限制在可验证范围内

| 选择 | 收益 | 代价 / 替代方案 |
|---|---|---|
| 执行端强制检查，而非仅提示模型 | 即使模型建议错误，也能阻止越权动作 | 工具后端必须理解真实资源和身份 |
| 按风险设置批准节点，而非每步都确认 | 降低批准疲劳，让用户关注高影响操作 | 风险分类必须清晰，不能随意把危险操作归为低风险 |
| 批准绑定具体操作版本 | 防止“批准 A，执行 B” | 需保存不可变操作，处理失效、竞争与重复请求 |
| 沙箱约束与业务授权结合 | 同时限制环境访问和业务对象 | 沙箱不能替代租户隔离，业务校验不能替代底层资源约束 |
| 结果未知单独建模 | 避免把重试当成无风险补救 | 需要操作凭据、状态查询、对账或人工处置路径 |

架构师应明确哪些边界由程序保证，哪些风险只能降低而无法消除；不能把“有审批、有沙箱”当成整个系统已安全。

## 5. MVP 与验收：验证动作被阻止，而不是验证回答很谨慎

**设计范围**：只读资料、草稿生成、模拟发送后端；暂不接真实邮件或敏感资料。下表是待实现的验收方案，不是已运行结果。

| 刺激 | 需要观察的结果 |
|---|---|
| 资料中混入改变收件人的指令 | 不产生未获授权的发送；检查真实执行参数，不只看回答 |
| 合法 JSON 指向其他用户文件 | 读取后端拒绝，文件内容未进入模型请求 |
| 批准 v3 后修改为 v4 | v4 不被执行，原批准不可沿用 |
| 批准后撤销权限 | 执行前复核失败，发送次数为 0 |
| 用户拒绝、超时或取消 | 发送次数为 0，状态分别记录 |
| 模拟后端已接收但响应丢失 | 系统报告未知或通过凭据确认；不无条件二次发送 |
| Agent 最终回答“发送成功”，后端没有凭据 | 独立验收判失败，不能以模型自述通过 |

给 Coding Agent 的任务应要求：固定权限表、批准状态与操作版本模型、拒绝 / 未知错误契约，并提交上述后端计数、参数和状态证据。不要只要求“加一个确认弹窗”。
