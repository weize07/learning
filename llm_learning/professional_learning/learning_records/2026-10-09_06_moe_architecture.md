# MoE：一个 token 怎样选择专家并完成计算

- 课程位置：LLM 基础，接在 [SwiGLU](2026-10-09_05_swiglu.md)之后、微调之前。
- 实际补写及重写：2026-10-19。旧日期前缀用于课程排序，不表示 10 月 9 日已经学习。
- [主索引](../index-2026-10-08.md) · [每日概览](topics_by_date.md)。
- 本文用一个“4 个专家、每次选 2 个”的例子走完计算，再解释训练和成本；不展开多卡部署。

## 1. 先定位：MoE 到底改了 Transformer 的哪一块？

先回忆一个 Transformer block 中的两项主要计算：

- **Attention**：当前位置从其他允许读取的位置汇总信息。
- **FFN**：对当前位置的隐藏向量做非线性加工，输入和输出宽度相同。

普通 dense FFN 是“这一层只有一套 FFN 参数，每个 token 都用这套参数”。

**本课讨论的稀疏 MoE（Mixture of Experts）把这个位置改成“多套 FFN + 一个选择器”。每个 token 只选少数 FFN 计算，然后合并结果。**

简化结构如下，暂不画 Norm 和残差：

```text
Dense block:
  Attention -> One FFN -> Next block

MoE block:
  Attention -> Router + Selected expert FFNs -> Next block
```

这里一个 **expert（专家）就是一个 FFN**，有自己的一套权重。不是一整个 LLM，也不分别生成一段文字让主模型汇总。

如果专家内部使用 SwiGLU，那么每个专家各有自己的 up、gate、down 投影矩阵：

| 机制 | 决定什么 |
|---|---|
| SwiGLU | 一个 FFN 内部怎样计算、怎样调节中间特征 |
| MoE router | 当前 token 交给哪几个 FFN |

**MoE 不替代 SwiGLU，而是可以让多个 SwiGLU FFN 成为专家。** 也不要求模型每层都采用 MoE；不同层通常有各自的 router 和专家参数。

## 2. 跟着一个 token 走：打分 → 选择 → 专家计算 → 合并

### 2.1 进入 MoE 的不是文字，而是向量

一句话经过分词、embedding 和前面层的计算后，每个 token 都有自己的隐藏向量。我们只跟踪其中一个位置。

假设它进入当前 MoE 子层的向量为 **x = [1, 2]**。这里用二维方便展示，真实模型的隐藏宽度通常大得多；这个向量也不是 token ID，它已经可以包含上下文信息。

本层有 4 个专家，采用 **top-2**：对每个 token，选分数最高的两个路由专家。

| 环节 | 输入 | 输出 |
|---|---|---|
| Router | 当前 token 的向量 x | 4 个专家的分数 |
| 选择 | 4 个分数 | 两个专家编号及合并权重 |
| 专家计算 | 被选中的两个专家各自接收完整的 x | 两个二维结果 |
| 合并 | 两个结果及其权重 | 一个二维向量 y |

下面的分数和专家输出是自拟算例，不是模型运行记录；不展开 router 和专家内部每一项矩阵乘法。

### 2.2 Router 怎么知道选谁？它本身也是可训练的计算

一种简单 router 先做线性投影，再做 softmax：

$$
s=xW_r,\qquad p=\operatorname{softmax}(s)
$$

读法：用 router 的权重矩阵，把当前隐藏向量变成“每个专家一个分数”，然后转成归一化权重。**它不是先用自然语言思考“这是数学题，所以找数学专家”。**

本例中 x 有 2 个特征、共有 4 个专家，因此 router 权重形状为 `[2, 4]`，输出有 4 个数。假设结果为：

| 专家 | Router 输出 | 是否选中 |
|---|---|---|
| 专家 1 | 0.50 | 是 |
| 专家 2 | 0.30 | 是 |
| 专家 3 | 0.15 | 否 |
| 专家 4 | 0.05 | 否 |

**这些数是专家的路由权重，不是下一个词的预测概率。** 预测下一个 token 的词表概率是在模型后面的输出头处计算的。

本例选择专家 1、2，并将选中权重重新归一化：

- 专家 1：0.50 ÷ (0.50 + 0.30) = **0.625**。
- 专家 2：0.30 ÷ (0.50 + 0.30) = **0.375**。

这样两个合并权重之和为 1。这是本例采用的规则；不同 MoE 的打分函数、选择约束和归一化方法可以不同，不要把本例当成 DeepSeek-V3 的完整实现。

### 2.3 选中的专家怎样算？都拿到同一个完整输入

Harness、用户或另一个 Agent 都不参与这一步；模型执行代码根据 router 的结果分发向量。

```text
                         -> Expert 1 -> [2, 0]
Input x = [1, 2] -------+
                         -> Expert 2 -> [0, 4]

Expert 3, Expert 4: not run for this token
```

假设专家 1 对 x 的输出是 `[2, 0]`，专家 2 的输出是 `[0, 4]`。两者不同，是因为它们有不同的权重。

三个关键点：

1. **不是把 x 切成两半**：两个专家都处理 `[1, 2]`。
2. **不是先过专家 1 再过专家 2**：这两个计算分支彼此独立，可以并行；实际调度由实现决定。
3. **未选专家不对这个 token 做 FFN 计算**：但同批其他 token 可能选中它们。

专家内部仍是之前学过的 FFN：投影、非线性、再投影回原来的隐藏宽度。输出是隐藏向量，不是两份文字答案。

### 2.4 怎样合并？按权重相加，不是拼接

将两个输出分别乘上 0.625 和 0.375，再逐坐标相加：

| 坐标 | 计算 | 结果 |
|---|---|---|
| 第 1 维 | 0.625 × 2 + 0.375 × 0 | 1.25 |
| 第 2 维 | 0.625 × 0 + 0.375 × 4 | 1.50 |

因此 **y = [1.25, 1.50]**。虽然用了两个专家，输出仍为二维，不会拼成四维。

算例对应的公式只有一件事：

$$
y=0.625\,E_1(x)+0.375\,E_2(x)
$$

其中 E₁、E₂ 就是两个专家 FFN。外围的 Norm / 残差结构照常处理；在常见 pre-norm block 中，MoE 接收归一化后的向量，其输出还要与该子层的残差分支相加。**y 只是 MoE 的结果，不是整个 block 的最终结果。**

### 2.5 下一个 token、下一层，还用这两个专家吗？

不一定，路由通常是**逐 token、逐层**进行的：

- 同层的另一个 token 有不同隐藏向量，可能选专家 2、4。
- 同一个 token 到下一层时，向量已经变化，而且下一层有自己的 router 和专家。
- 同一个词出现在不同上下文中，也不保证选中相同专家。

所以 MoE 不是“为整个请求选定两个专家，然后从头到尾只用它们”，而是**模型内部各 MoE 层根据当前向量选择计算分支**。

## 3. 为什么要这样做？把参数容量与每 token 的计算分开

### 3.1 增加更多参数，但不让每个 token 都用完

仍沿用“4 选 2”结构，这次把规模放大。假设每个专家有 **1 亿参数**；这不是上面二维玩具网络的实际参数量。

先只比较 FFN 部分，暂不计 router、Attention、embedding 等：

| 方案 | 拥有的 FFN 参数 | 每 token 使用的 FFN 参数 |
|---|---|---|
| 一个较小 dense FFN | 1 亿 | 1 亿 |
| 一个较大 dense FFN | 4 亿 | 4 亿 |
| 4 个专家，每次选 2 个 | 4 亿 | 2 亿 |

**收益是：拥有 4 亿专家参数供不同输入使用，但一个 token 不需要计算全部 4 亿参数。**

比较时必须说清基线：

- 相对较大的 dense FFN：MoE 可以减少每 token 的主要 FFN 计算。
- 相对较小的 dense FFN：本例反而计算了两个专家，并不更省。
- 参数量相同不保证质量相同；是否更好还取决于训练、数据与路由。

这就是“容量与计算解耦”的具体含义，不是“换成 MoE 就同时更准、更快、更便宜”。

### 3.2 为什么激活参数少，权重存储却没有同比减少？

因为没选中的专家只是**这次不算**，不是从模型中消失了。下一批 token 可能马上需要它们。

沿用上例，假设每个权重占 2 字节：

- 全部专家权重：4 亿 × 2 字节 = **8 亿字节，约 800 MB**（十进制）。
- 当前 token 只选 2 亿参数，不代表整个专家集合只需存 400 MB。
- 这还只是专家权重，不包括 Attention、KV Cache、临时张量；训练时还有梯度、优化器状态等。

权重可以分布到多块 GPU，或采用 offload 等方案，并非必须全部驻留在同一块 GPU；但存储和搬运的成本并不会因为“未激活”就消失。

### 3.3 为什么少算了，也不一定按比例变快？

还多了几项工作：

| 开销 | 实际发生什么 |
|---|---|
| 路由与分发 | 计算分数，把 token 按选中专家分组 |
| 通信 | 专家在不同设备时，需要发送输入、收回输出 |
| 负载不均 | 某些专家分到很多 token，其他设备等它们 |
| 合并与调度 | 将各专家结果还原到对应 token，再加权合并 |

因此“4 选 2”既不等于整个模型 FLOPs 减半，也不等于延迟减半。**激活参数、实际计算量、显存、延迟是四个不同指标。**

## 4. Router 和专家从哪里学会这些分工？

### 4.1 通常不是先给专家命名，再分别教专业知识

典型 MoE 中，router 和专家都是模型的一部分，通常联合训练。人先决定专家数量、大小和 top-k 等结构，但不必指定“专家 1 学数学、专家 2 学写作”。

以预测下一个 token 的训练为例：

1. 输入经过模型，在各 MoE 层完成上述路由与专家计算。
2. 模型输出词表预测，与训练目标计算损失。
3. 反向传播沿参与计算的路径传递梯度，学习专家权重和 router 中可学习的部分。
4. 大量样本重复这一过程，不同专家逐渐接触到不同的输入分布，可能形成不同偏好。

硬 top-k 的“选谁”不是普通平滑运算，不能直接当作 softmax 一样求导；router 如何获得梯度，依赖所选输出权重等可微路径与具体训练设计。

专家 3 没处理当前 token，不代表整个 batch 都不更新它：其他 token 可能选了它。“专家”也不保证最终对应一个清晰的人类学科。

### 4.2 为什么还要负载平衡？

假设 100 个 token 几乎都选专家 1、2：

- 专家 1、2 很忙，专家 3、4 利用不足。
- 多设备执行时，负载不均可能使总体速度受最忙的设备限制。
- 长期如此，增加专家带来的容量也没有得到充分利用。

所以训练 / 路由设计还要关注分配是否过度集中。常见办法包括辅助平衡损失、动态调整路由偏置等；具体模型采用的方式不同。

**不是要求每个 token 平均使用所有专家**，而是希望一批或一段时间的输入不要持续挤在少数专家上，同时尽量保留有利于任务质量的选择。

## 5. 回到真实模型：应该怎样理解参数宣传？

DeepSeek-V3 官方模型卡给出的主模型口径是：

| 数字 | 含义 |
|---|---|
| 671B 总参数 | 主模型拥有的总参数规模，B 为十亿 |
| 每 token 激活 37B | 按其架构口径，一个 token 前向计算涉及的参数规模 |

它表达的是“有很多参数，但每个 token 只使用其中一部分”，不是以下结论：

- 只要按 37B 权重估算就能装下整个模型。
- 它与一个 37B dense 模型是同一架构或同等效果。
- 它一定比 671B dense 模型快 671/37 倍。

真实应用仍需测任务质量、首 token 延迟、输出速度、并发吞吐与成本，不能用一个激活参数数字代替这些结果。

**整条主线：一个隐藏向量进入 MoE → router 打分选专家 → 所选专家分别计算 → 输出加权合并 → 继续经过后面的层。它始终是一次模型计算内部的流程。**

<summary>补充：形状、共享专家，以及与其他概念的区别</summary>

### 推广到一个 batch 的形状

设 B 为 batch 大小、T 为序列长度、d 为隐藏宽度、E 为路由专家数。以下为逐 token 路由的逻辑形状，实际实现可展平或打包：

| 对象 | 形状 |
|---|---|
| MoE 输入 | `[B, T, d]` |
| Router 权重 | `[d, E]` |
| 各 token 的专家分数 | `[B, T, E]` |
| 每个选中专家对单个 token 的输出 | `[d]` |
| 合并后的 MoE 输出 | `[B, T, d]` |

专家内部可以扩维，但输出必须回到所需隐藏宽度。一个 batch 的不同 token 合起来可能使用所有专家；“稀疏”说的是单个 token 的计算路径，不是每次 batch 只能使用 k 个专家。

### Shared expert 是什么？

某些 MoE 另外设置所有 token 都经过的共享专家分支，再与路由专家的结果合并。它为公共模式提供计算容量，但也消耗每 token 的计算；不是所有 MoE 都必须有。

有共享专家时，“top-2”可能只描述选了两个**路由专家**，不意味着总共只计算两个 FFN。本章算例特意不含共享专家。

### 不要混为一谈

| 名词 | 所在位置与作用 |
|---|---|
| SwiGLU 的 gate | FFN 内部，调节中间特征 |
| MoE 的 router / gate | 选择参与计算的专家 FFN |
| MLA | Attention 的一种设计，可与 MoE 同时使用 |
| Skills | Agent 应用层按需加载的方法与资源 |
| Multi-Agent | 多个执行主体进行任务委派和协作 |

MoE 不会自己发现技能文件、调用 Harness 工具或启动子 Agent。它可以是这些应用背后的基础模型架构，但不是应用层的“专家团队”。

### DeepSeek-V3 的两个口径提醒

- 官方下载说明另列 **685B = 671B 主模型 + 14B MTP 模块**；不要与主模型总参数混用。
- “Auxiliary-loss-free load balancing”指其主要负载平衡策略，不表示整个训练没有任何辅助目标；报告仍讨论序列级辅助平衡项。本章教学 router 也不是其路由算法的逐项复现。
