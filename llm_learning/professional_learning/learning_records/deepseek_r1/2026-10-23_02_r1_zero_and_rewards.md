# 02 · R1-Zero：没有示范推理，奖励怎样带来改进？

## 1. 先区分问题、回答、奖励

用一道**自拟教学题**贯穿：“正整数 1 到 20 的和是多少？”

| 对象 | 示例 | 谁能看见 |
|---|---|---|
| 问题与格式要求 | 求和，并在指定位置给最终答案 | 模型 |
| 验证元信息 | 正确结果为 210；合法答案解析规则 | 验证器，不默认放进模型提示 |
| 模型回答 | 一段推导加最终结果，可能正确或错误 | 验证器与训练程序 |
| 奖励 | 正确性分与格式分 | 用于构造训练信号 |

不需要先写一份完整推导给模型模仿。但需要问题、可靠的判断方式以及能生成不同解答的起点。

这里的题目、数值和表格不是论文训练样本。

## 2. 论文采用哪些奖励？

### 2.1 正确性奖励

**论文事实**：数学任务可按规定格式提取最终答案并验证；编程任务利用编译 / 执行以及预定义测试反馈。

“编译成功”只说明满足某些语法和类型条件，不等于功能正确。编程正确性还要看任务测试是否覆盖目标行为。

**机制解释**：只要最终结果能可靠评分，奖励就可以给完整回答一个结果反馈，不必逐条标注推理步骤。

### 2.2 格式奖励

**论文事实**：R1-Zero 使用格式奖励，要求推理放在 `<think>` 与 `</think>` 之间；论文训练模板还把最终回答放在答案区域。

这是结构约束，不是每一步推理的真值。格式合格、答案错误的回答仍可能出现。

### 2.3 为什么不用神经奖励模型？

**作者报告**：R1-Zero 不使用神经网络形式的 outcome RM 或 process RM，理由包括大规模 RL 中的 reward hacking，以及重训 RM 的资源与流程成本。

这句话只描述 R1-Zero 的方案：

- 不等于没有奖励计算。
- 不等于取消所有人工规则。
- 不等于规则验证器永远不会被利用。
- 不等于最终 R1 的所有阶段都不用学习型 RM。

最终 R1 的一般任务会使用奖励模型，见[四阶段训练](2026-10-23_04_r1_pipeline_and_data.md)。

## 3. 为什么结果奖励能影响前面的推理 token？

一次回答的生成路径由一串动作构成，每个动作是选择下一个 token。

```text
问题
  → 采样多个完整回答
  → 对各回答评分
  → 同题内比较奖励
  → 计算已采样 token 的策略目标
  → 更新模型参数
  → 用新策略继续采样
```

获得较好相对奖励的路径，其已采样动作倾向于被提高概率；较差路径则倾向于被降低概率。准确的目标包含 clip 和 KL，不是简单复制成功回答。

**重要局限**：整段回答奖励高，不说明里面每一步都正确。一个回答可以中间算错、后来纠正；也可以逻辑有问题但碰巧得到正确结果。结果奖励的信用分配比较粗。

这也是 RL 与筛选后 SFT 的区别：RL 直接用相对奖励改变采样策略；筛选后 SFT 则把保留文本当作示范。两者可以组合，但不是同一种更新。

## 4. “反思行为出现”应当怎样理解？

论文报告随着训练推进：

- AIME 表现提高。
- 平均回答长度增长。
- 部分输出会回看已有步骤、修正思路或尝试替代路线。

**合理解释**：如果检查与纠错确实帮助获得更高奖励，这类行为可能被强化。模型在推理时多生成一些 token，等于投入更多顺序计算。

**不能直接推出**：

- 字数越多越好。
- 每次出现“重新检查”就真的完成了有效检查。
- 这类行为完全不依赖预训练。
- 模型获得了人类式主观体验。
- 论文已经定位了对应的内部神经机制。

输出中的反思文字是可观测行为，不是直接读取内部认知过程的仪器。

## 5. 三个经常混淆的实验数字

| 作者报告 | 指标和对象 | 应怎样读 |
|---|---|---|
| 15.6% → 71.0% | R1-Zero 的 AIME 2024 平均 pass@1 训练变化 | 在给定协议下，单次采样的正确率估计提高 |
| 86.7% | R1-Zero 的 AIME 多数投票结果 | 使用了多样本聚合，不能当成同预算单次回答 |
| 图 2 每题 16 个回答 | R1-Zero 训练曲线的评估说明 | 降低估计波动，不是 GRPO 训练组大小的披露 |

最终 R1 的 AIME pass@1 为 79.8%，属于另一模型和结果表。不能把 71.0% → 79.8% 当成只加冷启动数据的独立消融；两条路线还有其他区别。

评测的精确解释见[第 6 章](2026-10-23_06_evaluation_and_evidence.md)。

## 6. 为什么 Zero 还不是理想产品？

**作者报告**：Zero 存在可读性不足、语言混杂等问题。

**机制解释**：如果奖励主要关心答案正确与格式，很难期待它同时精确表达“简洁、语言一致、适合用户、复杂指令可靠”。没有被充分衡量的目标，不能假设会自动达标。

可以把问题写成：

```text
任务能得分
≠ 推理每一步都可靠
≠ 表达适合用户
≠ 各类指令都遵守
≠ 能胜任长程 Agent 工作
```

这并不否定 Zero 的研究价值。它让作者先检验直接 RL 的潜力，再用 R1 的后续设计处理产品能力。

## 7. 奖励质量是核心工程约束

下表为**机制分析与工程建议**，不是论文公开的实现配置。

| 失败类型 | 训练会学到什么问题 | 需要检查什么 |
|---|---|---|
| 解析器接受了错误位置的答案 | 学会满足解析器，而非任务 | 唯一答案区域、歧义、空输出 |
| 测试只覆盖常见输入 | 学会通过窄测试 | 边界、随机与独立隐藏测试 |
| 奖励只偏向正确格式 | 格式增长，功能未提升 | 格式和正确性分开记录 |
| 运行环境超时被粗暴记为代码错误 | 混淆设施故障与模型错误 | 超时分类、版本和重试语义 |
| 所有回答都同分 | 正确性优势没有组内差异 | 按任务难度监测全对 / 全错组 |

评测测试集必须与训练奖励数据隔离。生成代码只能在适当隔离、受限的环境中运行，不在开发者日常环境直接执行。
