## 1. 这里主要不是 BPB

R1 报告关心实际生成的答案与任务结果。根据任务使用正确率、精确匹配、F1、指令遵循、代码测试、竞赛排名或裁判偏好。

| 测量对象 | 典型指标 | 问题 |
|---|---|---|
| 参考文本概率 | NLL / PPL / BPB | 真实参考续文有多大概率？ |
| 生成答案 | pass@1、EM、答案正确率 | 自己生成时是否答对？ |
| 程序与修改结果 | 测试通过、任务解决率 | 产物能否完成任务？ |
| 约束遵循 | IF-Eval 的 Prompt Strict | 该提示的规定约束是否全部满足？ |
| 开放回答偏好 | LC-winrate、裁判比较 | 在指定裁判协议下更偏好哪个回答？ |

这些指标不能互相替代。输出 token 的概率参与生成，不代表报告的评测分数就是概率指标。

## 2. 先固定采样协议，再看分数

**v1 §3 披露**：

- 最大生成长度为 32,768 token；这是上限，不是每题实际长度。
- 采样温度 0.6，top-p 0.95。
- 用每题多次采样估计 pass@1；报告写通常为 4–64 次，随测试集规模而定。
- AIME 另报告 64 样本的 consensus，即 cons@64。
- 部分原有 few-shot 提示改为 zero-shot；不同 benchmark 仍有自己的协议。
- o1-1217 的比较分数引用官方报告，不是作者对所有模型都进行完全同条件的本地重测。

**别混用三个采样数量**：

| 场景 | 文中说明 | 不是 |
|---|---|---|
| Zero 训练曲线 | 图 2 每题 16 个回答 | GRPO 训练组大小 |

官方仓库的评测段把需要采样的任务写为每题 64 次。读原论文时保留 v1 的 4–64 表述，不用可变 README 覆盖固定论文版本。

## 3. 多次采样估计 pass@1，为什么仍叫 @1？

对第 $q$ 题生成 $n_q$ 个回答，其中 $c_q$ 个正确：

$$
\widehat{\mathrm{pass@1}}_q=\frac{c_q}{n_q},
\qquad
\widehat{\mathrm{pass@1}}=\frac1Q\sum_{q=1}^{Q}\frac{c_q}{n_q}.
$$

多采样是为了更稳定地估计“从这个分布抽一个回答能答对的概率”，不是把所有回答都交给用户，再用真值替他选对的那个。

实际只让模型回答一次时，仍会失败。79.8% 不代表每题都以确定性的 79.8% 完成，也不是某一回合绝对保证。

## 4. pass@k 与 consensus 是两种不同操作

### 4.1 pass@k：有至少一个成功吗？

若一题抽了 $n$ 个样本，$c$ 个成功，常用估计式为：

$$
\widehat{\mathrm{pass@k}}
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}},
\qquad n\ge k.
$$

若剩余错误样本少于 $k$，分子视为零。这是基于采样与交换性条件的估计，不是多次调用任意系统都自动适用的保证。

它衡量成功样本是否存在，不负责解决部署时“如何知道哪个答案对”。

### 4.2 consensus：按答案频次选一个

先规范化答案，再选出现次数最多的答案。并列、解析失败和无效答案需要明确处理。

不需要查看正确答案来挑选，但大量相同的错误回答可以赢得投票。题目没有可一致抽取的最终答案时，投票也更复杂。

### 4.3 一组手算

**教学示例**：正确答案是 210，8 次输出为：

```text
210, 210, 210, 200, 200, 200, 200, 190
```

| 指标 / 操作 | 本例结果 |
|---|---|
| pass@1 估计 | 3 / 8 = 37.5% |
| pass@2 估计 | 1 − C(5,2) / C(8,2) = 9 / 14 ≈ 64.29% |
| 这批 8 个样本中至少一个正确 | 是 |
| 这批 8 个样本的 consensus | 选 200，错误 |

因此“至少一个正确”与“能无真值地选出正确答案”差别很大。投票增益不能直接当成权重训练增益。

| 指标 | DeepSeek-V3 | R1 | o1-1217 | 读法 |

| AIME 2024 pass@1 | 39.2 | 79.8 | 79.2 | 特定数学题与采样协议，不是数学全领域 |
| MATH-500 pass@1 | 90.2 | 97.3 | 96.4 | 高分仍受题集、提示和生成预算约束 |

| SWE Verified resolved | 42.0 | 49.2 | 48.9 | 仓库任务与框架共同影响结果 |
| IF-Eval Prompt Strict | 86.1 | 83.3 | 未列 | R1 并非所有指令遵循指标都高于 V3 |
| C-SimpleQA correct | 68.0 | 63.7 | 未列 | 论文讨论安全 RL 后的部分拒答影响 |

两个需要停下来想的问题：

- AIME 上 79.8 与 79.2 的差距，是否足以证明稳定领先？没有相应不确定性分析，不能只按小数点排出普适强弱。
- 数学与算法代码大幅提升，为什么指令格式和部分事实问答没有同步提升？因为训练目标、数据与评测并不相同。

表 4 是端到端模型比较，不是“只加 RL”的干净消融。模型版本、SFT、数据和其他训练差异都要纳入解释。

## 6. 执行代码不等于模型在做 Coding Agent

论文说明 SWE-bench Verified 使用 **Agentless 框架**，Aider 使用 diff 格式；算法编程还包括 LiveCodeBench 与 Codeforces。

```text
模型生成代码 → 外部执行器运行测试 → 得到分数
```

这个链条不要求模型主动选择测试工具或根据反馈修复。

```text
模型选动作 → 工具执行 → 读反馈 → 修改方案 → 再测试
```

后者才包含多步交互策略。框架、上下文、权限、测试环境和预算共同决定系统结果。不能把 R1 的某个算法题分数直接当成通用 Coding Agent 可靠性。

## 7. 开放式裁判评测也有口径

**论文事实**：AlpacaEval 2.0 与 Arena-Hard 采用相应裁判协议；评估只传最终摘要，避免整段长推理直接造成长度偏好。

**分析**：减少某一种偏差，不等于消除了所有裁判偏差。表达风格、语言、事实核查能力、模型相似性和对比位置都仍值得控制。

LC-winrate 是长度控制后的偏好胜率，不是“回答事实正确率”。

## 8. 自己重测时至少记录什么？

下表是**评测设计建议**，本次没有执行：

| 类别 | 最小记录 |
|---|---|
| 模型 | 精确 checkpoint、tokenizer、chat template、精度 |
| 数据 | 版本、时间窗、拆分与污染检查 |
| 生成 | 提示、temperature、top-p、最大长度、随机种子、每题次数 |
| 评分 | 答案解析、测试环境、超时、无效输出、投票平局规则 |
| 成本 | 实际生成 token、延迟、测试时间、截断率 |
| 统计 | 按题结果、失败切片、不确定性与运行间波动 |

比较长度或多采样增益，应固定模型与总预算。估计不确定性时保留题目结构，不把同一题的多次样本全当成独立题目。
