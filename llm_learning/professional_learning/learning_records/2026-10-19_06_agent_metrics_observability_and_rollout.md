# Agent 主干 14：指标、可观测性与上线

[主学习索引](../index-2026-10-08.md) · 上一课：[评测与执行环境](2026-10-19_05_agent_evaluation_and_environments.md) · [每日概览](topics_by_date.md)

学习日期：2026-10-19。本课从“已经能可靠判分”继续，走完 **汇总指标 → 查看失败 trace → 定位原因 → 决定发布 → 灰度与回滚**。全部数字、事件和门槛均为教学示例，不是实测或生产配置；不部署系统、不接入监控服务。

## 1. 是什么：分数说明表现，执行记录解释原因，发布门槛决定行动

上一课的周报任务是：生成草稿，申请发送；用户拒绝后保留草稿，不得发送。

假设候选版本运行了 100 个这样的任务，都已接纳、结算并完成判分，没有用户主动取消或评测环境错误：

| 已知结果 | 数量 |
---|---|
| 草稿、事实、申请与最终答复等业务结果满足要求 | 90 个任务 |
| 上述 90 个中，拒绝后仍尝试发送，但被策略拦住 | 3 个任务 |
| 其余业务结果未满足要求 | 10 个任务 |
| 实际发生未授权发送 | 0 个任务 |
| 工具调用尝试 / 返回执行成功 | 300 次 / 294 次 |
| 模型与收费工具的总费用 | 20 元 |

那这个版本的成功率是 90%、98%，还是 87%？

**取决于你算的是什么。** 按上一课的严格标准，既要满足业务要求，又不能有违规发送尝试，因此只有 **87 个任务整体通过**。策略挡住了错误动作，不等于模型没有提出错误动作。

本课区分三件事：

- **指标**：100 个任务中多少成功、慢在哪里、总共花了多少。
- **可观测性**：能否沿某个失败任务找到相关调用、结果、状态与版本，解释发生了什么。
- **发布控制**：根据预先设定的条件，决定拒绝发布、扩大流量、暂停或回滚。

只有仪表盘而没有可关联记录，往往只能发现“变差了”；只有大量日志而没有判分与门槛，也不容易知道“是否值得处理、能否上线”。

## 2. 先把指标算对：每个比例都要讲清分子与分母

### 2.1 工具成功，不等于任务成功

沿用同一批数据：

| 指标 | 计算 | 含义 |
---|---|---|
| 业务结果满足率 | 90 ÷ 100 = 90% | 只检查表中列出的业务要求 |
| 严格任务成功率 | (90 − 3) ÷ 100 = **87%** | 同时满足业务与过程约束 |
| 工具执行成功率 | 294 ÷ 300 = 98% | 工具尝试中返回执行成功的比例，不含策略拒绝 |
| 违规尝试任务率 | 3 ÷ 100 = 3% | 有过违规尝试的任务比例，不是调用次数比例 |
| 未授权发送任务率 | 0 ÷ 100 = 0% | 本批没有观察到实际未授权发送 |

工具成功只表示工具完成了契约中的动作。例如文件成功写入了，内容仍可能错误。反过来，策略拒绝一次不该执行的调用，可能降低工具执行成功率，却保护了系统。

因此应把**参数错误、授权拒绝、工具故障、业务结果错误**分开统计，不用一个“tool error”掩盖所有差异。参数正确率检查 schema / 参数契约，不能从工具返回成功率直接推导。

另外两个常用指标也需要限定口径：

- **恢复率**：在事先定义的可恢复故障任务中，有多少最终满足该任务的成功条件；不只是“后来有一次调用成功”。
- **无进展任务率**：有多少任务触发明确的无进展规则，例如状态未变时反复做同一动作；不能把所有长任务都当成死循环。

### 2.2 成本要把失败、重试和子 Agent 算进去

本例 20 元只计模型与收费工具，包含所有任务的重试和子 Agent 调用；评测 grader 费用、固定基础设施费用另列。

| 口径 | 结果 | 回答的问题 |
---|---|---|
| 每接纳任务平均成本 | 20 ÷ 100 = **0.20 元** | 接一个任务平均花多少 |
| 每成功任务摊销成本 | 20 ÷ 87 ≈ **0.23 元** | 把失败消耗也计入后，获得一次成功要花多少 |

第二项不是“只在成功任务中求平均”。如果只统计成功路径的费用，会隐藏失败和重试带来的成本。

不能简单用全部 tokens 乘同一个单价：输入、输出、缓存、不同模型可能分别计价。应保留 usage、价格版本与账单口径；缺失用量记为缺失，估算记为估算，不默认为零。

### 2.3 为什么还要看 p95，而不只看平均延迟？

先确定测量边界：

- **用户端到端时间**：从任务被接纳到结果交付，包括排队、模型、工具和等待用户回复。
- **扣除用户等待的系统处理时间**：用于观察系统本身的处理体验，仍包含工具 I/O、排队等，不是 CPU 实际工作时间。

两者应分别报告，不能在新版本中偷偷扣掉等待时间，让数字看起来改善。

假设这 100 个任务的系统处理时间为：

| 任务数 | 每个任务耗时 |
---|---|
| 94 | 10 秒 |
| 5 | 40 秒 |
| 1 | 100 秒 |

平均值为 **12.4 秒**，但本例按 nearest-rank 定义计算 p95：排序后取第 95 个值，得到 **40 秒**。平均值掩盖了慢任务的体验。

这只是对当前样本的描述，不保证下一批也有相同表现；不同统计库的分位数插值定义也可能不同，比较时要固定口径。不要平均各机器的 p95 来充当全局 p95。

并行任务的时长也不能把所有子 span 直接相加：两个同时进行的 5 秒读取，可能只占约 5 秒墙钟时间，而不是 10 秒。

### 2.4 在线数据不一定立刻有最终分数

真实任务可能仍在等待用户，语义检查可能延迟完成。应保留“待结算 / 已判分 / 无法判定”等状态，并报告判分覆盖率与观察窗口，不能把未知直接归入成功。

如果只抽样检查了部分任务，就报告抽样范围、估计和不确定性，不把样本成功率包装成全部流量的精确成功率。用户主动取消、环境错误的纳入规则也要固定，不能为抬高指标事后删除。

**每个指标都应带范围、窗口、版本和样本量。** 例如“本轮 100 个已判分周报任务”与“所有线上任务过去 7 天”是两种不同口径。

## 3. 从一个失败任务看 trace：究竟是哪一步出了问题？

### 3.1 Trace 和 span 先用一条执行路径解释

从那 3 个违规尝试中选一个任务 T42。它生成了正确草稿，但收到拒绝后仍请求发送，最终被权限策略阻止。

下面是教学用的执行结构，不是 DeepSeek Harness 的内置 span 命名或固定 turn / step 编号：

```text
Task T42
  Prepare draft
    LLM request
    Read development source
    Read operations source
    LLM request
    Write report
  Request approval
    User reply: denied
  Handle denial
    LLM request
    Send-mail tool attempt
      Policy decision: denied
      Backend execution: not started
```

- **Trace**：将一次执行中相关的工作关联起来，供我们查看整条路径。
- **Span**：其中一个有起止时间的工作单元，例如一次模型请求或工具尝试。
- **Event**：发生在某个时刻的事实，例如收到用户拒绝、策略拒绝调用。

模型请求结束后才执行的工具，不应仅为了画成一棵树就被记为仍在进行的模型请求的子操作。层级、时间和因果关系要符合真实执行；并行分支也要保留重叠。

本例可用一个 trace 表示任务；长时间暂停、恢复或跨服务任务也可拆成多个 trace，通过 taskId 和关联信息串起来，不必让一个 span 永远挂着。

### 3.2 记录哪些信息，才能把碎片连起来？

| 信息 | 用途 |
---|---|
| taskId / trialId | 确认属于哪个业务任务、哪次评测运行 |
| traceId / spanId / 父子或关联关系 | 串起同一次执行及其分支 |
| 工具调用 ID / provider request ID | 对应具体请求与结果，排查外部服务问题 |
| 开始、结束、等待和重试信息 | 判断时间花在哪里，是否存在放大或阻塞 |
| 结果类别 | 区分执行成功、参数错、策略拒绝、超时、取消、结果未知 |
| 版本与输入引用 | 知道用的是哪套模型、prompt、Skills、工具、策略和资料 |

任务根记录可以关联一份配置指纹，不必在每条事件里复制全文。仅记录“v2”通常不够：同一代码版本配不同 prompt 或 Skill，也可能产生不同结果。

一条策略拒绝事件可以像这样记录，字段为自拟格式，不是 OTLP 或 Harness 的固定 schema：

```json
{
  "taskId": "T42",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "event": "tool.denied",
  "toolName": "send_mail",
  "approvalDecision": "denied",
  "executed": false,
  "agentVersion": "report-agent-v2"
}
```

这能说明一次尝试被拦住，但它本身不证明“全任务从未发送”。仍需与完整的工具记录、后端状态和上一课的独立判分结合。

### 3.3 怎样从记录判断原因？

本例不要看到 `tool.denied` 就去“修复权限，让邮件能发出去”。策略拒绝恰恰是正确行为。

排查顺序：

1. **先核实事实**：交互记录确实是拒绝；发送后端确实未启动。
2. **再看模型当时收到什么**：拒绝消息是否进入后续实际 request，而不只是存在于数据库里。
3. **若拒绝未进入 request**：优先检查消息接纳、上下文组装或恢复是否丢失信息。
4. **若拒绝已进入 request**：检查是否有冲突指令、错误工具描述或模型行为问题，再用对照实验验证。
5. **修复后回归**：除了这条坏例，还要跑拒绝、批准、缺资料等其他任务，避免修好一个分支又破坏另一个。

Trace 提供证据和候选原因，不自动完成因果证明。比如“加载了某个 Skill 后失败”只说明先后关系，还需要控制其他变量比较。

### 3.4 Metrics、logs、traces 各自放什么？

| 信号 | 适合回答 |
---|---|
| Metrics | 哪个版本的失败率、费用或尾延迟变高了 |
| Logs / events | 某个错误或决策发生时有哪些具体字段 |
| Traces | 这些工作怎样关联、先后或并行，时间花在哪里 |

聚合指标用工具类别、错误类型、少量发布版本等可控标签；不要把每个 taskId、用户 ID、完整 prompt 都变成指标标签，否则维度会急剧膨胀。具体 ID 留在可查询的记录中。

也不应默认把所有请求正文上传到监控系统。优先记录结构、状态、摘要和受控产物引用；需要保留原文时，单独处理授权、敏感信息、访问控制与保留期限。内容哈希便于关联，但不自动完成匿名化，也不能替代受控的版本快照。

普通性能 trace 可以按明确规则采样；安全审计和费用账本不能依赖“刚好采样到了”。可观测数据丢失也要有显式状态或告警，不应把“没有记录”解释成“没有发生错误”。

### 3.5 回放不等于重新执行所有动作

| 回放方式 | 做什么 | 不能证明什么 |
---|---|---|
| 查看历史事件与产物 | 还原当时的可观察过程 | 修复后的版本会产生同样行为 |
| 使用记录的模型 / 工具响应 | 确定性重放部分控制逻辑 | 真实模型与外部服务的当前表现 |
| 在重置的隔离环境重新运行 | 验证新版本端到端行为 | 生产环境一定相同 |

**不能为了复现问题，把历史发送调用直接重新发到真实邮件服务。** 历史批准也不能自动授权新的操作；结果未知的副作用先查询与对账，不能靠回放制造重复执行。

## 4. 从指标到上线：先设门槛，再决定是否放量

### 4.1 给刚才的候选版本做一次发布判断

先设以下教学门槛，再看结果；这些数字只是演示，不是通用 SLA 或上线建议：

| 门槛 | 本批结果 | 判断 |
---|---|---|
| 严格任务成功率至少 90% | 87% | 不通过 |
| 违规发送尝试任务数为 0 | 3 | 不通过 |
| 实际未授权发送为 0 | 0 | 本批通过 |
| 系统处理时间 p95 不超过 45 秒 | 40 秒 | 本批通过 |
| 每成功任务摊销费用不超过 0.25 元 | 约 0.23 元 | 本批通过 |

结论：**拒绝发布这个候选版本。** 延迟与成本好看，不能抵消任务正确性和策略遵循问题。

门槛必须说明任务范围、观察窗口、样本要求与分位数算法。真实发布还要看相对基线的退化、不同任务类别和统计不确定性；100 次未观察到某种事故，不证明事故概率为零。

生产中的 SLO 可以理解为明确范围与时间窗口内的服务目标；它与一次离线测试门槛相关，但不是同一件事。线上语义判分覆盖不足时，也不能声称已经证明整体满足目标。

### 4.2 修复并通过验证后，再逐步接近真实流量

| 阶段 | 怎样控制风险 |
---|---|
| 离线回归 | 固定任务、预算和判分，检查坏例及其他分支 |
| Shadow / 影子运行 | 在获准数据上比较新旧行为；写操作必须隔离、模拟或禁用，不重复操作真实业务 |
| Canary / 小流量灰度 | 仅让一小部分获准任务使用新版本，同时保留旧版本作为对照 |
| 逐步扩大 | 达到预定观察窗口和样本要求，且未触发停止条件，才继续放量 |

不能把生产流量复制一份就称为“无风险 shadow”；副本如果也能发邮件、修改文件，同样会产生副作用。

分组尽量稳定在用户、Session 或业务任务等合适单位，不在同一任务中随意切换新旧策略。比较时注意任务难度、流量和服务状态差异，避免把输入分布变化误判为版本提升。

### 4.3 触发回滚时，具体退回哪些东西？

至少要能定位并退回适当的代码、模型配置、prompt、Skill、工具与策略版本；并明确：

- 停止给问题版本分配新任务。
- 已在运行的任务是安全排空、取消还是人工接管，不能任其成为遗留后台工作。
- 已保存 Session 和状态能否由旧版本读取；存在不兼容迁移时，不是简单切一个版本号。
- 已发送邮件、写入数据库等副作用怎样查证和补救。

**回滚代码不会撤回已发送邮件。** 版本回滚、执行取消、数据恢复和业务补偿是不同动作，要分别设计。

## 5. 最小实现与验收：先让一个失败能被定位

建议从现有周报评测器增加以下能力，不先引入多套监控平台：

1. 一条任务级结果记录：判分状态、检查项、版本、耗时与成本口径。
2. 可关联的模型 / 工具 / 交互 / 策略记录，明确尝试与实际执行。
3. 一张按版本汇总的表：成功、安全、成本、延迟及判分覆盖率。
4. 一份可执行的发布门槛和停止 / 回滚流程。

待实施的验收：

| 测试 | 应观察到什么 |
---|---|
| 100 个任务中 90 个业务满足，其中 3 个违规尝试 | 严格成功率是 87%，不是 90% 或工具成功率 |
| 两个读取各耗时 5 秒且完全并行 | 不把它们的累计 10 秒当成任务墙钟耗时 |
| 同一工具失败两次后成功 | 所有尝试的时间、调用数和费用都有记录；任务仍需独立判分 |
| 缺失一次模型 usage | 显示缺失或标明估算，不按零费用处理 |
| 用户拒绝后工具被拦截 | 能沿记录定位拒绝、模型请求、调用尝试和策略结果 |
| 只采集了部分 trace | 不据此宣称所有任务无违规，或把样本分布当成完整分布 |
| 回放历史发送步骤 | 只在隔离 / 模拟目标中执行，不触发真实发送 |
| 候选版本违反安全门槛 | 停止发布或放量，不让平均质量分覆盖违规 |

本轮只提供学习材料与算例核对，以上运行时能力和验收尚未实现。
