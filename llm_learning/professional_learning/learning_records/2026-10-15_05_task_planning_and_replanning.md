## 1. 先给任务，再看为什么需要计划

用户要求：

> 合并 sales.csv 与 returns.xlsx，按地区统计第三季度净销售额，生成报告和结果表。不要改原文件，不要发送邮件；单位与退款口径有疑问先问我。

这个任务不是“写一段看起来像报告的文本”。需要定义：

- 净销售额如何计算，退款按哪个日期归属。
- 两张表的关联键、货币单位与重复订单规则。
- 资料是否覆盖完整季度。
- 输出文件及验收方式。
- 不修改原件、不对外发送。

计划的作用是组织这些依赖与未知项，不是让模型提前猜出所有表结构和结论。

### 1.1 第一版计划应当写什么？

| 步骤 | 动作 | 前提 | 完成证据 |
|---|---|---|---|
| P1 | 只读检查两文件的列、类型、样例与时间范围 | 已获文件读取权限 | 实际检查结果与来源 |
| P2 | 确认关联键、单位与退款口径 | P1；缺信息则询问用户 | 明确规则与确认来源 |
| P3 | 清洗并合并到新中间结果 | P2 | 处理日志、行数与匹配 / 未匹配统计 |
| P4 | 计算地区汇总与检查总额 | P3 | 可复核计算与一致性检查 |
| P5 | 写新结果表、图表与报告 | P4，输出位置允许写入 | 可打开的实际文件 |
| P6 | 核对产物与限制，再交付 | P5 | 内容检查、未修改原件的检查 |

列名、处理方法与具体路径在读取后再定，不把计划里的猜测提升为事实。用户授权生成新文件，不等于授权覆盖任何同名文件。

## 2. 最容易混淆的三个“计划”

| 层次 | 例子 | 谁保证它生效？ |
|---|---|---|
| 自然语言计划 / todo | “先读表，再合并，最后写报告” | 给模型与用户提供导航，本身不执行 |
| 可执行控制结构 | P4 依赖 P3；P2 缺信息就暂停 | runtime / workflow 的调度与状态规则 |
| 验证与授权条件 | 单位未确认不能计算；报告未检查不能交付；禁止发邮件 | 程序校验、权限与必要人工确认 |

**有 todo 列表，不等于有 DAG 调度器；写了“待批准”，不等于程序真的阻止执行。**

模型把 P5 标成 completed，最多说明它更新了进度声明。实际是否存在文件、金额正确，还要通过独立证据确认。

## 3. Plan–Execute：边执行，边更新已知状态

一种容易理解的模式：

```text
目标、约束与当前事实
        ↓
提出当前可行的计划
        ↓
选择一个前提已满足的步骤
        ↓
校验与执行工具
        ↓
取得结果，验证步骤
        ↓
更新事实 / 进度 / 未知项
        ↓
计划仍成立？继续；不成立？澄清或重规划
```

Planner 和 Executor 是职责，不要求两份模型。单 Agent 可以同时承担；业务流程也可用程序定义关键骨架，模型只决定如何检查文件或解释结果。

### 3.1 什么可以并行？

P1 中两个文件的独立只读检查可以在受控条件下并行；P4 不能在 P3 尚未形成有效合并结果时执行。

依赖图可简化为：

```text
检查销售表 ─┐
            ├→ 确认口径 → 合并 → 汇总验证 → 写产物 → 交付检查
检查退款表 ─┘
```

图中依赖是数据与业务前提，不是“在列表里排得更靠前”。共享写入路径、同一文件或 API 配额还会限制并行。

### 3.2 计划粒度怎么选？

太粗：“分析数据、完成报告”，无法检查进度。太细：提前列出每一次搜索或每一个 token，容易与真实环境脱节。

优先按可验证的里程碑分解；下一步所需事实清楚后，再展开局部动作。小任务可能不需要显式计划工具，多写一份计划不是自动增加能力。

## 4. 重规划：不是失败后再写一份漂亮清单

假设 P1 发现 sales.csv 金额单位为元，returns.xlsx 只写“金额”，没有单位。

错误做法：默认也是元，继续算完，再在报告里写“已核对”。

合理处理：

1. 保存已完成的文件检查及单位未知状态。
2. 将 P2 标为等待用户，不执行依赖单位确认的 P3 / P4。
3. 询问退款金额单位；保持禁止修改原文件等原有约束。
4. 用户确认后形成新计划版本，继续尚未完成的步骤。

另一种情况：用户确认退款金额单位为分。此前相关中间计算若基于错误假设，就需要作废并重算依赖结果；不是简单把失败项改成 completed。

| 触发因素 | 可能处理 |
|---|---|
| 缺少必要条件 | 澄清 / 等待，不猜测 |
| 单次临时工具故障 | 受限重试，未必改变整个计划 |
| 工具缺失或文件不可读 | 选择获准替代方式，或明确失败 |
| 用户改变口径 | 重新核对范围，作废受影响结果 |
| 预算不足 | 缩小任务需用户同意，或说明未完成并停止 |
| 已发出的外部写操作状态未知 | 先核查，不用重规划再次提交 |

重规划应记录变化原因、旧结果是否仍有效和剩余预算。不能通过“新计划”清空已用预算、扩大权限或绕过审批。

## 5. 计划清单如何与程序控制配合？

假设清单上写“单位确认后合并”。这句话不会自己阻止程序开始合并，必须明确规则：

```text
读取当前状态：
  销售表已检查？是
  退款表已检查？是
  单位已确认？否

程序决定：
  不执行合并，记录阻塞原因，等待澄清
```

用户确认单位后，程序更新状态并重新检查前提；合并完成后，也不是仅看模型是否勾选任务，而是检查产物和统计结果。

因此需要分别看：

1. **进度声明**：模型认为做到了哪一步。
2. **允许执行条件**：程序检查能否开始下一步。
3. **完成证据**：文件、工具结果、计算检查是否支持完成。

“先给我计划，批准后再执行”也要由实际授权机制落实。不能只在提示词里说先规划，却继续允许任何写入。

计划被保存后，下一次模型调用也不一定自动包含它；应用需要显式选取必要计划与任务状态。这属于通用上下文组织问题，不依赖特定框架的内部对象。

## 6. 如果要做自己的实现，计划数据应该加什么？

若需求超出简单进度清单，可以自行设计：

```json
{
  "plan_version": 2,
  "steps": [
    {
      "step_id": "merge",
      "description": "按确认口径合并到新结果",
      "depends_on": ["inspect_sales", "inspect_returns", "confirm_units"],
      "status": "blocked",
      "acceptance": "关联键、单位和退款归属已确认；保留未匹配统计",
      "evidence_refs": []
    }
  ]
}
```

这只是自编 schema，不是任何特定框架的接口。依赖中其他步骤在完整计划中另行定义。

字段不会自动实现保证。程序还需检查依赖存在、无环、状态转换、执行权限、产物证据与版本一致。`acceptance` 的自然语言可用于审核，但关键条件尽量转成可执行验证。

不要求每个 Agent 都实现自定义 DAG 系统。只有任务确实需要严格前提与调度时才增加这层复杂度。

## 7. 怎样判断规划真的有收益？

对相同办公任务与预算比较：

1. 单 Agent 直接执行，保留基本状态与安全控制。
2. 增加显式 todo，其他工具和模型不变。
3. 增加明确依赖 / 验证规则，记录额外实现和运行成本。

检查：

- 任务最终正确性与产物完整性。
- 未确认条件下是否提前执行。
- 条件变化后是否正确作废旧结果。
- 无用重复、失败恢复与成本。
- 模型标“完成”但产物不合格的比例。

先用可控文件与模拟工具测试，不能为评测批量修改真实办公资料。以下是待运行场景：单位缺失、表头改变、部分文件损坏、用户改口径、输出文件已存在、预算耗尽。

任务更长时可研究 Plan–Execute、Reflexion、树搜索等模式，但不要把“再反思一次”当独立验证；工具执行和可核验结果仍重要。

## 8. 阅读要点与进度

先记住：

> 计划组织意图；执行流落实依赖；验证提供完成证据；重规划只改变获准范围内的后续方案。

可选复习：

1. 模型更新 todo 状态，会自动生成执行依赖吗？
2. 提示模型“先规划”，是否必然禁止写入？
3. 用户改变退款口径后，旧汇总可否继续使用？
4. 应用保存过计划，是否意味着每轮模型都一定看到它？

<details>
<summary>参考答案</summary>

1. 不会，取决于是否有实际调度与约束实现。
2. 不一定，需要查看并验证执行权限。
3. 需检查依赖，作废并重算受影响结果。
4. 不一定，保存的信息需要经应用选择后才能成为本轮模型输入。
