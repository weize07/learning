## 1. 先明确评测对象：模型还是应用？

一个真实问答系统通常包含：

```text
用户问题
   ↓
资料选择 / 检索 → Prompt / 历史组织 → 模型生成
                                       ↓
                       解析 / 校验 / 重试 / 工具执行
                                       ↓
                                用户最终结果
```

模型评测可能固定资料与提示，只比较生成器。端到端应用评测还包含资料选择、错误处理与实际执行。

回答错误不一定是模型本身不行：可能检索没有找到答案、提供了过期资料、截断丢了条件或解析器错误。评测需保存足够上下文用于归因。

| 范围 | 要回答的问题 |
|---|---|
| 单组件 | 固定输入时，生成、检索或解析是否可靠？ |
| 端到端 | 用户任务是否完成，风险与成本是否可接受？ |
| 回归 | 新版本有没有破坏过去通过的关键场景？ |

## 2. 先定义成功，再挑指标

对有依据问答，成功至少意味着：

- 回答解决当前问题，事实与必要条件正确。
- 重要主张被本次提供的证据支持。
- 引用实际支持对应主张。
- 不足时合理说明，不无依据保证，也不过度拒答。

不能只看“出现了 [D1]”或“回答很长”。对工具 Agent，成功还包含执行结果与授权，不只看语言流畅。

把质量拆成可讨论的维度，不急着合成一个总分。高质量平均值不能掩盖关键越权、编造或错误执行。

## 3. 评测数据分成哪些用途？

| 集合 | 作用 | 是否用于调参 |
|---|---|---|
| 开发 / 验证集 | 比较 prompt、模型、配方与配置 | 是，因此不是最后的独立证据 |
| 留出测试集 | 选定方案后的最终评估 | 不反复用来挑方案 |
| 回归集 | 固定关键场景，阻止已知问题重现 | 可用于开发，但熟悉这些题不证明泛化 |
| 边界 / 对抗集 | 有意集中测试罕见高风险情况 | 单独报告，不冒充真实流量分布 |
| 线上样本 | 观察真实使用与分布漂移 | 需授权、隐私处理与清晰采样口径 |

训练数据与独立评测按文档、实体、会话等必要分组隔离，检查近重复。公开基准也可能已进入预训练，不能自动当成完全未见数据。

覆盖式黄金集有助于检测问题；只有采样与权重匹配目标流量，才适合声称估计线上平均效果。

## 4. 一条评测样本保存什么？

以虚构政策问答为例：

```json
{
  "id": "eval_001",
  "document_group": "policy_set_B",
  "question": "申请一定三天完成吗？",
  "evidence": [
    {"id": "D1", "text": "处理通常需要三个工作日。"},
    {"id": "D2", "text": "工作日不包含周末。"}
  ],
  "answerability": "partially_answerable",
  "required_facts": ["通常需要三个工作日", "不能据此保证三天完成"],
  "forbidden_claims": ["保证三天完成"],
  "support_map": [
    {"fact": "通常需要三个工作日", "evidence_ids": ["D1"]}
  ]
}
```

这是评测 schema 示意，不是当前 pilot 已实现的字段。执行时只把问题与允许的证据送给待测模型；required_facts、forbidden_claims 等保留给评分器，不泄露为提示答案。

可以保存参考答案，但允许等价表达，不要求逐字匹配。问题缺乏必要条件时，参考要求也不能偷偷补出条件。

运行结果另存：

- 模型、prompt、schema、生成配置与版本。
- 原始响应、最终展示答案与结束原因。
- 使用的实际证据、工具轨迹与错误状态。
- 输入 / 输出 token、耗时、重试与成本。
- 各项评分、评分器版本与审核状态。

失败请求也要记录，不只保存成功回答；缺失结果与评分器故障不能默认记满分。

## 5. 三类评分各擅长什么？

| 评分方式 | 适用情况 | 局限 |
|---|---|---|
| 规则 / 执行 | JSON 解析、schema、数值、引用 ID、代码测试、数据库状态 | 可验证局部条件，不自动理解全部语义 |
| 人工 | 事实、证据支持、复杂任务与错误归因 | 成本、一致性、专业知识与偏好偏差 |
| LLM-as-Judge | 大批量语义比较、预筛与辅助归因 | 可能误判、偏好长回答、自偏好、顺序偏差 |

推荐先制定 rubric，用人工审核的小样本校准规则和 LLM judge，再扩大自动评分。不是选一个大模型打分就获得客观真值。

### 5.1 LLM judge 怎样减少偏差？

- 提供判断所需的问题、证据与规则；仅看回答不能判断引用支持。
- 匿名模型身份，比较时随机答案顺序，必要时交换顺序复核。
- 要求具体错误与证据，不只输出一个不透明总分。
- 用独立人工标签评估 judge 的错误类型与分层一致性。
- 检查被评分文本中的指令注入，限制 judge 权限。
- 保存拒绝、无法判断与格式错误，不静默修成有效评分。

一致性高也不证明事实全对；两种评分器可以共同犯错。安全等高代价条件不只依赖平均 judge 分。

## 6. 有依据问答的指标与分母

| 指标 | 一个可操作的定义 | 注意 |
|---|---|---|
| 任务成功率 | 满足事先规定全部必要条件的请求数 / 纳入请求数 | 请求失败是否计失败应事先规定，通常需计入端到端结果 |
| 可答题正确率 | 可答问题中正确回答数 / 可答问题数 | 拒答不能当正确 |
| 不足处理正确率 | 不足题中合理处理数 / 不足题数 | 部分可答不等于必须全拒绝 |
| 事实支持率 | 被证据支持的受评主张数 / 受评主张数 | 主张切分与重要性规则固定 |
| 引用支持率 | 正确支持对应主张的引用数 / 输出引用数 | 引用 ID 存在只是结构检查 |
| 引用覆盖率 | 有有效支持引用的需引用主张数 / 需引用主张数 | 不是引用越多越好 |

没有输出主张或引用时，分母可能为零。应明确记为不适用或按任务规则判失败，不能因空答案把支持率或引用准确率默认设为 100%。

聚合也要明确：

- 按主张汇总：主张多的回答贡献更多项。
- 按请求先算再平均：每个有效请求权重相同，需处理不适用项。
- 业务流量加权：依据事先定义的目标分布，不依据训练配比。

不同指标共享事实支持，但不等价。例如每条引用都正确，仍可能遗漏关键结论。

## 7. 比较两个方案，怎样才可信？

固定独立输入、资料、评分规则与必要的生成设置，做配对比较。例如同一题分别调用基线和新版本，而不是两者各挑一批不同的简单题。

| 需要报告 | 原因 |
|---|---|
| 绝对指标与差值 | 说明基线和改善幅度 |
| 样本量、失败与不适用数量 | 防止只展示筛选后的成功结果 |
| 按类型拆分 | 平均提升可能掩盖长文或不可答退化 |
| 随机运行与不确定性 | 小分数差可能只是波动 |
| 成本、延迟、重试 | 更高质量可能对应明显成本 |

同一会话或文档中的问题可能相关，置信区间不应默认它们完全独立。多次试验只挑最高分，容易对验证集过拟合；最终留出集用于确认选定方案。

不要强行把不支持的参数传给所有供应商。允许模型各自正确模板，但记录差异，明确比较的是完整配置而非纯参数量。

## 8. 离线评测与在线评测

离线用于安全地复现、对照与归因；线上用于观察真实用户、工具和流量。两者都需要：

- 请求成功与失败。
- 质量与风险。
- 延迟、token 成本和重试。
- 任务 / 语言 / 长度等分布变化。

在线 A/B 应随机分配适当单位，例如用户或会话，避免跨组污染；指标应匹配分配单位，并检查样本比例异常等问题。涉及外部修改或高风险任务时，先离线、影子运行或有限灰度，不直接放开试验。

点赞率、点击率不是事实正确率；用户没投诉也不证明没有幻觉。需要抽样人工审核或可信任务结果作为补充。

## 9. 发布门槛与 bad case 闭环

```text
固定离线集 → 质量与风险门槛 → 影子 / 小范围灰度
                                     ↓
                             在线监测与抽查
                                     ↓
                         回滚或扩大 → 分类分析坏例
                                     ↓
                   修改资料、检索、prompt、模型或流程
```

门槛按风险确定，不提供全行业统一的“95% 即可上线”。给定资料问答应同时关注可答正确性、编造、过度拒答与引用；工具任务还要独立检查越权和副作用。

坏例归因可分为资料缺失、检索错误、上下文构造、生成错误、校验 / 工具错误、评分错误。修复后加入回归集，再用独立数据检查泛化，不仅验证背熟了坏例。

## 10. 常见工具与使用范围

| 工具 / 入口 | 可关注的方向 |
|---|---|
| [lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness) | 通用语言模型基准执行，不等于完整业务评测 |
| [Ragas](https://docs.ragas.io/) | RAG / LLM 评测指标与数据流程，具体定义依版本 |
| [DeepEval](https://github.com/confident-ai/deepeval) | LLM 测试与评测组织，judge 可靠性仍需校准 |
| [OpenAI Evals](https://github.com/openai/evals) | 评测构建参考，不将平台分数当客观万能指标 |

这是资料入口，不是已经验证的工具兼容或性能排名。本阶段不安装额外工具；先设计可信样本和评分定义，再决定采用哪种框架。
