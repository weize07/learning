## 1. 怎样使用

- 功能验收：用户能否完成任务，是否得到正确结果。
- 系统设计验收：在并发、错误、取消、重启、扩展时，规则是否仍成立。
- 每条用例保存：**版本 / 配置、初始状态、刺激、预期、实际结果、证据位置、通过 / 失败 / 未运行 / 不适用**。
- 不适用必须说明原因。例如第一版没有 UI，就不能声称“UI 与 SDK 一致性已通过”。
- 没有实现、没有执行、缺 API key 导致跳过，都不能标记通过。

## 2. 功能验收

| ID | 场景与操作 | 通过条件 | 必留证据 |
|---|---|---|---|
| F01 | 脚本化模型返回纯文本 | 正好 1 次模型请求；0 次工具执行；入口收到完整文本和明确结束状态 | 请求记录、最终输出、turn 结果 |
| F02 | 模型先调用 read，收到结果后回答 | 正好 2 次模型请求、1 次 read；第二次请求含同 callId 的正确结果 | 两次请求、工具事件、读取内容 |
| F03 | 在 idle / busy 状态下分别提交 queue、steer、inject | 符合下方投递表；输入不丢失、不重复、不悄悄修改在途请求 | 可控 barrier、输入 ID、请求 / turn 序列 |
| F04 | 模型首请求失败后成功；另测工具读取失败 | 模型按策略重试且计数准确；工具失败形成 error result，供后续步骤处理，不冒充成功 | attempt 数、调用次数、错误与恢复记录 |
| F05 | 分别在模型流、退避等待、工具执行期间取消 | 取消被传播；不启动后续工作；已启动工作按约定退出；入口明确显示取消 | 启动计数、abort 观察点、退出状态 |
| F06 | 保存会话，重新打开，再发送一个新问题 | 历史及调用关联恢复正确；新输入只接纳一次；不无依据重跑旧工具 | 保存内容、重建 messages、实际工具计数 |
| F07 | 请求越出允许目录、使用非法参数或未授权工具 | 执行被拒绝且原因可见；被保护文件未读取 / 修改，目标执行体未调用 | provider 调用计数、拒绝结果、文件对照 |
| F08 | 从正式交付入口完成只读文件问答 | 引用的文件存在、答案与受控测试文件一致；无意外写入；错误 / 取消不展示为成功 | 入口测试、独立答案核对、目录前后对照 |

### F03 的投递表

拟保留已学习的 DeepSeek 基本语义。这里限定普通运行阶段、创建已完成且未取消；maintenance、销毁和取消后新输入另列用例。

| 状态 / 时间点 | queue / followup | steer | inject |
|---|---|---|---|
| idle | 唤醒，进入新 turn | 唤醒，进入可接纳的 turn / step | 留在待接纳队列，不自行唤醒 |
| busy，目标 step 尚未 claim | 留待后续 turn | 当前可接纳的 step | 当前可接纳的 step |
| busy，目标 step 已 claim | 留待后续 turn | 后续可接纳的 step，不改在途请求 | 后续可接纳的 step，不改在途请求 |

测试用 barrier 精确控制 claim 前后，不用随机 sleep 猜时序。steer / inject 不承诺打断当前工具；当前活动结束也不保证取消后的待接纳输入仍保留。

## 3. 关键系统设计验收

| ID | 设计问题 | 用什么测试判定 | 通过条件 |
|---|---|---|---|
| D01 | 状态由谁修改？ | 同时提交多条输入；创建监听未完成时排队；重复请求 dispose | 每个 Agent 最多一个 Driver 推进；初始化失败不启动模型；已获取资源有明确释放者 |
| D02 | 模型输入能否追溯？ | 捕获一次请求，再用对应事件前缀、配置和投影重建；包含 prompt / tools 变化 | messages、模型配置、工具声明等模型可见字段一致；无未记录上下文；signal / 凭据不作为模型内容持久化 |
| D03 | 工具结果与外部副作用怎样区分？ | 正常、抛错、取消未启动调用；另在副作用发生后、结果提交前模拟崩溃 | 正常结算不重不漏；崩溃恢复可标记未知结果，不伪造成功、不自动重试非幂等操作 |
| D04 | 重试与新步骤是否混淆？ | 设置最大重试 2 次，模型持续报可重试错误；退避期间取消 | 总请求最多 3 次；仍属同 step 的不同 attempt；用户输入不重复接纳；取消后无重试启动 |
| D05 | 释放资源是否早于工作结束？ | 用 barrier 阻塞运行工作，发起 unload / dispose，再允许退出；模拟清理失败 | 运行所需资源保留到退出；之后注册与监听被移除；清理错误显式报告；不在仍有工作时谎报已释放 |
| D06 | 并发输入和工具是否有确定规则？ | 同时提交带 ID 的输入；工具并发上限设 2，混入 exclusive 调用 | 输入各接纳一次且顺序符合规则；并行数不超过 2；exclusive 不与其他调用重叠 |
| D07 | live 展示与持久结果是否一致？ | 分别在首 chunk 前、chunk 后、结算前失败 / 取消；完成后再打开历史 | 失败 attempt 不当作成功模型历史；保留片段明确标记中断；提交前进程丢失不冒充已持久化 |
| D08 | 替换模块是否真的只改相应实现？ | 用第二个脚本化模型适配器通过同一入口运行；反复装卸同一工具注册 | 不改 Driver 核心流程；无重复注册和泄漏；缺服务或非法配置显式失败 |
| D09 | 权限检查在哪里执行？ | 直接调用工具入口；使用包含 `..` 的路径、指向范围外的链接；若有审批，审批后改变参数 | 无法绕过策略进入未授权执行体；授权绑定实际动作和参数；不支持的隔离能力不得默许放行 |
| D10 | 上下文整理改变了什么？ | 固定 tokenizer / 计数方式，触发压缩，再重建实际请求 | 模型输入不超过已配置预算；必要任务约束及调用关联按预设断言保留；替换可追溯；工具落盘不被误算为 prompt 已缩短 |
| D11 | 如何阻止无止境运行？ | 步数上限设 3，模型持续要求工具；另给协作任务设置 deadline | 不启动第 4 步；停止原因明确；deadline 信号能传播；不配合退出的工作显式保留为未结束，不虚报清理成功 |
| D12 | 总预算会不会被重试和并发绕过？ | 用确定性预算账本：总额 100 单位，每次 attempt 预留 60；首次实际结算 50 后再申请；另测并发申请、辅助请求和 usage 缺失 | 并发时最多一笔 60 的预留成功；结算后剩 50，不批准下一笔 60；重试 / 辅助请求使用同一任务额度；usage 未知不按零结算；预算拒绝可见 |
| D13 | 队列和慢消费者是否有界？ | 阻塞 Driver 消费，待接纳上限设 2，提交 3 条；另阻塞展示消费者直至达到配置缓冲上限 | 队列不超过 2，第三条明确拒绝或背压，不静默丢弃；展示缓冲有界；溢出按声明策略断开 / 合并暂态帧，并能重读持久结果 |
| D14 | 能否排障又不泄露数据？ | 注入失败 attempt 与工具错误；在不应输出的认证字段放入测试标记；若有遥测，分别验证禁用与启用策略 | 可关联到 session / turn / step / attempt / callId；保留错误类别与停止原因；展示 / 日志 / 遥测不泄露标记；禁用遥测时无外发 |
| D15 | 打开不兼容记录会不会破坏原数据？ | 打开当前格式与未知未来格式；若声明支持旧版，运行旧版 fixture 及迁移失败场景 | 当前格式可打开；未知未来格式明确拒绝，文件不变；受支持旧版按声明规则迁移，失败不覆盖原记录；未实现迁移不得声称兼容 |
| D16 | 不同故障是否由正确层处理？ | 分别注入初始化失败、关键持久化检查点失败、已声明非关键的遥测发送失败；再组合主任务失败与清理失败 | 初始化失败不启动任务；关键保存失败停止依赖该检查点的后续副作用；非关键遥测故障可见但不重试整个任务；主错误与清理错误均可查，不互相覆盖 |

数字是测试配置，不是 DeepSeek 默认值，也不是生产性能承诺。D09 是目标项目授权边界的防御性验收，不代表已对下载源码进行安全审计。D12 的单位用于验证预算算法，不是假定供应商按此计费：真实费用需明确价格、usage 口径、预留上界与在途请求风险，不能据此宣称绝对不超支。D14 中无遥测实现时，外发分支标记不适用，但本地排障与凭据保护仍须验证。

## 4. 证据分层与上游参考

| 层次 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 静态源码 / 测试阅读 | 设计选择、实现分支、已有断言 | 此环境能运行、测试已经通过 |
| 确定性模块测试 | 时序、计数、状态与错误规则 | 正式装配和真实 provider 一定可用 |
| 正式入口 + 脚本化模型 | 配置装配、执行链、持久化和交付接线 | 真实模型格式兼容与任务效果 |
| 真实模型 + 独立任务检查 | 指定版本 / 配置 / 样例的实际效果 | 所有任务都可靠或全部环境都通过 |

优先参考[上游测试策略](../projects/deepseek-harness/docs/testing.md)的三个要求：只模拟外部不确定边界；走真实入口；独立检查实际产物，而非模型自述。

## 5. 放行规则

1. 任务卡声明的验收项必须全部通过；不通过就修复或明确缩小交付范围，不能悄悄降低标准。
2. 给出版本、命令、结果、关键产物与未验证项；仅交一张“全绿”截图不够。
3. 正式入口未验证，只能称模块实现完成；真实模型未验证，不宣称真实模型效果。
4. 如需延迟、内存、吞吐门槛，先固定硬件、模型、负载与测量区间，再约定数值；本轮不编造 p95 指标。
5. 当前状态：**清单已建立，所有运行验收均未开始；没有安装依赖、启动 Harness 或调用模型。**
