# 架构师如何指导 Coding Agent 实现类似 Harness

> [架构索引](2026-10-17_01_deepseek_harness_architecture_index.md) · [验收清单](2026-10-17_03_harness_acceptance_checklist.md)
>
> 本文是拟定的实施方法，不是要求立即开工，也不是复制 DeepSeek 的包结构。语言、框架、部署形式与模型预算在正式实施前确认。

## 1. 架构师与 Coding Agent 各自负责什么

| 架构师先确定 | Coding Agent 实现并举证 | 必须回来确认的变化 |
|---|---|---|
| 用户场景、成功条件、不做什么 | 需求对应的最小实现 | 扩大能力或更改用户行为 |
| 模块职责、接口、状态所有权 | 模块内实现、调用方接线 | 改公共接口、存储格式、并发语义 |
| 权限、失败处理、资源限制 | 校验、取消、清理和故障测试 | 增加外部副作用、凭据或部署要求 |
| 验收方式与放行标准 | 实际命令、结果、产物与残余风险 | 降低断言、跳过必测场景、刷新预期输出 |

架构师不必提前设计每个类；但不能把“状态归谁、失败怎么办、怎样算完成”交给 Agent 随意决定。

## 2. 第一版：做完整小闭环，不做缩水的全产品

**建议场景：用户提出文件问题 → 读取允许目录中的文件 → 返回回答与文件依据。**

- 先做：单 Agent、一个模型接口、只读工具、结构化消息、顺序执行、显式错误、取消、执行记录。
- 后做：持久化恢复、steer / inject、第二个 provider、受控写入与审批。
- 暂不做：桌面端、MCP、浏览器、多 Agent、动态热重载、完整插件市场。
- 控制流先用脚本化模型响应验证；接真实模型时再验证格式兼容与任务效果。两者不能互相替代。

### 编码前锁定六条规则

| 规则 | 第一版拟定要求 |
|---|---|
| 状态所有权 | 每个 Agent 同时最多一个 Driver 推进模型 / 工具闭环 |
| 消息关联 | 每个已接纳 tool call 有稳定 callId；结果显式标记成功、失败或跳过 |
| 请求来源 | 模型可见消息与配置有可追溯记录；不在发送前偷偷追加无记录上下文 |
| 失败分类 | 模型请求失败、工具失败、用户取消分别处理；不能一律 retry |
| 取消语义 | 阻止新的模型请求和工具启动；在运行的工作协作退出，已发生副作用不承诺回滚 |
| 完成语义 | 明确区分执行结束、执行错误、取消，以及业务验收是否通过 |

## 3. 按可验收的小闭环分批实现

每一批都从入口走到可观察结果；不是先让一个 Agent 写全部接口、另一个写全部存储，最后再拼起来。

每张任务卡还要检查[跨模块主题 X1～X8](2026-10-17_01_deepseek_harness_architecture_index.md)：写清本批的错误归属、预算、权限、恢复、资源上限及观测证据；不适用项说明理由，不要求每批重建所有机制。

| 批次 | 交付 | 依赖 | 放行项 |
|---|---|---|---|
| P0 固定外部接口 | Message、ModelAdapter、Tool、SessionEvent、运行结果定义；一份正常与失败事件样例 | 无 | 接口 / 样例静态审查，覆盖 ID 关联与状态所有权；不计任何运行验收通过 |
| P1 文本闭环 | 入口 → Driver → 脚本化模型 → 最终回复；保存事件 | P0 | F01、D02、D07 |
| P2 只读工具闭环 | 两次模型请求、中间真实 read、工具错误回填与权限拒绝 | P1 | F02、F07、D03、D09 |
| P3 可控执行 | busy queue / steer / inject、可取消等待、限次 retry、资源清理、步数 / 总预算、限并发、独占工具及有界队列 | P2 | F03～F05、D01、D04～D06、D11～D13 |
| P4 保存与恢复 | 持久化打开、消息重建、中断 / 未知结果、格式拒绝与故障归属 | P3 | F06、D02、D03、D15～D16 |
| P5 真实适配与交付 | 真实模型适配、正式入口 smoke、独立产物 / 答案检查、可关联日志与敏感字段保护 | P4；另确认 API 与环境授权 | F08、D07～D09、D14；复验 D12 的真实 usage 接线 |

MVP 不含上下文压缩，因此 D10 暂不适用；一旦增加 compaction 等能力，它必须进入同批验收。D13 的展示背压先覆盖当前入口；D14 遥测、D15 旧格式迁移仅在声明支持时测试相应分支。P0 不要求照搬 Cordis；接口可替换和完整插件系统不是同一成本。

## 4. 可直接交给 Coding Agent 的任务卡

下面以 P2 为例。实际使用时补入已确认的仓库路径、接口名称和验证命令。

```text
目标：
  完成“用户问题 -> 模型提出 read -> 真实读取 -> 模型回答”的闭环。

前置：
  P1 已通过；沿用已批准的 Message、ModelAdapter 和 SessionEvent。

范围：
  修改工具注册/执行模块、Driver 的工具衔接、对应测试及直接相关文档。
  不新增 UI、shell、网络工具；不改模型接口或持久化格式。

行为：
  1. 参数不合法、路径不允许或文件不存在时，返回结构化工具错误。
  2. 工具执行结果与原 callId 对应，写入事件后进入下一次请求。
  3. 不因工具失败自动重做外部操作。
  4. 未声明支持的输出类型显式报错，不静默丢弃。

验收：
  F02、F07、D03、D09。
  使用脚本化模型，保留真实 Driver、工具管线和文件读取实现。
  临时目录由测试创建和清理；同时校验非目标文件没有变化。

提交结果：
  修改摘要；实际执行的命令与结果；请求/事件关联证据；尚未验证项。
  不把“代码已写完”或模型自述当作测试结果。

停止条件：
  发现公共接口不能满足任务，先说明冲突和最小替代方案。
  未经确认不扩大范围、不安装不必要依赖、不调用真实模型。
```

## 5. 审查和返工：用证据作决定

| Agent 返回的情况 | 架构师动作 |
|---|---|
| 只有代码，没有执行证据 | 不放行；要求运行对应验收用例 |
| 单测通过，但没有真实入口测试 | 仅接受模块结论；不宣称产品可用 |
| 测试通过，但断言只检查“回答中有成功字样” | 改为独立检查文件 / 请求 / 事件 / 状态 |
| 为通过测试改弱断言或更新全部快照 | 审查行为是否本来就应该变；不能默认接受 |
| 错误被吞掉、取消后直接显示成功 | 返工错误模型和结果展示，不只补文案 |
| 接口、权限或恢复语义需要变化 | 先更新设计决定与受影响验收项，再继续实现 |
| 要求的证据齐全，未验证范围已说明 | 放行当前批次，不扩张为全系统通过 |

## 6. 从 DeepSeek 的工程规则学什么

项目的 [AGENTS.md](../projects/deepseek-harness/AGENTS.md)把设计规则变成协作约束；[测试策略](../projects/deepseek-harness/docs/testing.md)进一步规定怎样举证。对自建项目，优先借鉴：

1. **改动有归属**：新增能力先找接口或扩展点，不把所有逻辑堆进 Driver。
2. **资源有主人**：注册、监听、运行中的任务都要有对应清理。
3. **行为变化带测试**：新增状态或失败分支时，同批给出能检查该分支的断言。
4. **测试检查真实结果**：文件任务检查文件；恢复任务检查重建后的状态；展示任务检查用户实际看到的内容。
5. **贯穿真实入口**：模拟只替代模型 / 网络等外部边界，不把待测执行链也模拟掉。

不直接照搬其包数量、覆盖率政策或所有维护流程。先保留真正约束可靠性的规则，随着项目需求增长再增加机制。
