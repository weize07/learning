# 第 7 站：从设计到实现与验收

[专题入口](README.md) · 上一站：[异常与预算](2026-10-17_06_failures_budgets_resources.md)

可选扩展：[Multi-Agent 的实例、会话与协作管理](2026-10-18_08_multi_agent.md)。不改变本章单 Agent MVP 的范围与放行顺序。

## 1. 是什么：把架构决定转成实施任务与验收证据

下文 **Driver 指 Agent 实例内部启动的执行活动**；DeepSeek 由 ReactLoopAgent 的 kick / turn / step 方法实现，不额外创建 Driver 类实例。自建 MVP 可以采用不同组织方式，但要区分实例、执行活动和完成凭据的生命周期。

架构师不需要提前设计所有类，但必须明确：

1. **做什么、不做什么**：用户任务、允许能力与成功条件。
2. **谁拥有状态和资源**：输入、Driver、Session、预算和清理各归谁。
3. **失败怎样处理**：重试、取消、拒绝、未知结果与存储失败的动作。
4. **怎样证明完成**：需要哪些实际请求、事件、文件和测试结果。

Coding Agent 可以选择模块内部的合理写法，不能自行扩大权限、改变公共接口或降低验收标准。

## 2. 为什么要做：可运行代码不等于满足需求的系统

- 没有范围和接口约束，Coding Agent 可能实现一个能演示、却不符合权限和恢复要求的系统。
- 只有“测试通过”，无法判断测试是否走真实入口、是否检查了实际产物。
- 一次交付太大时，错误难以归属；需要每批都有明确行为和可验证结果。

## 3. 怎么做：先定任务，再分批实现与验证

### 3.1 拆出 read_doc 的输入、执行和输出

| 部分 | 本例的设计 | 关键问题 |
---|---|---|
| 模型输入 | path、可选读取上限 | schema 能表达哪些约束，哪些仍要业务检查？ |
| 权限 | 仅允许受控目录内的目标 | 链接与实际路径会不会越界？ |
| 主体 execute | 读取文件，传递 signal，返回规范值 | 取消后是否仍留有未观察的工作？ |
| 规范输出 | path、text、truncated 等明确字段 | 失败不能返回像成功的空文本 |
| 内容渲染 | 将规范结果转成模型可读内容 | 截断和错误是否被诚实表达？ |
| 注册与清理 | 注册由所属 plugin / scope 管理 | 卸载后是否仍残留旧工具？ |

这是我们拟定的工具，不是照抄上游字段。第一版不支持 shell、写入、后台任务或网络读取。

**原文明确**：[工具编写参考](../../projects/deepseek-harness/docs/cookbook/adding-a-tool.md)要求 typed defineTool 对已声明输入校验、execute 返回规范 JSON 值、output.render 负责内容、异步工作遵守 signal；无法由 schema 表达的业务约束仍需实现者检查。

**分析**：这使“模型能用”与“程序能验证”使用同一份数据。代价是你必须认真设计输入和输出，而不是只返回一段自然语言。

### 3.2 给 Coding Agent 的任务卡示例

以下是实施说明，不是可直接运行的代码。真实开工前补入已批准的接口名称、仓库范围和验证命令。

```text
目标：
  完成一次只读问答：用户问题 -> 模型调用 read_doc -> 真实文件读取
  -> 关联工具结果 -> 第二次模型请求 -> 答案。

前置：
  已有单 Agent 文本闭环、Message、ModelAdapter、SessionEvent。

允许修改：
  工具定义与执行模块、Driver 工具衔接、对应测试、直接相关文档。

行为要求：
  - 仅访问测试创建的允许目录；越界或不支持的操作明确拒绝。
  - 成功结果与错误结果均保留原 callId。
  - 规范值与渲染内容来自同一结果，截断明确标记。
  - 传递取消 signal；本批先顺序执行。
  - 不因工具失败自动重复操作，不隐式增加模型重试。

验证：
  - 只模拟模型，保留真实 Driver、工具管线和文件读取。
  - 正常路径：2 次模型请求、1 次工具执行，第二次请求含正确结果。
  - 错误路径：文件缺失、参数错误、路径拒绝，分别有明确断言。
  - 拒绝时执行体调用次数为 0，非目标文件字节不变。
  - 测试资源无论成功或失败都要清理。

停止条件：
  公共接口不够用或需要扩大权限时，说明冲突后请求决定。
  不自行添加 UI、shell、真实 API 调用或新的持久化格式。

提交：
  变更摘要、实际命令与结果、请求/事件证据、未验证项。
```

### 3.3 三层验证，各回答不同问题

| 证据 | 检查什么 | 不能替代什么 |
|---|---|---|
| 确定性模块 / 集成测试 | 输入关联、计数、错误、预算和并发规则 | 正式配置装配是否正确 |
| 正式入口 + 脚本化模型 | 真实启动、模块接线、存储、结果交付 | 真实 provider 格式与模型效果 |
| 真实模型 + 外部检查 | 指定环境下能否完成真实任务 | 全部任务、平台和故障组合 |

**原文明确**：[测试策略](../../projects/deepseek-harness/docs/testing.md)要求只 mock 贵或不确定的边界，走真实入口，并检查外部世界而非 Agent 自述。

因此不能把 Driver、工具和存储都替换成假对象，再据此宣布闭环可用。没有 API key 导致真实测试跳过，也不能写成通过。

### 3.4 直观例子：怎样识别“假通过”

文件内容为 `This fixture requires Node.js 24.`：

- **弱断言**：最终回答含“成功”或“读取完成”。
  - 模型即使没读文件，也可能输出这句话。
- **有效断言**：
  - 真实 read_doc 被调用一次，目标路径正确。
  - 第二次模型请求含文件中的版本要求，与 c1 对应。
  - 答案与测试文件一致，文件和目录无意外修改。
- **仍未证明**：
  - 所有真实模型都能遵守工具协议。
  - 恶意输入、崩溃和并发都已正确处理。

同理，恢复测试看重建状态和实际操作次数；预算测试看是否阻止超额启动；取消测试看是否还有新工作和遗留资源。

### 3.5 实施顺序：每批都能观察结果

| 批次 | 小闭环 | 必须先有 |
|---|---|---|
| P0 | 接口、状态所有权、正常 / 错误样例 | 已确认的范围与规则 |
| P1 | 输入 → 脚本化模型 → 文本输出与事件 | P0 |
| P2 | 工具调用 → 真实只读操作 → 后续回答 | P1 |
| P3 | 排队、重试、取消、预算、资源和并发控制 | P2 |
| P4 | 保存、打开、恢复、格式拒绝和存储故障 | P3 |
| P5 | 真实模型、正式入口和独立任务检查 | P4，以及环境 / API 授权 |

这与[实施方法](../2026-10-17_02_harness_architect_to_coding_agent.md)一致；准确的放行编号维护在该文，不另建第二套计划。

### 3.6 按证据放行

| 返回情况 | 决定 |
|---|---|
| 只交代码，没执行测试 | 未完成验证 |
| 单测绿，但没经过交付入口 | 仅认可模块结论 |
| 为通过测试删除断言或刷新全部预期 | 先审查行为变化，不能默认放行 |
| 超时被显示为成功，清理错误被吞掉 | 修复状态和错误模型，不只改文案 |
| 对应验收项通过，未验证范围明确 | 放行该批次，不扩张成全系统可靠 |

原文要求的覆盖率与 CI 规则属于该项目维护政策；自建 MVP 不必原样照搬，但必须保留“检查真实行为”的原则。

## 4. 为什么这么做：缩短反馈路径，避免验证错对象

| 依据 | 设计理由与代价 |
|---|---|
| **原文明确**：[工具编写参考](../../projects/deepseek-harness/docs/cookbook/adding-a-tool.md)区分规范值和渲染内容 | 程序不必解析自然语言；代价是输入 / 输出约束要设计并测试 |
| **原文明确**：[测试策略](../../projects/deepseek-harness/docs/testing.md)只模拟外部不确定边界 | 保留真正要验证的执行链；相比全 mock，测试要管理真实临时文件和资源 |
| **原文明确**：真实入口与外部结果是验证目标 | 避免“模块测试绿、产品却不能用”；代价是需增加组合和产物检查 |
| **我们的实施建议**：分可验收的小闭环交付 | 比全部模块写完再集成更早发现接口问题；需要每批维护稳定接口和验收范围 |

另一种做法是先让 Agent 自由完成，再整体评审。演示很快，但接口、权限和测试方向容易一起偏离；小闭环更适合约束多、失败后果不清楚的系统。

## 5. MVP 与验收：七站串起来得到什么

- 第 1 站确定模块分工。
- 第 2 站定义它们交换的数据。
- 第 3、4 站明确谁推进、怎样操作。
- 第 5 站说明哪些状态能恢复。
- 第 6 站规定什么时候重试、拒绝和停止。
- 本站把这些决定转成任务卡与证据门槛。

这就是架构师引导 Coding Agent 的最小输入：**范围、接口、规则、步骤、验收**，而不是一句“做一个类似 DeepSeek Harness 的项目”。

当前阶段仅完成学习材料整理。正式技术栈、实现范围、环境和模型预算需在开工前确认；没有安装依赖、启动服务或执行模型调用。
