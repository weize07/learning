# 扩展章 8：Multi-Agent 的实例、会话与协作管理

[专题入口](README.md) · 前置：[系统与作用域](2026-10-17_01_system_and_plugins.md)、[执行与生命周期](2026-10-17_03_loop_and_lifecycle.md) · 实施方法：[第 7 站](2026-10-17_07_implementation_and_acceptance.md)

**这是七站最小路径之外的扩展，不增加单 Agent MVP 的必做范围。** 本章先解释默认进程内 spawn / fork，再说明实验性 Agent Teams 和外部委派的区别。

阅读版本：`571902028a75c64c1d767f4ae5fd099485f0ddf0`。以下基于本地源码与文档；没有启动 Harness、执行行为测试或调用模型。配置摘录、已有测试与自拟例子分别标明。

## 1. 是什么：复用单会话执行机制，增加协作管理

**本地子 Agent 不是另一套执行引擎，而是普通 Agent 实例，加上父子关系、委派配置和子任务管理。**

### 1.1 先分清角色、会话、实例与活动

| 概念 | 含义 | 不能等同于 |
|---|---|---|
| profile / Agent preset | profile 装配应用；preset 组合角色的提示词、工具等能力 | 已创建的 Agent，或自动执行的协作流程 |
| 用户可见会话 | 前端展示的一次交互，可包含主任务和子任务 | 必然只有一个内部 Session |
| 内部 Session | 一个执行主体的事件、消息与待处理工作记录 | 当前活跃的 JS 对象 |
| Agent 实例 | 默认由 ReactLoopAgent 绑定一个 Session，持有 Inbox、scope、phase | 一个角色的全局单例 |
| Driver 活动 | 同一实例内部的一次 kick 执行链，可以处理多个 turn | Agent 对象的整个生命周期 |
| 子任务 Activation | 管理一次委派的 handle、父子关系、容量名额、结果和释放 | 新的 Driver 或额外执行线程 |

**单 Agent 模式不等于整个服务器只有一个实例。** 两个独立用户会话可以分别有自己的 Agent，且每个会话都不使用子 Agent。

反过来，一个用户会话也可以包含主 Agent 和多个子 Agent。教学示例：

| 用户会话 | 执行主体 | 对应内部 Session |
|---|---|---|
| A | 主 Agent A，汇总答案 | A-main |
| A | 子 Agent A-reader，读取指定文档 | A-reader |
| A | 子 Agent A-checker，核对证据 | A-checker |
| B | 主 Agent B，与 A 无关 | B-main |

这不是要求四个实例始终同时驻留：子任务结算后可以释放运行实例，保存的会话记录仍在。

### 1.2 多个会话怎样隔离

| 架构方案 | 状态归属 | 在本项目中的对应 |
|---|---|---|
| 一个共享执行器服务多个 Session | 队列、取消信号、执行状态必须按会话另行保存 | 可以作为其他系统的设计，但不是当前默认 Agent 实例的组织方式 |
| 多个 Agent 实例分别绑定 Session | 每个实例持有自己的会话状态 | 默认实现；LLM、Tools 等底层服务仍可共享 |

**共用服务和实现，不等于共用 Inbox、取消信号或 Session。** 同一 Session 在不同时间可以由恢复后新建的实例承载，不保证永久使用原对象。

### 1.3 子 Agent、Team 与外部委派

| 机制 | 额外提供什么 | 执行主体 |
|---|---|---|
| 本地 spawn | 创建不带父对话历史的子会话 | 同一默认 Agent 类的新实例 |
| 本地 fork | 用父会话已完成轮次的历史前缀初始化子会话 | 同一默认 Agent 类的新实例；不是共享父日志 |
| Agent Teams | 在可继续子 Agent 上增加具名队友、同伴消息和共享任务板 | 根 Agent 是 Lead，队友仍使用子 Agent 机制 |
| 外部委派 | 用统一入口管理外部后端的一次执行 | 不一定使用本地 Agent、Driver 或 Session 存储 |

Team 是实验性功能；固定“规划员、执行员、审查员”的角色声明也不会自动产生协作。谁参与、何时创建、怎样交接，仍需工具调用或编排逻辑。

## 2. 为什么要做：分开任务上下文，而不是增加对象数量

- **上下文分工**：读取者只需要指定材料，核对者只需要候选结论与证据；不必把所有中间过程塞进主 Agent 的历史。
- **独立推进**：互不依赖的子任务可以分别执行，再由主 Agent 汇总；是否真的并行取决于调度与容量。
- **职责与能力约束**：可以让不同执行主体使用不同工具集合或模型配置，减少不必要的权限与输入。
- **可追踪交付**：明确每个子任务是谁创建、执行了什么、返回给谁、由谁取消与回收。

**不应默认使用多 Agent。** 如果一次工具调用就能完成，增加委派通常只会增加模型调用、消息传递、恢复和验收成本。角色不同也不保证判断独立或答案更正确，必须用任务结果验证收益。

## 3. 怎么做：装配能力，按需创建，复用执行，统一结算

### 3.1 启动服务与创建 Agent 是两个阶段

| 阶段 / 入口 | 实际动作 | 是否创建用户 Agent |
|---|---|---|
| 装配默认 base 与 Team 插件 | 创建 Agent 工厂、LLM / Tools / 子 Agent / Team 服务；注册适配器和监听 | 不因这些服务的装配而创建 |
| 默认 Web server 接到会话创建 / 激活请求 | 创建或恢复对应 Agent 与 Session | 按需创建；并非每条消息都新建 |
| headless 收到具体任务 | 检查任务后创建或恢复主 Agent | 是；这是执行任务，不是启动 server 等待未知请求 |
| 显式配置非空启动 Agent 列表 | 按条目创建或恢复指定会话实例 | 是；实例从创建时就绑定 Session |
| Lead 实际委派任务 | 子 Agent manager 创建队友 | 按需创建；不是加载 Team 就创建全体队友 |

[base 配置](../../projects/deepseek-harness/packages/bundle/base/cordis.patch.yml)中的实际默认值：

```yaml
- id: agent-loop
  name: '@deepseek-ai/dsh-agent-loop'
  config:
    agents: []
```

LLM 服务在启动时提供适配器注册与调用入口，Tools 服务提供注册表和执行管线；这不表示已调用模型、加载本地模型权重或执行工具。Agent 创建后通过自己的 scope 使用这些服务。

**Team 工具还有一次延后注册**：工具插件先监听 agent/created，等某个 Lead / 队友创建后，再把工具安装进该 Agent 的 scope。插件已加载、工具已对某个 Agent 可见、工具已实际执行，是三件事。

### 3.2 实际例子：headless 加 Team 补丁

仓库的 [team-targets 场景](../../projects/deepseek-harness/snapshots/session/team-targets/snapshot.yml)选择 headless profile。按[内置模板](../../projects/deepseek-harness/packages/boot/app-boot/src/profile.ts)，其等价核心配置片段为：

```json
{
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-headless"
      ]
    }
  }
}
```

这不是另一个仓库自带的“team profile”。场景是在现有 profile 上叠加下面的[实际补丁](../../projects/deepseek-harness/snapshots/session/team-targets/cordis.yml)：

```yaml
- id: tool-subagent-control
  disabled: true
- id: tool-subagent-list-agents
  disabled: true
- id: tool-subagent-report
  disabled: true
- id: tool-subagent
  disabled: true
- id: tool-subagent-fork
  disabled: true
- insert:
    - id: agent-team
      name: '@deepseek-ai/dsh-experimental-agent-team'
    - id: tool-agent-team
      name: '@deepseek-ai/dsh-experimental-tool-agent-team'
```

- **是什么**：禁用原有子 Agent 工具，增加 Team 服务和模型可调用的 Team 工具。
- **为什么要做**：提供具名协作与任务板，并避免同名工具冲突。
- **怎么做**：保留 base 的持久化、子 Agent 管理及 spawn / fork 后端，让 Team 调用这些已有能力。
- **为什么这么做**：协作层不必复制创建、恢复和执行机制；代价是需要正确装配依赖与工具作用域。

全新任务启动时，headless 创建一个主 Agent，它就是 Lead；没有额外的“Team Agent”。Lead 调用 spawn_teammate 时才定义队友。例如下列参数是自拟教学示例，不是运行记录：

```json
{
  "name": "checker",
  "description": "核对答案中的文件依据",
  "prompt": "仅使用允许的只读工具，检查给定结论是否有指定文档支持，汇报缺失证据。",
  "context": "fresh"
}
```

这里 description / prompt 表达任务职责，**自然语言中的“只读”不能代替工具授权**。工具参数默认用 fresh 对应 spawn 后端；选择 fork 则用 fork 后端。示例配置并未在启动时静态创建 checker。

证据边界：

- team-targets 的已提交快照只检查名单查询与向自己发送消息的拒绝，不是多个队友成功协作的证明。
- [创建队友测试](../../projects/deepseek-harness/packages/experimental/agent-team/tests/team.spec.ts)确实分别创建 fork-worker 和 fresh-worker；前者释放后再创建后者，验证独立历史、名单及限制，不能据此声称测试证明了三实例同时并行。

### 3.3 主 Agent 与本地子 Agent 共用到哪里

| 机制 | 共用实现 | 子 Agent 额外处理 |
|---|---|---|
| 创建 / 恢复 | registry.create / resume，再进入同一默认工厂 | 入场容量、父身份、子任务描述与创建配置 |
| 运行实例 | ReactLoopAgent、Inbox、scope、Driver、turn / step | 任务由委派方传入，结果由管理层收集 |
| 模型与工具 | 同一套服务接口、请求和执行管线 | 沿用或选择能力配置，施加委派约束 |
| Session / 存储 | 同种日志、投影、单写者和恢复机制 | parentSession、委派深度、descriptor、子任务目录等 |
| 取消 / 释放 | cancel、whenIdle、handle.dispose | 管理一次 Activation 及后代，释放容量并报告结果 |

两条创建路径的共同后半段是：

```text
App entry ------------------> AgentRegistry.create/resume
SubagentManager.materialize -> AgentRegistry.create/resume
                            -> AgentLoop factory
                            -> ReactLoopAgent + Session + scope
```

fork 只在创建时使用父历史前缀；子会话后续写入自己的日志。默认沿用父能力配置也不表示共享可变会话状态。spawn 支持选择独立 Agent preset；fork 和外部后端不支持这一选项。

### 3.4 从一次委派到结束：主流程下钻

- **接收委派与准入**
  - 调用 startActivation，验证父身份、后端能力、深度和容量。
  - 在异步创建 / 冷恢复之前占用容量；不能等实例已启动后才检查上限。
  - Team 另要求只有 Lead 能创建队友，并先持久化 provisioning 名单记录。
- **准备子会话**
  - spawn 不提供父历史种子；fork 提供选定的历史前缀。
  - 固定父子身份、模型 / preset、工作目录与相关委派权限状态。
  - 审批能力已装配时，子任务不能自行发起提权批准；超出范围应报告给父方。
- **共用工厂创建**
  - manager 调用 registry.create；冷恢复走 resume。
  - 创建独立实例与 scope，安装子任务能力和运行上下文，写入 descriptor 等记录。
- **接纳输入并执行**
  - 初始任务进入子 Inbox，由同一套 Driver 机制处理。
  - 创建接口返回接纳凭据与结果 Promise，不是等待全部模型工作完成后才返回。
  - 普通父子消息使用受授权的消息入口；Team 额外允许成员间通信。消息接纳不等于目标已经处理。
- **判断本次活动能否结算**
  - 等待 Agent 空闲，再检查待处理输入、后代与结算期间的新变化。
  - 普通路径不能只看到一次 idle 就回收仍有待处理工作或后代的实例；失败路径有单独收尾分支。
- **保存、回收与交付**
  - 完成最终持久化处理并捕获本次结果，释放 Agent handle、后代资源和容量。
  - parent delivery 向父 Agent 发完成通知；caller delivery 让工作流等待结果，不注入父通知。
  - 输出结果与清理失败是不同事实，不能用“模型有答案”掩盖资源释放失败。

直接实现见 [manager](../../projects/deepseek-harness/packages/subagent/subagent/src/manager.ts) 的 materialize、watchLocalSettlement、finishDisposal、notifySettlement，以及 [Team roster](../../projects/deepseek-harness/packages/experimental/agent-team/src/roster.ts) 的 spawnAdmitted。

### 3.5 Session、运行实例与 Activation 的结束不是一回事

| 情况 | 存储 / 运行行为 | 不能误读成 |
|---|---|---|
| 子 Agent 普通一轮执行结束 | 先检查是否仍有输入或后代需要处理 | 本轮结束必定立即销毁 |
| 本次 Activation 完成结算 | 本地运行实例被释放；启用持久化时历史仍可存在 | 团队名单中的成员也被删除 |
| 对已释放的本地子会话再次发消息 | 在授权、持久化与查询能力具备时，冷恢复新的实例与 Activation | 原 JS 对象再次醒来 |
| 父 Agent 普通 turn 结束 | 不等于父对象 dispose | 自动取消整棵任务树 |
| dispose 一次 Activation | 停止并等待其后代及未完成创建的回滚，再完成释放 | 只 abort 一下就已清理干净 |

LLM / Tools 服务通常比这些实例活得久。Team 的 roster / task 状态记录在 Lead 日志中，各成员收到的消息记录在目标自己的 Session 中。**一个 Team 不是一份被多个 Agent 共同追加的对话数组。**

### 3.6 关键边界与默认限制

| 边界 | 固定版本的行为 / 需要区分的口径 |
|---|---|
| 容量 | maxActiveSubagents 默认 8，按 activation tree 计算；根主 Agent 不占名额，创建中、停止中等尚未释放的活动仍占名额 |
| 深度 | maxDepth 默认 1，供未另设深度的委派工具使用；不是所有直接服务调用都被强制固定为一层 |
| 团队名单 | maxMembers 默认 16，限制累计创建的队友，失败者也计入；不是同时运行 16 个 |
| 超额准入 | 拒绝并报告容量错误，不隐式排队；与模型 token 总预算是不同机制 |
| 文件协作 | Team 共用工作目录；任务板的 writeScopes 是冲突提示，不是文件锁或隔离环境 |
| 外部子任务 | 共用准入、结果和释放接口，但不保证使用本地 Session；当前外部执行不支持本地子会话式的继续与冷恢复 |

不能从容量上限推导出“已有整个任务树的 token 预算”，也不能从不同 scope 推导出“已隔离共享文件的副作用”。

## 4. 为什么这么做：共用执行内核，把委派责任放在外层

| 依据 | 方案选择与收益 | 代价 / 替代方案 |
|---|---|---|
| **原文明确**：[子 Agent 文档](../../projects/deepseek-harness/packages/subagent/subagent/README.md)用一个 manager 管理本地和外部活动 | 统一准入、父子关系、结算与释放 | 两种后端能力不同，不能把统一入口误当相同 Session 语义 |
| **分析**：本地父子复用默认 Agent 与存储实现 | 重试、取消、工具与恢复不必维护两套 | 子任务差异必须通过创建参数、scope 和管理层表达 |
| **原文明确**：[Team 文档](../../projects/deepseek-harness/packages/experimental/agent-team/README.md)把名单 / 任务与目标消息分开记录 | Lead 管团队事实，各成员管理自己的输入 | 不提供新消息的独立持久 outbox 或自动重发去重 |
| **分析**：按需创建并回收运行实例 | 不要求为每个角色永久保留对象，记录仍可恢复 | 需要处理新输入与回收竞争、冷恢复及身份授权 |
| **分析**：不把多个 Agent 都接到同一组可变执行字段 | 隔离队列、取消与执行进度，易于追踪结果归属 | 仍要额外解决共享文件、预算和全局限流 |

固定角色方案也合理，但需要显式编排：“为会话创建哪些角色、输入如何交接、失败是否停止、谁汇总”。仅在 profile 写三个角色名，不足以完成这些设计。

## 5. MVP 与验收：先增加一个可控子任务

### 5.1 给 Coding Agent 的最小扩展任务

**以下是实施建议，不是已经实现或验证的项目状态。**

- **范围**：在既有单 Agent 闭环上增加一个本地 fresh 子任务，限定受控目录只读；先不做 fork、同伴通信、共享写入、外部后端或分布式团队。
- **接口**：启动返回 childId、结果 Promise 与 dispose；每次委派对应独立 Session，复用现有 Agent 工厂和执行机制。
- **初始约束**：只允许一层委派、一个活跃子任务；父任务等待需要的结果再汇总。恢复能力和失败策略在任务卡中明确，不默默降级。
- **交付证据**：提供父子事件、实际工具调用、准入计数、取消 / 清理轨迹和重启后结果；不接受只看最终回答中的“完成”。

### 5.2 把统一验收项落到多 Agent 场景

下表是[统一验收清单](../2026-10-17_03_harness_acceptance_checklist.md)的场景化补充，不另建第二套编号。约束值用于确定性测试，不冒充上游默认值。

| 对应项 | 验证场景 | 可观察标准 |
|---|---|---|
| D01 / D06 | 两个独立会话同时接收输入；取消其中一个 | Inbox、事件和取消不串会话；没有两个执行者同时推进同一实例 |
| D02 / D07 | fresh 子任务完成；之后冷恢复同一子 Session | fresh 不带父历史；恢复仍保留父子关系和子历史，只有一个活跃写者 |
| D05 / D06 | 用 barrier 挂住子任务，再 dispose；重复 dispose | 退出前所需资源不被提前卸载；最终无残留实例 / 后代，名额只释放一次 |
| D06 / D13 | 容量设 1，第一个子任务保持运行，再创建第二个 | 第二个显式被拒；第一个清理完成后才能重新准入，超额请求未启动模型 |
| D09 / D16 | 子任务请求越权读取，或清理阶段抛错 | 实际访问被阻止；失败可归属，不能变成空结果或成功状态 |
| D12 | **后续若实现任务树预算**：余额 100，两子任务各申请 60 | 只能批准一个；容量限制不能代替预算预留 |
| F08 | 子任务读取指定测试文件，主 Agent 基于结果汇总 | 检查真实路径、调用次数、证据内容与无写入副作用，不只断言答案措辞 |
