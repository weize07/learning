# 第 6 站：异常、预算与资源控制

[专题入口](README.md) · 上一站：[保存与恢复](2026-10-17_05_persistence_and_recovery.md) · 下一站：[实现与验收](2026-10-17_07_implementation_and_acceptance.md)

## 1. 是什么：异常恢复、预算限制与资源收尾

三者相互影响但不等价：异常处理决定失败后怎么办；预算控制决定还允许做多少；资源管理保证停止后不留下失去管理的工作。

下文 **Driver 指 ReactLoopAgent 实例内部的一次异步执行活动**，不是独立类实例，也不等于 Agent 对象的整个生命周期；AgentLoop 是创建、恢复和管理实例的服务。

### 1.1 异常及其处理归属

| 情况 | 负责处理的层 | 行为 / 设计要求 |
|---|---|---|
| 配置 / 初始化失败 | 装配与创建者 | 明确失败，清理已获取资源，不开始任务 |
| 模型请求可恢复失败 | Driver 的 request-error 扩展与策略 | 在有限策略允许时重试；每次尝试可追溯 |
| 普通工具失败 | 工具管线与后续 Driver | 形成关联 error result，让后续步骤处理，不自动重做外部动作 |
| 用户取消 | Driver，向模型 / 工具传播 | 停止新增工作，等待可观察的在途工作退出；不是回滚 |
| 工具超时 | 超时包装与具体执行能力 | 发出取消信号；实际终止仍取决于能力是否配合 |
| 关键持久化失败 | 存储与依赖该检查点的调用者 | 不把未可靠记录的状态当成功；依赖性副作用应停止 |
| 非关键遥测失败 | 遥测所有者 | 明确报告并按策略隔离，不能重试整个业务任务 |
| 总预算耗尽 | 拟定的预算执行者 | 不接纳超额新工作，说明停止原因，处理在途额度 |

最后三行是要为自建系统明确的跨模块要求，不宣称已核对上游全部组合。**错误类别、处理动作、影响范围、报告位置必须一起设计。**

## 2. 为什么要做：任务不能无限重试，也不能假装已经停下

- 模型和工具会失败；没有分类策略，就会把取消、越权、临时网络错误都当成同一种重试。
- 每次重试和辅助模型调用都可能消耗资源；仅限制单次请求无法约束长任务。
- 已发送的请求、子进程和排队输入有不同生命周期；只发 cancel 不足以证明执行已结束。
- 错误、超时或未知 usage 被隐藏后，用户既无法判断结果，也无法控制风险和成本。

## 3. 怎么做：分类、计量、执行限制与收尾

### 3.1 请求重试：事实与策略分开

- **记录失败事实**
  - LlmFailure 包含 code、message，以及可选 HTTP status、Retry-After、request ID。
  - 关键设计点：provider 要求等待多久是事实，不是授权无限重试。
- **判断是否重试**
  - 请求恢复层依据错误类别、次数、取消信号和其他恢复处理作决定。
  - 固定版本 normal 默认允许初次之后最多 5 次重试；不代表所有准备 / 中间件错误都走这条路径。
- **等待并开始下一次 attempt**
  - 退避等待可取消；同 step 中开始下一次尝试，不重复接纳用户输入。
  - 关键设计点：失败尝试可能已消耗 token 和费用；“没得到答案”不等于没收费。

**原文差异**：部分 API 文档写了“新 turn 重试”，与当前 Driver 内的循环不一致。本站采用已核对的同 step 行为，具体依据见[第 3 站](2026-10-17_03_loop_and_lifecycle.md)。

**分析**：重试权若同时分散在 SDK、adapter、Driver，实际尝试次数会相乘且难追溯。原文要求一次 adapter 调用对应一次 provider attempt，避免在底层藏一套重试。

### 3.2 区分预算对象

| 限制 / 计量 | 控制对象 | 不能替代什么 |
|---|---|---|
| 请求输入窗口 | 这次能容纳多少上下文 | 全任务累计 token / 费用 |
| maxTokens | 一次模型响应的输出上限 | 总步数、重试次数、全部请求的成本 |
| TokenUsage | 一次调用实际报告的使用量 | 主动拒绝下一次请求的预算逻辑 |
| 工具 timeout | 某次调用的时间 | 一轮任务总时长、进程强制终止 |
| 并发 / 队列上限 | 同时运行与等待的数量 | 总任务花费 |
| 重复工具提醒 | 劝模型改变做法 | 硬性调用次数上限 |

**已核对**：工具超时只覆盖声明了时限的工具，是协作取消；重复调用插件是提醒而不是 veto。**未核对结论**：不能据此断言上游已有或没有完整的任务总预算系统。

### 3.3 最小预算方案（我们的设计建议）

- **定义额度**
  - 明确作用域：request、turn、整个 task，还是用户配额；恢复 / 重试不能随意重置。
  - 明确口径：token、费用估算、请求数、时间分别计量，不混成一个意义不明的数。
- **接纳前预留**
  - 将“已花费 + 在途预留 + 本次所需”与上限比较。
  - 并发申请必须由同一所有者原子判断，否则两个请求都可能看到同一笔剩余额度。
- **执行后结算**
  - 使用实际 usage 结算，释放未用预留；失败 attempt、压缩和标题等辅助调用也按约定纳入。
  - usage 缺失时保留未知状态并采取明确策略，不默认按零释放。
- **耗尽时收束**
  - 拒绝超额新工作；如要追加模型总结，提前预留总结额度。
  - 已发送请求可能继续计费；本地取消不能撤销 provider 已发生的消耗。

#### 数字例子：并发预留

教学预算总额 100 单位，A 和 B 各需预留 60：

| 时点 | 已结算消耗 | 在途预留 | 可用余额 | 决策 |
|---|---:|---:|---:|---|
| 初始 | 0 | 0 | 100 | 尚无请求 |
| A 获准 | 0 | 60 | 40 | A 可启动 |
| B 同时申请 60 | 0 | 60 | 40 | 拒绝 B |
| A 实际使用 50 后结算 | 50 | 0 | 50 | 释放多余 10 |
| A 的后续尝试再申请 60 | 50 | 0 | 50 | 拒绝，不因 retry 获得新总额 |

这是预算算法示例，不是供应商计费模型。只有预留覆盖真实上界，才能用它讨论严格不超额；估算偏低、价格变化和 usage 延迟都需单独处理。

#### TokenUsage 如何避免重复算

原文口径中 inputTokens 是未缓存输入；cacheReadTokens / cacheWriteTokens 另计。reasoningTokens 若有，是 outputTokens 中的细分，**不能再加一次**。

例如：未缓存输入 40、缓存读 60、缓存写 0、输出 20，其中 reasoning 5，则总 token 为 **120，不是 125**。费用还需按对应价格分类计算，不能把 token 总数当费用。

### 3.4 区分取消、超时与清理结果

| 信号 / 结果 | 意味着什么 |
|---|---|
| cancel / abort 发出 | 已请求停止 |
| timeout 标记 | 某个时间限制已触发 |
| 工作 promise 结算 | 可观察工作已走到约定结束点 |
| dispose 完成 | 所拥有工作与资源已按约定收尾 |

例子：一个子进程收到超时信号后自行退出，exit code 是 0。**超时与 exit 0 可以同时成立**；不能因为 code 为 0 就隐藏超时事实。

**原文明确**：[防御性模式](../../projects/deepseek-harness/docs/defensive-patterns/general.md)要求独立结果分别报告，dispose 等待实际停稳，且运行结束所需的资源和监听必须保留到消费者完成。

### 3.5 队列、所有权与观察者

- **队列有界**：生产速度长期快于消费速度，必须背压或明确拒绝；不能只限制执行并发却让等待队列无限增长。
- **状态单一所有者**：同一 Agent 的推进和预算结算不能被多个不协调的控制器修改。
- **观察与决策分开**：普通观察者异常可隔离并报告；有意传播给调用者的初始化 / 决策错误不能一概吞掉。
- **明确同步点**：用 claim、flush、工作退出等实际边界，不用“延迟一个 microtask 大概就好了”保证正确性。

这些规则共同回答：**故障发生后，谁还能继续，谁必须停止，谁负责最后报告？**

## 4. 为什么这么做：限制要能执行，结果要能解释

| 依据 | 选择理由与代价 |
|---|---|
| **原文明确**：[防御性模式](../../projects/deepseek-harness/docs/defensive-patterns/general.md)要求独立事实分别报告 | 避免 exit 0 隐藏 timeout；调用者需要处理多维结果，而非只看一个成功标志 |
| **原文明确**：dispose 等到实际停稳，必要资源保留到完成 | 避免清理顺序破坏收尾；不配合停止的能力可能让等待变长，需要能力层另定终止机制 |
| **原文明确**：[工具超时](../../projects/deepseek-harness/packages/guard/timeout-policy/README.md)不抛弃下游 promise | 避免后台仍运行却无人管理；代价是不承诺到点立即返回 |
| **我们的预算建议**：统一预留和结算，而不是事后统计 | 并发时能阻止可预见的超额启动；需要可靠计量上界、原子申请和未知用量策略 |

软提醒实现便宜，适合提示模型改进；硬限制必须由程序拒绝新工作。两者可并存，不能用前者证明后者成立。

## 5. MVP 与验收

先实现有限重试、步数上限、总预算口径、有界队列、协作取消、可追踪失败和完整清理。不要先堆熔断、分布式配额等机制。
