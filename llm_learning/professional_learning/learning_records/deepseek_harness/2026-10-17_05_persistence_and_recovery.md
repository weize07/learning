# 第 5 站：持久化与恢复

[专题入口](README.md) · 上一站：[工具执行](2026-10-17_04_tools_and_policy.md) · 下一站：[异常与预算](2026-10-17_06_failures_budgets_resources.md)

## 1. 是什么：可恢复的记录与持久性保证

本篇涉及的 AgentHandle 管理一个活跃 Agent 实例，默认实现类为 ReactLoopAgent；Driver 是实例内部的一次异步执行活动，结束后实例可以仍存在。AgentLoop 则是提供实例创建与恢复能力的服务。恢复历史可构造新实例，不是重新唤醒旧 JS 对象。

| 操作 / 状态 | 能说明什么 | 不能直接说明什么 |
|---|---|---|
| Session 内存 append | 当前进程的日志和视图发生变化 | 重启后还在 |
| 持久化 handle 的 append 成功 | 该后端已接纳、有序，相关读取可观察 | 通用接口下不必然已抗崩溃 |
| flush 成功 | 已确认写入达到持久性屏障 | 外部工具动作与日志形成一个原子事务 |

**先问“哪个 append、完成到哪一层”，再说已保存。**

即使某个后端的 append 本身已落盘，也不能把它的更强实现保证自动归给所有后端。

### 1.1 两种 handle，不要混淆

| handle | 管什么 | 释放意味着什么 |
|---|---|---|
| AgentHandle | 活跃 Agent 及其生命周期 | 停止并等待工作退出，释放 Agent 资源 |
| SessionHandle | 对已存储会话的一条访问通道 | 读通道释放资源；写通道完成待持久工作并释放所有权 |

SessionHandle 支持 read 或 write 访问。相同会话已有写入者时，新的 write open 被拒绝，而不是两个执行者同时追加和修复。

## 2. 为什么要做：进程结束不应抹掉任务事实

- 长任务会遇到崩溃、重启和重新打开；只有内存状态就无法解释此前做过什么。
- 两个写入者若同时执行和修复，可能产生冲突记录；必须保护写入所有权。
- 操作已经发生、日志却没保存时，盲目继续或重做都有风险；恢复需要表达“不知道”。

## 3. 怎么做：保存、打开、修复与继续

### 3.1 从事件到磁盘

- **事件产生**
  - Session 同步通知已追加事件，挂载的持久化路径接收它们。
  - 关键设计点：同步通知不表示同步磁盘写入，也不应让每条 UI chunk 都变成一次写盘。
- **有界批量写入**
  - 事件进入写后缓冲，在批处理窗口或显式触发时送入 handle。
  - 关键设计点：批量可以降低写入开销，但形成“内存已看到、尚未可靠保存”的区间。
- **关键位置 flush**
  - 显式 flush 等待缓冲和写入收束，向调用者暴露失败。
  - 关键设计点：需要依赖记录继续操作的地方，必须等待这个保证；不能仅看后台写入已启动。
- **关闭**
  - 结束时排空待写入工作，再关闭 handle。
  - 关键设计点：清理流程必须仍能使用存储，不能先释放后端再说“最后 flush 一下”。

后台写入失败需可见；项目文档描述其保留事件顺序、暂停自动路径，由显式 flush 再尝试并向调用者报告仍存在的失败。不是静默丢掉失败批次。

### 3.2 恢复记录，不是恢复程序栈

- **打开有效记录**
  - 后端返回物理上有效的连续日志前缀，不返回半条撕裂记录。
  - 关键设计点：损坏的物理尾片段与合法但没有结束的 turn 是两种问题。
- **识别中断**
  - 有 turn/start、缺 turn/end，表示执行没有留下完整结算。
  - 关键设计点：不把整个 turn 删掉，长任务里此前可能已有大量有效结果。
- **补齐中断结算**
  - Agent resume 在写所有权下补缺失工具错误、未关闭 step 和 interrupted turn end。
  - 只读观察者可在内存构造平衡视图，不把修复写回。
  - 关键设计点：补缺失错误表示“不知道完整结果”，不是证明外部动作没执行。
- **继续新工作**
  - 用恢复后的 Session 和适当状态创建活跃 Agent，再接收后续输入。
  - 关键设计点：不会凭日志恢复原来的线程、网络连接或进程指令位置。

### 3.3 用崩溃例子检查副作用边界

考虑一个**超出只读 MVP 的假设工具**：创建一条远程工单。

| 崩溃位置 | 日志知道什么 | 恢复时的风险 |
|---|---|---|
| 工具尚未发起 | 可能只有调用意图 | 需确认是否真的未发送 |
| 远程服务已创建，结果未回到本机 | 没有成功结果 | 重新执行可能创建第二条 |
| 结果已到内存，但未 flush | 本次进程知道，重启后可能不知道 | 同样可能重复 |
| 结果已可靠记录 | 有可恢复证据 | 仍需遵守外部系统的有效性规则 |

**分析**：本地日志与远程服务不是同一事务。幂等键、查询核对或人工介入是单独的业务设计，checkpoint 本身不提供 exactly-once。

只读工具一般副作用风险较低，但重新读取也可能得到已变化的内容。恢复时不能伪装成“当时的同一结果”。

### 3.4 格式不兼容与数据损坏分开

| 情况 | 应表达什么 |
|---|---|
| 当前软件看不懂未来格式 | 明确拒绝解释，保留原数据 |
| 支持的旧格式 | 按声明的迁移路径转为当前逻辑值 |
| 物理数据损坏 | 与“不支持版本”区分报告 |
| 有更新一代但不可读，同时存在较旧可读代 | 不能偷偷退回旧代假装完整恢复 |

**原文明确**：格式迁移保留历史原件；只读打开不发布新一代，写打开在所有权下发布验证后的当前代。MVP 不必实现全套历史迁移，但必须诚实拒绝不支持的格式。

## 4. 为什么这么做：把存储、恢复和外部操作的责任分开

| 原文明确的理由 / 规则 | 本文分析：代价与替代方案 |
|---|---|
| [持久化文档](../../projects/deepseek-harness/docs/subsystems/persistence.md)把 handle 作为访问与写入所有权的统一入口 | 减少执行与修复竞争；代价是要处理生命周期、租约和关闭失败 |
| 原文说明长 turn 可包含大量已可靠保存的事实，不能因未结算就整轮截掉 | 保留有效前缀并标记中断比删除简单，但读取者要理解中断状态 |
| 原文区分 append 与 flush，并允许批量写入 | 每事件同步落盘更直观但成本高；批量写提高效率，却要求关键位置显式等待持久性 |
| 原文保留历史格式原件，不静默退回较旧代 | 保持证据和可诊断性；代价是版本管理、磁盘占用及显式拒绝 |

外部副作用不属于本地日志的事务，故不能仅靠这些机制承诺 exactly-once；需要业务层幂等或核对方案。

## 5. MVP 与验收

- 先实现一种存储、一个明确 flush 屏障、单写者、错误可见和中断状态。
- 不先做复杂压缩存储、跨版本链或云后端；但不能省略未知结果的处理。
- F06 检查恢复历史；D03 检查不盲目重做；D15 检查不兼容数据不被破坏；D16 检查关键保存失败阻止依赖它的后续动作。见[统一清单](../2026-10-17_03_harness_acceptance_checklist.md)。
