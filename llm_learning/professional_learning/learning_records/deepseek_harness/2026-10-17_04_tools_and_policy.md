# 第 4 站：工具执行与权限边界

[专题入口](README.md) · 上一站：[执行循环](2026-10-17_03_loop_and_lifecycle.md) · 下一站：[持久化与恢复](2026-10-17_05_persistence_and_recovery.md)

## 1. 是什么：带输入、输出与执行规则的能力

一个工具至少有三面：

| 面向谁 | 内容 | 作用 |
|---|---|---|
| 模型 | 名称、描述、参数 schema | 让模型提出结构化调用 |
| 执行系统 | execute、输出定义、并发分类、时限 | 让程序知道怎样调用和管理结果 |
| 策略 / 交付系统 | 授权检查、结果处理、可选展示元数据 | 决定能否执行、用户看见什么 |

模型看到的 schema 不包含 execute 回调、超时时限等宿主字段。**模型能生成合法参数，不代表它获准执行。**

### 1.1 四个数据对象

- **ToolDefinition**：已注册工具的定义，包括输入描述、规范输出和 execute。
- **ToolExecution**：本次调用的身份、参数、agent、signal；不是一份可随意改写的定义。
- **规范值 value**：工具主体返回的结构化 JSON 数据，受 output schema 约束。
- **模型内容 content**：由规范值渲染成内容块，经策略处理后进入 tool result。

## 2. 为什么要做：模型建议可能无效、越权或执行失败

- 模型生成参数不可靠，需要校验；参数合法也可能越权，需要授权。
- 工具会失败、超时或被取消，需要明确结果和停止机制，而不是一律返回字符串。
- 多种工具共用审批、计量与展示需求；这些行为若散落各处，容易漏检或不一致。

## 3. 怎么做：从调用建议到关联结果

### 3.1 五个执行子流程

- **登记调用**
  - Driver（即 ReactLoopAgent 实例内部的一次异步执行活动，不是独立类实例）从已结算的 assistant message 取得 tool-call；按 callId 记录与调度。
  - 关键设计点：未完成、失败的流片段不直接执行；并发安全与操作授权是两项不同判断。
- **前置策略和最终守卫**
  - `tools/pre-execute` 可允许、拒绝或请求审批；通过后仍须经过单调 guard。
  - 关键设计点：可重排的扩展策略适合组合；关键拒绝不能被后续插件轻易改回允许。
- **围绕实际执行施加控制**
  - `tools/execute` 包装超时、计量等处理，然后执行工具主体和实际 provider。
  - 关键设计点：调用身份和参数保持受保护；包装器可替换并恢复 signal，而不是借机偷偷更换目标操作。
- **形成并处理结果**
  - 工具返回规范值，经校验、快照、渲染 / 内容投影；post-execute 可按约定替换或阻止结果。
  - 关键设计点：正常结果路径和流水线异常路径不必经过完全相同的回调；异常也要收敛成可解释的结果。
- **最终约束、观察与记录**
  - 定义拥有的 finalizeContent 处理最终内容约束；tools/result 观察不可变结果；Driver 记录关联的 tool/result。
  - 关键设计点：观察者不再任意改结果；最终记录应是交给模型的权威结果，而不是某个中间值。

这是一条正常路径的结构摘要，不要求现在背所有回调。**先掌握前置授权、实际执行、结果结算三个位置。**

### 3.2 状态 → 动作

| 情况 | 程序怎样做 | 不能怎样做 |
|---|---|---|
| 参数通过 schema，但目标不在授权范围 | 策略拒绝，不进入受保护操作 | 因参数合法就允许 |
| 策略要求审批，但审批缺失 / 拒绝 / 取消 | 不执行，形成拒绝结果 | 默认批准 |
| 使用 defineTool，参数不满足已声明 schema | 在主体执行前拒绝 | 把无效参数交给主体赌它能处理 |
| 主体抛错、规范输出无效或渲染失败 | 按管线规则形成 isError | 拼一个看似成功的默认结果 |
| 调用超时，但主体不响应取消 | 等待与报告未退出状态，能力层负责终止机制 | 宣称工具已被强杀或资源已释放 |

直接注册原始 JSON Schema 的工具不能假定享有 defineTool 的全部参数校验；DSL 表达不了的跨字段或业务约束也需另查。

### 3.3 一个 read_doc 例子

教学工具只允许读取 `C:\mvp-fixture` 中的文件：

- **输入定义**：path 是必填字符串。
- **权限规则**：检查实际目标是否在允许范围；不能只用文本前缀判断，也不能忽略链接跳转。
- **执行**：将 signal 传给实际读取操作。
- **规范值**：可返回 path、text、是否截断等结构化信息。
- **模型内容**：渲染可用正文；如果截断，要明确标记，不能假装已读取全文。
- **失败**：文件不存在、无权限、取消分别可辨认，不混成“空文件”。

这是 **MVP 建议**，不是上游 read 工具的完整字段或安全实现。真实路径检查需结合具体文件系统、链接与并发修改风险验证，不能把以上几行当成隔离证明。

## 4. 为什么这么做：共用策略、固定身份、分离结果与表达

| 原文明确 | 分析 |
|---|---|
| [工具参考](../../projects/deepseek-harness/docs/subsystems/tools.md)只向模型暴露允许的 schema 字段 | 执行策略不依靠模型自己遵守；但工具定义需要维护宿主与模型两种视图 |
| [流水线说明](../../projects/deepseek-harness/docs/tool-execution-pipeline.md)让 hooks 跨工具系列工作，避免每个工具耦合某个策略服务 | 共用检查不必复制；代价是策略顺序和短路语义成为设计的一部分 |
| [工具编写规则](../../projects/deepseek-harness/docs/cookbook/adding-a-tool.md)要求返回规范值，并通过渲染提供内容 | 机器消费与人类解释可分离；但必须避免二者不一致或只脱敏其中一面 |

MVP 可以先只有一层授权、一层执行和一种结果转换。**复杂管线可以减，授权不能减，错误归属不能含糊。**

### 4.1 为什么 value 和 content 分开

- 程序需要 `{"count": 3}`，不应从“找到了三个文件”中反向解析数字。
- 模型和界面可能需要不同表达，但应来源于同一结果。
- 代价是两种输出面都要检查：仅隐藏文本，不等于规范值已被保密。

替代方案是每个工具自己完成校验、授权、超时和展示。少量工具时直观，但工具增多后容易出现漏检和规则分歧；共用管线则要承担顺序和扩展点设计的成本。

## 5. MVP 与验收

- F02：一次工具调用对应同 callId 的结果，正确进入下一次请求。
- F07 / D09：绕过 UI 直接调用工具仍不能越权；拒绝时执行体调用次数为零。
- D03：结果有成功、失败或跳过，不靠自然语言猜状态。
- D06：声明并发安全才允许重叠；exclusive 调用不与其他调用同时执行。
