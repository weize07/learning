# Agent 主干 15：训练数据与学习目标

[主学习索引](../index-2026-10-08.md) · 上一课：[指标、可观测性与上线](2026-10-19_06_agent_metrics_observability_and_rollout.md) · [每日概览](topics_by_date.md)

学习日期：2026-10-19。本课把已经能评测、能定位的行为问题连接到训练，重点是 **轨迹怎样变成数据、哪些输出参与学习、怎样验证训练收益**。不重复完整的 SFT / DPO / PPO / GRPO 推导，不下载权重、不启动训练，也不恢复此前暂停的 SFT 实验。

## 1. 先判断：这个错误真的应该靠训练解决吗？

沿用上一课的任务 T42：草稿正确，用户拒绝发送，但模型仍提出发送调用，幸好被策略拦住。

不能直接得出“增加一批拒绝发送的数据，微调一下”。先看模型当时实际收到的输入：

| 观察到的原因 | 优先处理什么 | 为什么不先训练 |
---|---|---|
| 用户拒绝没有进入模型 request | Harness 的消息接纳、上下文构造或恢复 | 模型根本没有拿到必要信息 |
| 工具说明含糊，Skill 与权限说明冲突 | 工具契约、prompt、Skill 内容与加载方式 | 先消除输入矛盾 |
| 缺少报告事实、工具无法查询真实状态 | 检索、数据与工具能力 | 不应让模型靠记忆猜动态事实 |
| 工具返回超时，程序却当作成功 | 工具适配、错误语义和状态处理 | 权重更新不能修复确定性程序错误 |
| 输入完整、契约清楚，仍反复选错动作 | 先建立提示基线，再评估行为训练 | 此时才有明确的可学习差距 |

**训练通常改变模型参数或适配器；不会自动修复数据库、权限检查或消息队列。** 即使训练显著减少违规调用，执行时的硬权限也不能删除。

训练是否值得做，需要同时具备三项条件：

1. 在独立任务上观察到了稳定的行为问题，不是只有一个偶发坏例。
2. 有可信示范、可判定偏好或可靠环境反馈。
3. 能与“不训练，只改 Harness / Skills”的方案比较质量、成本和维护代价。

## 2. 从执行记录到训练数据：不是把日志文件直接喂给模型

### 2.1 先切出一个真实决策点

T42 可以分成：

```text
Verified draft exists
  -> Agent requests approval
  -> User denies
  -> Model requests sending
  -> Policy blocks the request
  -> Agent continues
```

我们想改善的是“收到拒绝后下一步怎么做”。因此先固定这一时刻：

| 部分 | 本例是什么 |
---|---|
| 当时可见的输入 | 任务要求、草稿状态、工具定义、申请记录、用户拒绝 |
| 原来的错误输出 | 请求发送 |
| 想学习的输出 | 保留草稿、不发送、如实回复 |
| 后来才发生的事 | 策略拦截、最终判分、后续修复 |

**后来的拦截与判分可用于筛选、标注，但不能倒灌到这一步的输入。** 否则训练时模型能“提前看见答案”，真实运行时却没有这些信息。

也不能只拿最终 Session 日志当作每一步实际输入：当时可能有不同的工具集合、已加载 Skill、摘要、截断或上下文压缩。应恢复或保存对应的真实 request 视图。

### 2.2 哪些记录可以留下，留下后怎么用？

| 数据 | 用法 |
---|---|
| 经验证的成功行为 | SFT 示范候选；仍需检查中间步骤是否有问题 |
| 明确失败的行为 | 偏好中的较差候选、错误分析或回归用例，不直接当正确示范 |
| 失败后正确恢复 | 可把失败历史作为输入，学习其后的正确处理 |
| 人工或教师模型修正的行为 | 需要重新验证，不能因为来自教师就自动视为正确 |
| 环境错误、日志缺失、状态无法核实 | 隔离标记；未澄清前不能伪装成完整成功数据 |

例如，“读取失败 → 有界重试 → 成功核验”可以是有价值的恢复示范。模型需要学的是面对真实错误如何处理，不是生成一段看起来成功的工具返回。

如果把错误发送动作改成“不发送”，后续环境状态可能也变了。**不能只替换一句 assistant 输出，却保留原路径中不再成立的工具结果。** 应从相应状态重新验证修正后的分支；涉及副作用时只在获准的隔离 / 模拟环境中进行。

### 2.3 数据整理的完整顺序

```text
Authorized execution records
  -> Recover the model-visible context
  -> Verify outcomes and action validity
  -> Group related tasks and remove duplicates
  -> Split train / development / held-out evaluation
  -> Build examples for the chosen objective
  -> Apply the model's chat template and token masks
  -> Train
  -> Evaluate in the same controlled agent environment
```

数据旁边保留来源、任务族、模型与 Harness 配置、工具 / Skill 版本、环境和判分版本。这些是溯源元数据，**不是默认全部拼进模型 prompt**。

只有获得允许的数据才能用于训练。调试日志的保留权限不自动包含训练或对外上传权限；凭据、个人信息与敏感业务内容要按既定规则排除或处理。脱敏还要保持 ID、引用和工具结果之间的一致性。

## 3. 三种学习目标：模仿正确行为、比较好坏、根据执行反馈改进

### 3.1 SFT：给定这些输入，应该输出什么？

SFT 的目标仍是学习示范输出。在 Agent 中，示范不只有最终回答，还可以是：

- 正确的工具选择与参数。
- 需要澄清时的提问。
- 面对工具错误的下一步动作。
- 证据不足时的诚实说明。
- 收到拒绝后的停止与答复。

下面是一个**简化的教学标注记录**：测试现场已准备好草稿，只练习申请与拒绝后的决策。它不是从 T42 原始日志直接导出的数据，也不是可以原样交给任意 trainer 的通用格式。

```json
{
  "sampleId": "deny-send-001",
  "taskFamily": "weekly-report-17",
  "messages": [
    {
      "role": "system",
      "content": "发送须获得用户对当前草稿和收件人的明确批准。"
    },
    {
      "role": "user",
      "content": "草稿 draft-17 已准备好，请询问我是否发送给 lead@example.test。"
    },
    {
      "role": "assistant",
      "content": "是否允许发送 draft-17 给 lead@example.test？"
    },
    {
      "role": "user",
      "content": "不同意发送，保留草稿。"
    },
    {
      "role": "assistant",
      "content": "好的，保留草稿，不会发送。"
    }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "send_mail",
        "description": "发送指定草稿；执行时仍检查批准。",
        "parameters": {
          "type": "object",
          "properties": {
            "draftId": { "type": "string" },
            "recipient": { "type": "string" }
          },
          "required": ["draftId", "recipient"]
        }
      }
    }
  ],
  "targetMessageIndexes": [4]
}
```

`targetMessageIndexes` 是本例自定义的标注字段，编号从 0 开始：**只把最后一条 assistant 回复作为本样本的监督目标**。工具虽然可见，正确行为仍然是不调用它。

转换时可以将前四条作为 prompt，最后一条作为 completion，再使用模型兼容的工具与聊天序列化方式。元数据和自定义标注要由预处理代码解释，不能期待 trainer 自动理解。

#### 哪些 token 参与损失？

先明确本课采用“只监督要学习的 assistant 输出”的设计，而不是宣称所有训练默认如此：

| 内容 | 本设计中的作用 |
---|---|
| system / user / 工具定义 / 已加载指令 | 条件输入，不要求模型模仿生成 |
| 历史 assistant 消息 | 本决策点的上下文；上例不监督那条历史申请 |
| 当前选定的 assistant 回复或工具调用 | 监督目标；工具名、参数及协议相关生成 token 也需要正确处理 |
| 环境返回的 tool / observation | 后续决策的条件输入，不当作模型应该编造的输出 |
| 未来的 observation、最终 grader 答案 | 不得出现在尚未发生的决策输入中 |

Loss mask 是“哪些目标 token 计算训练损失”，不是 causal attention mask。工具结果不计入自身的生成目标，仍然可以被模型读取，影响后面的 assistant 输出。

若训练一整段多轮轨迹，可以监督其中多个经过选择的 assistant 片段；不是必须每次只学最后一句。但**错误动作不能因 role 也是 assistant，就被自动当成正确标签**。

因此必须抽查序列化后的 tokens 与 labels：

- 工具结果和用户消息是否被误标为生成目标。
- 工具调用与结束标记是否正确保留。
- 截断是否删掉用户拒绝、工具定义或关键 observation。
- 历史坏动作是否被不加区分地计入监督。

“使用了 assistant-only loss”不等于这些问题都已解决。具体 mask 依赖数据格式、聊天模板与 trainer 支持；上例只学最后一步，也不同于学习所有 assistant 消息。

### 3.2 DPO：在同一个输入下，哪种输出更好？

用上例最后一条回复之前的**相同上下文与工具定义**，构造偏好：

| 部分 | 内容 |
---|---|
| 共同输入 | 草稿已准备、发送需要批准、用户明确拒绝 |
| chosen | “保留草稿，不会发送。” |
| rejected | 对同一草稿和收件人发起 `send_mail` 调用 |

标准 DPO 学习的是 chosen 相对 rejected、相对于参考策略的条件概率优势，不是另训练一个“好坏分类器”来替代 Agent。工具调用也要按模型支持的 assistant 输出格式序列化，不能随意变成另一种日志字符串。

**不能把“用户批准后的发送”与“用户拒绝后的不发送”直接凑成同一偏好对。** 两者输入条件不同，而且都可能正确。

对 Agent，先做“同一状态下的一步动作 / 回复偏好”通常更容易核实。整条多轮轨迹的偏好训练还要明确：

- 两条轨迹是否从相同任务与初始状态开始。
- 各自 observation 是否由各自动作真实产生。
- 哪些 token 是策略输出，哪些是环境输入。
- 怎样处理不同长度、多个决策以及概率聚合。

不能假定普通的两段文本 DPO 配置，会自动正确处理任意多轮工具轨迹。标准 DPO 的原理回看[既有 DPO 教材](2026-10-10_09_dpo.md)。

### 3.3 PPO / GRPO 类环境训练：先尝试，再根据结果学习

与固定示范不同，这类训练可让当前策略在可重置的环境中生成新的尝试：

```text
Task and reset environment
  -> Model generates an action
  -> Harness executes or rejects it
  -> Environment returns an observation
  -> Model continues
  -> Independent grader assigns feedback
  -> Update model policy
  -> Generate new trials
```

这里一次完整尝试叫 rollout。模型生成动作，环境产生 observation；**数据库和工具结果不是由策略梯度直接“学着生成”的业务事实**。参数更新主要针对选定的模型策略输出，环境仍按自己的规则运行。

- **PPO**：利用优势估计等信号更新策略；常见实现另学习价值估计。细节见 [PPO 教材](2026-10-10_08_ppo.md)。
- **GRPO**：对同一任务输入生成一组候选，用组内相对表现构造学习信号；不代表让多个 Agent 开会。细节见 [GRPO 教材](2026-10-11_01_grpo.md)。

工具型 Agent 的 rollout 还需真实接入多步执行、环境 reset、预算和动作 token 标记。一个普通文本训练脚本不会因为提供了工具名称，就自动拥有这些能力。

### 3.4 Reward 应该奖励什么？

对“生成草稿、申请发送、用户拒绝”这道固定任务，可以先用严格判分构造最简单的结果奖励：

| 同一任务下的 rollout | 教学奖励 |
---|---|
| 草稿正确、申请发生、拒绝后无违规尝试、答复真实 | 1 |
| 草稿正确，但拒绝后仍尝试发送，随后被拦住 | 0 |
| 没有生成草稿，只说“我不会发送” | 0 |

**防线拦住错误是系统保护成功，不表示错误动作应该得到正奖励。** 其他任务要使用各自的成功条件：用户批准时正确发送也应受到正向评价，不能把所有任务都训练成拒绝执行。

只有最终 0 / 1 奖励时，很难知道长轨迹中具体哪一步贡献了成功或失败，这就是信用分配问题。过程奖励可以增加检查点，但也会带来额外标注成本与偏差。

几个常见陷阱：

- 只奖励答案中出现“完成”：模型可能学会说完成，而不做事。
- 只奖励没有违规：模型可能什么都不做。
- 只奖励工具调用次数少：模型可能跳过必要核验。
- 把费用扣分设得过重：省钱掩盖了任务失败。
- 让 Agent 可修改 grader、测试结果或奖励文件：可能直接操纵评分。

奖励和执行约束应分开。再大的违规扣分，也不能替代运行时权限。GRPO 同组结果全部一样时也缺乏区分信号，不应把“产生了更多 rollout”当作已经学到有效行为。

## 4. 为什么训练 loss 下降，Agent 却可能没变好？

### 4.1 模仿日志，不等于学会可执行行为

SFT 可以在给定的历史上学得很好，但推理时要使用自己生成的动作。一个错误动作带来新的 observation，后续上下文就偏离训练示范。

因此需要在执行环境中评测，而不只看离线 token loss；恢复数据也有价值，因为真实运行不会永远沿着完美轨迹前进。

训练只包含“用户拒绝”还可能造成过度拒绝。数据应覆盖批准、拒绝、缺资料、工具失败、恢复、正常完成等不同状态，并保留明确的条件差异。

### 4.2 划分与权重会悄悄改变实验结论

- 同一任务的重复运行、改写和切出的多个决策点放在同一数据划分中，避免训练和评测共享几乎相同的前缀。
- 尽量按项目、来源、任务模板等分组，不只随机打散行。
- 在划分后做数据增强，并继承原任务组；教师生成的改写也不能跨组泄漏。
- 长轨迹、重复前缀和超长答案可能获得更多 token 权重；采样与损失归一化如何处理，要明确记录。
- 用开发集修正数据；保留独立评测集，不反复看答案后还宣称是未知任务测试。

一条任务最终成功，也不意味着中间每一步都是最好的示范。反复无效查询、被拦截的错误动作和偶然猜中，都需要单独检查。

### 4.3 模型、格式与运行环境必须匹配

训练时见过工具调用，不代表换一个工具 schema 后仍能正确调用。至少固定并记录：

- 模型、tokenizer、聊天模板和工具调用序列化。
- 可见的工具定义、关键 Skill 与系统约束。
- 训练数据版本、样本来源和监督 / 奖励口径。
- 推理时的 Harness、工具与环境版本。

数据中的临时路径、旧工具名或过期业务规则，可能变成错误习惯。动态事实仍应在运行时通过检索和工具取得，不应依赖微调来永久记住。

LoRA 与这些目标不是并列选项：它主要回答“哪些参数、怎样更新”，SFT / DPO / RL 回答“根据什么信号学习”。可回看 [LoRA / QLoRA](2026-10-10_02_lora_qlora.md)。

## 5. 最小实验：先证明数据与目标有效，再扩大训练

### 5.1 先做不训练的数据验收

以下为待实施检查，本轮没有导出数据或运行 trainer：

| 检查 | 明确的通过条件 |
---|---|
| 时序与可见性 | 当前决策不含未来 observation 或 grader 答案 |
| 工具协议 | 每个保留的结果都能对应正确调用，参数符合对应版本的 schema |
| 标签范围 | 抽查及程序检查确认监督位置与标注一致，错误动作不被误作正例 |
| 数据划分 | 同一任务族及其衍生样本不跨 train / dev / held-out 集 |
| 状态一致性 | 修改动作后的轨迹经过重新核验，不复用不再成立的环境结果 |
| 偏好对 | 相同条件下比较，chosen 的质量有证据，不仅是更长或更像参考措辞 |
| 奖励 | 假完成、消极不做事、违规被拦截均不能骗过当前任务的严格判分 |
| 来源与权限 | 每条入选数据可追溯，并满足使用与敏感信息处理要求 |

标注和数据检查通过，也不等于真实模型已经受益。

### 5.2 训练实验至少保留这些对照

| 方案 | 用来回答什么 |
---|---|
| A：原模型 + 原 Harness / Skills | 原始基线是什么 |
| B：原模型 + 改进的 Harness / Skills | 不训练能解决多少问题 |
| C：SFT 模型 + 与 B 相同的运行系统 | 训练是否带来额外收益 |
| D（按需）：继续做偏好或环境训练，保持其他条件一致 | 进一步优化是否值得其成本 |

如果 B 同时改了多个组件，只能先归因于这组改进，不能认定某个组件单独贡献了全部收益。D 不是必做阶段，也不存在每个项目都必须走完 SFT → DPO → RL 的规则。

固定任务集、初始状态、授权、预算和 grader，比较：

- 严格任务成功率，而不只是训练 loss 或奖励均值。
- 违规尝试、过度拒绝、工具参数错误与恢复行为。
- 未见项目 / 模板上的表现，以及其他能力是否退化。
- 推理成本、延迟，加上数据制作、验证与训练投入。

**本课的完成标准不是“得到一个新权重文件”，而是能用独立证据说明：哪个行为改善了、哪些边界没退化、相对不训练方案是否值得。**

- [TRL GRPO Trainer](https://huggingface.co/docs/trl/grpo_trainer)：在线采样、组内反馈与训练机制。

官方文档用于核对机制，不表示所有 trainer 都自动正确处理任意 Agent 轨迹。实际实施需固定依赖版本，检查预处理后的 token / mask 与执行集成；本章没有采用其示例脚本开展训练。

</details>
