## 1. 这一轮怎样练

你负责的不是记住框架 API，而是提出一个**别人能实现、你能验收**的方案。

| 步骤 | 你负责 | 我负责 |
|---|---|---|
| 设计 | 根据下面的需求回答三道题，明确接口、数据流和结束条件 | 给出任务约束，不提前提供完整参考实现 |
| 评审 | 解释取舍，确认需要修改的地方 | 指出具体缺口及其影响，不因模块名字不同就判错 |
| 实现 | 确认评审后的方案 | 按方案编写 Python 代码与测试，先检查实际运行环境 |
| 验收 | 阅读运行记录，对照断言判断是否完成 | 提供命令、结果与证据；失败则修复，不只展示一段成功输出 |
| 复盘 | 解释本轮暴露的问题 | 讲评题目，并在本记录补充真实进展与剩余问题 |

本轮先练接口设计、调用时序和边界诊断，不同时安排无关算法题。后续题目根据你的表现调整；不会因为代码由我实现，就默认你已经理解。

## 2. 项目任务：先把只读闭环跑通

最终项目是“读取资料 → 生成周报草稿 → 获得批准后发送”。**本轮只实现第一段：读取两份资料，直接返回带来源的摘要。**

固定用户请求：

> 请读取本周研发和运营资料，说明关闭了多少个缺陷、完成了多少次演练，以及数据库迁移的当前状态。每项注明资料来源，只返回摘要，不发送邮件。

### 2.1 本地测试资料

以下是自拟数据，不读取你的工作文件或企业资料。第一版存放在测试用的内存资料库中。

| 资料 ID | 标题 | 正文 |
|---|---|---|
| `dev-week` | 研发周记 | 本周关闭 8 个缺陷。数据库迁移仍在进行，尚未验收。 |
| `ops-week` | 运营周记 | 本周完成 2 次演练。 |

Agent 只能通过两个工具取得资料：

| 工具 | 能做什么 | 边界 |
|---|---|---|
| `list_documents` | 返回可用资料的 ID 和标题 | 不返回正文；不需要参数 |
| `read_document` | 接收一个 `document_id`，返回对应资料的 ID、标题和正文 | 只接受资料库中的 ID，不接受任意文件路径 |

模型请求调用工具，不等于工具已经执行。执行器只能分派这两个已登记的工具，不能把模型输出当作 Python 代码或 shell 命令执行。

### 2.2 暂时用模拟模型

不下载模型、不接真实 API。用一个**脚本化的模拟模型**代替模型服务：测试预先安排它每次返回“工具调用”还是“最终回答”。

正常测试安排：

1. 第一次模型调用：请求 `list_documents`。
2. 第二次：请求读取 `dev-week`。
3. 第三次：请求读取 `ops-week`。
4. 第四次：返回包含正确事实与来源的摘要。

这里的脚本只固定模型响应，**不能替 loop 执行工具或偷偷补齐消息历史**。模拟模型要检查每次实际收到的请求；否则，即使 loop 从未传回资料，它也可能照脚本输出正确摘要，造成假通过。

这轮证明的是运行程序能否正确传递信息、执行工具并结束，**不是证明真实 LLM 已具备资料理解或自主决策能力**。

### 2.3 固定本轮边界

- 单个 Agent、单次用户任务、串行执行；每次模型响应只包含一个工具调用或一个最终回答，二者互斥。
- 工具结果必须关联到对应调用，进入下一次模型请求；不能只打印在终端。
- 每次运行最多调用模型 **5 次**，产生最终回答的调用也计数；本轮没有自动重试。
- 第 5 次返回最终回答，允许成功结束；第 5 次仍要求调用工具，则明确报预算耗尽，不执行该次工具调用，也不发起第 6 次模型请求。
- 未知工具、无效参数、未知资料和工具执行异常，均明确失败并停止；不能当成空结果或伪造成功摘要。错误如何表达、如何记录，由你设计。
- 收到最终回答后，不再继续调用模型或工具。
- 不做文件写入、邮件发送、审批、持久化恢复、并发、MCP、RAG、Skills、多 Agent 或训练。这里只是划定第一轮范围，不是说这些能力永远不需要。

预算数值 5 和遇错即停是本轮教学约束，不是通用生产配置。

## 3. 你的三道设计题

可以用文字、表格或伪代码回答，不要求先写可运行 Python。没有唯一的类名、文件数或设计模式；不要为了形式把小程序拆成十几个模块。

### 题 1：把需求变成接口

给出一张简图，说明运行循环、模型适配器和工具执行之间怎样连接，再写出关键数据的结构。

至少覆盖：

- 一次模型请求包含什么；工具的名称、说明和参数约束由谁提供。
- 如何明确区分“请求工具”和“最终回答”，而不是靠搜索自然语言里的关键词。
- 一个工具调用怎样与其结果对应。
- 谁持有历史消息和模型调用计数；谁检查输入并真正执行工具。
- 运行结果如何区分成功、执行错误和预算耗尽。

**交付形式：** 一张简图 + 一张接口 / 数据结构表即可。字段、类型和责任必须说清楚，不必拘泥于某家模型 API 的格式。

每一行写清：

|---|---|---|---|---|
| 第一次调用 | 待填写 | 待填写 | 待填写 | 待填写 |
| 第二次调用 | 待填写 | 待填写 | 待填写 | 待填写 |
| 第三次调用 | 待填写 | 待填写 | 待填写 | 待填写 |
| 第四次调用 | 待填写 | 待填写 | 待填写 | 待填写 |

重点解释两个位置：**读取研发资料的结果何时首次对模型可见；第四次模型请求为什么已经具备回答所需的事实。** 不要把测试资料直接预填到第一次请求里，也不要把尚未执行的工具结果提前写入历史。

### 题 3：修正一个会越界的循环

有人提出以下执行顺序：

> 先调用模型；如果模型请求工具就执行；最后检查“模型调用次数是否大于 5”，超过才结束。

请完成：

1. 指出这个顺序违反了哪些本轮约束，包括第 5 次和第 6 次附近的行为。
2. 给出你的检查顺序，保留“第 5 次返回最终回答仍算成功”的行为。
3. 写出至少两条边界测试的具体断言：不能只写“程序应该停止”，要说明模型调用数、工具执行数以及最终状态。

可以用“模型持续请求 `list_documents`”作为故障输入。计数都从一次全新的运行开始，不继承上一次测试的状态。

## 4. 后续实现必须提交的验收证据

下面是待实现检查项，不是已运行的测试结果。

| 用例 | 必须证明什么 |
|---|---|
| 正常闭环 | 调用两种工具、实际读取两份资料；后续模型请求含对应结果；摘要数字准确，迁移不能被写成已验收，三项均有正确来源 |
| 历史时序 | 第一次模型请求没有资料正文；工具结果只在执行后出现，并与调用正确关联；每次模拟模型收到的请求都有断言 |
| 未知工具 | 不分派执行，不生成成功结果，运行留下明确错误 |
| 无效参数 / 未知资料 | 分别测试；无效参数不能到达实际读取逻辑，未知 ID 不能被当成空资料 |
| 工具执行异常 | 失败明确可见并结束，不继续调用模型掩盖错误；错误记录保留可定位的信息 |
| 一直请求工具 | 模型调用不超过 5 次；第 5 次的工具请求不执行；运行以预算耗尽结束 |
| 第 5 次才给最终回答 | 成功接纳最终回答，不能因为计数刚好等于 5 就误判失败 |
| 正常结束后 | 没有额外模型调用或工具执行 |

单看最终摘要不够，因为模拟模型的最终文字是预设的。除了文字检查，还要检查**真实传入适配器的请求、实际工具执行、计数和结束原因**。结构与消息传递测试通过后，接真实模型仍需独立评测。
