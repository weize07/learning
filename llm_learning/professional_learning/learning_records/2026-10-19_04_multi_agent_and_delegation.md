# Agent 主干 12：多 Agent 与委派

[主学习索引](../index-2026-10-08.md) · 上一课：[MCP 与连接器](2026-10-19_03_mcp_and_connectors.md)

**核心：多 Agent 是执行主体之间的分工与交接，不是把同一个问题多问几遍就自动变强。**

本课沿用周报场景，讨论通用设计，不重复 Harness 类名。模式名称在不同框架中可能有不同定义，本文以“谁决定下一步、谁持有任务状态、谁向用户交付”为准。接口、例子和验收均为教学设计，未运行实验。

## 1. 是什么：划分决策权、上下文与责任

### 1.1 先区别工具、模型调用与 Agent

| 形式 | 谁控制下一步 | 例子 |
|---|---|---|
| 普通工具 | 调用方决定；工具按契约执行 | 按文档 ID 读取内容 |
| 一次模型调用 | 外部流程决定何时调用、怎样使用结果 | 固定输入生成一段摘要 |
| 子 Agent | 在授予的范围内选择工具或推进多个步骤，向委派方返回结果 | 自行查找资料、核实里程碑并提交证据 |
| 确定性 workflow | 程序规定主要节点和分支 | 并行读取两份文档 → 固定摘要 → 合并 |

多次模型调用、多线程或多个角色 prompt，都不必然构成多个 Agent。**如果固定流程已经足够，就不必赋予每个节点自主规划能力。**

### 1.2 四种常见组织方式

| 方式 | 控制关系 | 适合解决的问题 | 周报例子 |
|---|---|---|---|
| Router | 选择一个合适处理方；路由后谁交付需明确 | 请求类别不同，各需不同能力 | 判断是研发周报还是销售周报 |
| Supervisor / hierarchical | 主体分派子任务、收集结果并决定后续 | 需要跨任务协调与统一交付 | 主 Agent 分派检索，再汇总成稿 |
| Handoff | 把当前处理权交给另一主体，按契约转交必要状态 | 后续应由另一专业主体继续对话或处理 | 普通支持转交账单处理 |
| Parallel workers | 把可分离任务同时交给多个执行者，再聚合 | 独立证据搜集、多方案探索 | 研发与运营资料分别核查 |

这些不是互斥分类：supervisor 可以并行委派，也可以先路由。hierarchical 只是说明存在层级，不要求树越深越好。

**委派与 handoff 的核心差别**：

- 委派：主 Agent 保留汇总与交付责任，等待子结果后继续。
- handoff：接收方取得当前处理责任；原主体不应同时继续承担同一交付。失败、退回与完成通知必须另有规则。

handoff 是逻辑控制权转移，不意味着转移进程，也不要求共用同一个 Session。

### 1.3 同一角色可以有多个实例

“资料核查员”是能力配置；执行“核查本周研发进展”时创建的对象是运行实例。两个用户各有自己的核查任务，不能因此混用状态或授权。

本地每个实例绑定独立 Session 是一种实现选择；其他系统也可用显式任务状态管理。通用要求是：输入、身份、进度、取消与结果归属明确，不能把共享对话数组当成天然的协作协议。

## 2. 为什么要做：先证明单 Agent 有瓶颈

| 已观察到的瓶颈 | 可能有用的分工 | 也可能更简单的替代 |
|---|---|---|
| 两类资料相互独立，串行等待太长 | 并行检索 / 核查 | 直接并行工具调用 |
| 一份上下文过大，任务边界清晰 | 子任务各自处理局部证据 | 检索、分块、摘要与更好的上下文选择 |
| 不同任务需不同工具或模型 | 按能力路由或委派 | 单 Agent 动态工具集、固定工作流 |
| 草稿经常遗漏证据 | 独立核查阶段 | 程序化检查、规则校验、单模型二次检查 |

多 Agent 的代价包括更多 token、调度等待、上下文交接、结果冲突与恢复状态。核查员也会犯错；多个主体使用相同模型、相同证据时，错误可能高度相关，不能把“大家同意”当作事实验证。

**角色数量不是目标。目标是在允许的成本和延迟下，提高可验证的任务成功率。**

## 3. 怎么做：从一个可控委派开始

### 3.1 周报任务的最小组织

```text
Coordinator
  -> Research worker: collect development evidence
  -> Operations worker: collect operations evidence
  -> Merge supported claims
  -> Verify draft
  -> Request human approval
  -> Send approved report
```

这是 supervisor 加并行分工的教学设计：

- 两个 worker 可以分别搜索、读取与核实资料，返回结构化证据。
- 核查阶段可以先用规则或一次模型调用，不必再建一个常驻 Agent。
- 发送由受控执行路径负责；worker 不因为参与协作就获得发送权。

如果两个 worker 只是读取固定文件并摘要，优先用简单 workflow，而不是引入完整自主循环。

### 3.2 委派任务卡：不只写一句“帮我查一下”

| 字段 | 必须讲清什么 |
|---|---|
| 目标与范围 | 查哪一周、哪个项目、什么算完成 |
| 输入与版本 | 资料标识、快照版本、用户 / 租户范围 |
| 可用能力 | 工具、目录、网络和审批约束；由程序执行，不只写在 prompt |
| 输出契约 | 结论、证据定位、冲突、未完成项和状态 |
| 控制约束 | deadline、预算分配、可否再委派 |
| 生命周期 | 谁等待、谁取消、结果交给谁、失败怎样处理 |

教学任务描述：

> 核查项目 P 本周已完成事项。仅访问本用户获准的项目资料，不发送消息、不修改文件。每条结论附文档 ID、版本和段落定位；证据不足时列出缺口，不把计划当成已完成。使用父任务分配的时间和费用额度。

这个描述帮助模型理解任务，但授权、预算和取消仍需执行系统强制落实。

### 3.3 上下文交接：传够用的信息，不转发全部聊天

- **是什么**：给接收方明确目标、当前事实、证据与约束。
- **为什么要做**：全量复制历史会增加成本、泄露无关信息，还可能把已失效结论带入子任务。
- **怎么做**：
  - 区分用户原始要求、已验证事实、模型假设和不可信资料。
  - 传递资料引用、版本与必要片段；接收方能按权限回查。
  - 发送待核查结论不等于授予认可；核查方应能独立访问原始证据。
  - 带上任务版本；主任务重规划后识别旧子结果，不盲目合并。
- **为什么这么做**：减少上下文污染和过期结果，但需要显式的数据契约与引用管理。

以下为自拟结果片段，不是完整 API：

```json
{
  "taskId": "research-1",
  "taskVersion": 2,
  "status": "partial",
  "claims": [
    {
      "text": "接口迁移已完成。",
      "evidence": [
        {
          "documentId": "doc-17",
          "version": 3,
          "locator": "验收结果，第2段"
        }
      ]
    }
  ],
  "unresolved": ["没有找到生产部署的确认记录。"]
}
```

汇总者还要验证证据是否支持结论；结构化 JSON 合法不代表内容真实。

### 3.4 运行与结算的主流程

- **接收与拆分**
  - 主体识别可独立子任务、依赖和所需能力。
  - 依赖未满足的节点不能提前用猜测结果执行。
- **准入与创建**
  - 原子预留父任务中的预算和容量；传递剩余 deadline。
  - 记录子任务身份、版本与所有者，失败创建也需回滚资源。
- **执行与更新**
  - 子任务推进自己的局部工作，只发布契约允许的状态与结果。
  - 进度消息不等于任务完成；消息送达不等于被处理。
- **收集与验证**
  - 验证版本、来源、输出契约与证据。
  - 对冲突回查原始资料，不靠投票自动消除冲突。
- **收束与交付**
  - 等待需要的子任务；超时后选择明确失败或诚实的部分结果。
  - 回收资源并结算预算；主任务生成草稿，执行批准与发送流程。

**“子任务运行结束”“结果通过验证”“父任务完成”是三个不同状态。**

### 3.5 共享状态：谁能修改什么

| 状态 / 资源 | 推荐的初始约定 |
|---|---|
| 主任务目标与版本 | 主体单一维护；更新后通知受影响子任务 |
| 局部证据与输出 | 子任务各自写入，主流程校验后合并 |
| 共享任务板 | 用版本检查 / CAS 等机制避免覆盖，不靠角色礼让 |
| 最终周报草稿 | 一个汇总写者；并行产生候选段落，不直接同时覆盖成稿 |
| 共享目录 | 分配不重叠产物位置；需要共享写入时另设冲突与提交机制 |
| 发送操作 | 专门执行者持有能力，批准绑定不可变内容与收件人 |

任务板上的“某人负责这个文件”不是文件锁。两个 Agent 有不同 scope，也不表示共享磁盘上的写入已隔离。

### 3.6 失败传播与取消规则

| 情况 | 系统动作 |
|---|---|
| 一个必需子任务失败 | 有界重试、重新分派或终止；不把缺失内容伪装成成功 |
| 可选子任务超时 | 根据预定规则返回带缺口的部分结果，并处理未退出工作 |
| 主任务取消 | 停止新委派，向需要停止的后代传播取消，等待清理 |
| 旧任务的晚到结果 | 按 taskId / taskVersion 识别，不覆盖当前结论 |
| 父方收结果前崩溃 | 通过持久任务与结果记录恢复，不仅依赖内存回调 |
| 副作用结果未知 | 查询或对账；不能因为“换了一个 Agent”就安全重做 |
| handoff 中途失败 | 用明确的状态转移和接管规则恢复，避免两个主体同时交付或无人负责 |

树深、扇出、并发、总调用数和任务树费用分别限制。不能让每个子任务重获一份完整总预算，也不能让父任务占满容量后无限等待无法启动的后代。

### 3.7 业界有没有大幅胜出的著名案例？

**有，最典型的公开生产案例是 Anthropic 的 Claude Research；但“大幅提升”不等于“多 Agent 已成为所有任务的公认最佳实践”。**

[Anthropic 的系统介绍](https://www.anthropic.com/engineering/multi-agent-research-system)说明其采用 lead + 并行研究子 Agent：

| 公开报告 | 正确口径与限制 |
|---|---|
| Opus 4 主体 + Sonnet 4 子 Agent，相对单 Opus 4 的研究内部评测表现提升 90.2% | 厂商报告的相对提升；不是准确率 90.2%，不是提升 90.2 个百分点，也不是同预算架构消融 |
| 复杂查询研究时间最多缩短 90% | 并行子 Agent 与并行工具调用等组合优化，不能全归因于多主体本身 |
| 多 Agent 系统 token 用量约为普通聊天的 15 倍 | 分母是 chats，不是该实验的单 Agent 基线，不能说“比单 Agent 贵 15 倍” |

其优势场景是广度优先的独立探索，例如分别查找多家公司的董事会信息，再由主 Agent 汇总证据。这里不是让几个 Agent 围绕同一段文字反复聊天，而是把可分离的信息搜集任务并行展开。

为什么不能视为普遍证明？模型组合、额外计算、工具策略和上下文分工同时改变；这是有价值的生产案例，但不是独立、等预算、跨行业复现后的统一结论。

再看 [Towards a Science of Scaling Agent Systems，固定 v1](https://arxiv.org/html/2512.08296v1)：论文报告在控制工具、提示与 token 预算的设置下比较 180 种配置，覆盖 3 个模型家族、4 类 agent benchmark。报告中：

- 集中协调在结构化金融推理任务上约有 **81% 相对改善**。
- 顺序规划任务的多 Agent 变体出现约 **39%～70% 的性能下降**。

这些是该论文具体基准与配置的结果，不是生产 SLA、普遍准确率或已确立的行业共识；本课未复现实验。它们说明**任务结构与协调方式决定收益**，而非 Agent 越多越好。

可以形成的工程原则是：**可并行、低耦合、局部上下文清晰、结果可验证的研究 / 探索，值得优先评估多 Agent；强顺序依赖、频繁共享状态的任务，不能照搬。** 先与单 Agent + Skills、并行工具和固定 workflow 比较。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)也建议从最简单可用方案开始，仅在确有收益时增加复杂度。

## 4. 为什么这么做：共享结果，不共享模糊责任

| 选择 | 收益 | 代价 / 替代方案 |
|---|---|---|
| 主体保留交付责任 | 子任务失败或冲突时有明确裁决者 | 汇总主体可能成为延迟与上下文瓶颈 |
| 按证据与任务版本交接 | 便于核查、重规划与恢复 | 需维护引用和状态，摘要不能替代全部证据 |
| 局部结果合并，而非共享可变对话 | 降低状态串扰和并发覆盖 | 必须设计消息及结果契约 |
| 先简单委派，再按需增加层级 | 更容易定位收益与故障 | 不追求一开始覆盖所有组织模式 |
| 核查使用外部事实和程序检查 | 避免模型互相赞同就被当作成功 | 增加工具成本，也可能仍需人工判断 |

有时最好的“多 Agent 优化”是删除一个 Agent，把它改成确定性检查或普通工具。

## 5. MVP 与验收：与同预算单 Agent 比较

### 5.1 最小扩展任务

**实施建议，不是已运行结果**：

- 保留已有单 Agent 周报基线，增加一个只读证据搜集子任务。
- 先做一层委派、固定输出契约、共享总预算和 deadline。
- 暂不做 peer-to-peer 自由讨论、递归组队、共享写入或真实发送。
- 用可控模型替身验证状态与故障，再在获准环境比较真实模型效果。

### 5.2 确定性验收

| 刺激 | 可观察标准 |
---|---|
| 两个用户同时委派 | 输入、证据、权限、结果不串用户 |
| 主任务由 v1 改为 v2，v1 晚到 | v1 不被自动用于当前草稿 |
| 子任务报完成但证据不支持结论 | 校验拒绝或标为待确认，不直接发送 |
| 两结果冲突 | 回查资料并保留未解决冲突，不用多数意见替代事实 |
| 主任务取消，子任务仍在读资料 | 停止后续操作并等待已启动任务收尾；无遗留容量 |
| 子任务上限为 1，再请求一个 | 超额拒绝或进入明确定义的有界等待，不悄悄突破 |
| 子任务结束后汇总失败再恢复 | 保留已验证结果，不无条件重跑，更不重复外部副作用 |

### 5.3 同预算对照怎么做

| 方案 | 目的 |
|---|---|
| 单 Agent 顺序处理 | 建立原始基线 |
| 单 Agent + 并行工具 / 固定 workflow | 排除收益仅来自并行 I/O，而非多主体决策 |
| 多 Agent 委派 | 测试上下文分工与局部自主性是否带来额外收益 |

实验约定：

- 相同任务集、资料快照、授权、成功标准和任务级费用 / 时间上限。
- 先固定模型版本与主要采样配置；若比较异构模型，作为额外变量单独报告。
- 多 Agent 的拆分、沟通、核查、重试及汇总费用全部计入，不能只报 worker 成本。
- 使用独立参考答案、文件状态或执行凭据检查结果；不能由参与协作的模型自评放行。
- 报告成功率、证据支持率、越权与重复副作用、每任务成本、端到端延迟及失败类别。
- 随机任务应重复运行，报告样本量与波动；小样本优势不直接推广。

**同预算指可用上限一致，不要求故意把费用花满。** 如果多 Agent 更贵但更准，应报告质量与成本的取舍，不能称为同成本下必然更强。
