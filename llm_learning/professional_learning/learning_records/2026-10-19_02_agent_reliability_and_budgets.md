# Agent 主干 10：鲁棒性与成本预算

[主学习索引](../index-2026-10-08.md) · 上一课：[安全、权限与人工介入](2026-10-19_01_agent_permissions_and_human_approval.md)

下一课：[MCP 与连接器](2026-10-19_03_mcp_and_connectors.md)。

**核心：可靠性不是“失败就多试几次”，而是让每次继续执行都有依据、有上限、有结果记录。**

沿用上一课：读取资料 → 生成周报 → 用户批准 → 发送。接口与数值均为教学设计，不是某个模型或框架的默认值；本文没有调用模型、发送邮件或执行测试。

## 1. 是什么：控制失败、等待、重复与消耗

### 1.1 先区分六种控制

| 控制 | 解决什么问题 | 不保证什么 |
|---|---|---|
| timeout / deadline | 一次操作或整个任务最多等多久 | 超时不代表远端未执行，也不代表自动停止 |
| retry / backoff | 临时故障后，何时再尝试 | 不能修复权限错误或保证副作用不重复 |
| idempotency（幂等） | 同一逻辑操作被重复提交时，不重复产生业务效果 | 不是简单复用一个字符串就成立 |
| rate limit / concurrency limit | 控制单位时间请求量与同时运行数 | 不限制一个任务累计花费 |
| circuit breaker（熔断） | 下游持续故障时暂时停止继续调用 | 不等于每个任务自己的重试次数 |
| budget | 限制任务累计 token、费用、调用、步数等 | 不能只看单次模型输出上限 |

鲁棒性是这些机制与状态记录的组合，不是一个统一的 retry 开关。

### 1.2 一次重试增加的是 attempt

```text
任务
  -> 一轮处理
    -> 一个模型 step
      -> attempt 1：临时故障
      -> attempt 2：成功
```

重试未必需要新建 turn / step；但**每次实际尝试都要记录，并检查剩余时间与预算**。失败请求也可能已经消耗 token 或产生费用，不能统一按零计费。

## 2. 为什么要做：局部补救可能放大全局故障

- **重复副作用**：发送超时后直接重试，可能给同事发两封周报。
- **重试放大**：客户端、网关和模型适配层都独立重试，各最多尝试 3 次，最坏可能形成 27 次底层调用。
- **等待超支**：每次请求都有 30 秒超时，但连续重试和工具调用让整个任务拖到数分钟。
- **并行超支**：两个子任务都看到余额充足，同时开始，最终总消费超过上限。
- **错误降级**：服务失败时用空文本或旧缓存假装成功，用户得到一份缺失事实的“完整周报”。

因此必须同时看：单次操作、一个任务，以及共享下游服务这三个范围。

## 3. 怎么做：先分类，再决定继续条件

### 3.1 错误到动作的决策表

| 情况 | 默认动作 | 再次执行前的条件 |
|---|---|---|
| 参数不合法 | 返回明确参数错误，必要时让模型修正 | 修正后的参数重新校验、授权；不是原样网络重试 |
| 无权限、用户拒绝 | 停止该操作，报告原因 | 新的有效授权；不能靠循环请求绕过 |
| 临时网络错误、部分 5xx | 有界退避重试 | 错误确属临时性；操作可安全重复；时间与预算仍足够 |
| 429 / 容量不足 | 按服务端建议和本地策略延后或拒绝 | 等待不超过 deadline，且准入容量允许 |
| 模型输出不合契约 | 有界修复、重新生成，或失败 | 计入模型调用预算；先确认是否有已执行副作用 |
| 发送超时、远端是否接受未知 | 查询操作状态或对账 | 有可靠幂等保证才能安全重提；否则保留未知状态 |
| 用户取消 / 任务到期 | 停止启动新工作，传播取消并收尾 | 不自动把取消当瞬时错误重试 |
| 下游持续故障 | 熔断，明确报告不可用或启用获准降级 | 经探测恢复，不让全部请求同时试探 |

“5xx 可以重试”也不是无条件规则：如果服务可能先执行再报错，仍需考虑幂等和结果未知。

### 3.2 让一个明确的层负责重试

- **是什么**：为一次远端操作确定重试所有者，其他层不再无感叠加重试。
- **为什么要做**：每层看似只补救两次，组合后可能显著放大请求和成本。
- **怎么做**：
  - 明确 maxAttempts 包含首次尝试，例如设为 3 就是最多请求 3 次。
  - 使用有上限的指数退避并加入 jitter，避免大量请求同时再次冲击。
  - 服务端要求等待时，按协议处理 Retry-After，并检查是否超过任务剩余时间。
  - 等待阶段也响应取消；每次重试重新检查准入和预算。
- **为什么这么做**：临时故障获得恢复机会，但不会无限消耗或造成同步重试风暴。

教学示意：第 1、2 次失败后的随机等待上界分别为 0.5、1 秒；达到总尝试次数或任务 deadline 就停止，不继续等待。

### 3.3 deadline 是总时间边界，不是重复使用同一个 timeout

假设任务总时限 60 秒，单次模型请求最多 20 秒：

| 已耗时 | 剩余时间 | 新模型请求的等待上限 |
|---|---|---|
| 5 秒 | 55 秒 | 最多 20 秒 |
| 45 秒 | 15 秒 | 最多 15 秒，还需考虑收尾余量 |
| 已到期 | 0 秒 | 不启动 |

应把任务 deadline 向下传播；重试、排队、退避和工具操作都消耗同一时间窗口。业务 deadline 通常不因重启或恢复而重置，进程内计时则宜使用单调时钟衡量经过时间。

**超时后的两项责任要分开：**

1. 停止等待并报告超时。
2. 请求取消实际操作、跟踪仍在执行的工作并清理。

仅用 Promise.race 返回超时，不会自动终止输掉竞争的操作。到期后可以需要额外的有界清理时间，但不能把清理阶段变成新的业务执行机会。

### 3.4 发送只发生一次：幂等与操作记录

**是什么**：同一封已批准周报的重复提交，被后端识别为同一逻辑发送。

**为什么要做**：第一次已经发送，但响应在网络中丢失，调用方无法仅靠异常判断结果。

**怎么做**：

1. 创建稳定的 operationId，绑定当前用户 / 租户、收件人和批准后的不可变内容。
2. 执行前持久化操作记录；重试同一操作复用同一 ID。
3. 由支持幂等的发送服务原子处理同 ID 的并发与重复请求；同 ID 不同内容必须拒绝。
4. 响应丢失时，优先按 ID 查询状态；在明确的幂等有效期与语义内重提。
5. 保存最终凭据；内容改变应成为新操作，并重新检查批准。

**为什么这么做**：去重发生在能控制真实发送效果的边界，而不是只让 Agent “记得别再发”。

如果发送服务不支持幂等，也无法可靠查询，仅靠本地数据库不能消除“已发送但尚未记成功”的崩溃窗口。此时应保留结果未知并对账 / 人工处理，不能承诺 exactly-once。

### 3.5 预算：先预留，再启动，最后结算

| 预算维度 | 计数对象 | 设计要点 |
|---|---|---|
| 模型费用 / token | 每次模型尝试 | 输入、输出、缓存等按服务商实际口径计算 |
| 调用数 | 模型或工具尝试 | 明确是否包含失败、重试与子任务 |
| step 数 | 任务推进次数 | 不替代 attempt 上限，否则一个 step 内可无限重试 |
| 时间 | 整个任务 deadline | 包含等待、排队和退避 |
| 并发容量 | 当前尚未释放的执行活动 | 是资源准入，不是累计消费预算 |

教学示例：总费用预算 100 单位，并行任务 A、B 各需预留 60：

| 动作 | 已结算 | 预留 | 可用 |
|---|---|---|---|
| 初始 | 0 | 0 | 100 |
| A 原子预留 60 | 0 | 60 | 40 |
| B 申请 60 | 0 | 60 | 40；拒绝启动 |
| A 实际花费 50，完成结算 | 50 | 0 | 50 |
| B 再申请 60 | 50 | 0 | 50；仍拒绝 |

关键规则：

- 准入条件是“已结算 + 未结算预留 + 本次预留不超过上限”，检查与预留必须原子完成。
- 子任务与重试计入同一个任务预算；不能每个子 Agent 都重新获得完整总额。
- 取消请求不等于费用为零；费用未知时保留保守占用，等待对账，不立即全部退款。
- 若预留只是估计，实际消费仍可能超过估计。硬上限需要可靠的单次最大费用约束、保守预留或服务端配额支持，不能把事后统计包装成绝对保证。
- 除 token 外，收费工具、搜索、存储等成本也应按业务范围明确是否计入。

### 3.6 限流、熔断与降级放在哪一层

- **限流 / 并发准入**
  - 按 provider、租户等共享范围控制请求；单任务自己限制调用数，不能保护整个下游。
  - 排队要有长度和等待上限，取消后移除等待项；队列满则显式拒绝。
- **熔断**
  - 一段时间故障达到阈值后暂停常规调用，只放行少量恢复探测。
  - 不把参数错误或用户拒绝混进“下游故障”统计，也不在多副本间无约束同时探测。
- **降级**
  - 可以在用户许可和能力要求满足时换模型、缩小任务或返回部分结果。
  - 明确缺失内容、模型变化和证据范围；不能用过期缓存、空值或未经授权的模型供应商静默替代。

## 4. 为什么这么做：同时控制局部恢复和全局消耗

| 选择 | 收益 | 代价 |
|---|---|---|
| 按错误与操作语义决定重试 | 避免无意义重试和重复副作用 | 需要维护明确错误分类，不能只捕获所有异常 |
| 统一 deadline 与重试所有者 | 组合后仍有时间和请求量边界 | 需跨层传递截止时间、attempt 与取消信息 |
| 幂等在副作用后端落实 | 重试不必靠猜测第一次是否执行 | 依赖服务保证；没有保证时必须接受未知状态 |
| 预算先原子预留 | 并行任务不会同时花掉同一份可用额度 | 需要占用、结算、异常和对账状态 |
| 熔断与有界队列 | 下游故障时不把系统拖入无限等待 | 部分请求会被拒绝，产品必须诚实展示 |

允许暂时失败、部分完成或结果未知，往往比“持续尝试直到界面显示成功”更可靠。

## 5. MVP 与验收：使用可计数的故障，不依赖模型自述

先使用可控模型替身与模拟发送服务，不要求真实 API。以下是待实现方案。

| 刺激 | 明确通过条件 |
|---|---|
| 模型前两次临时失败，第三次成功 | maxAttempts=3 时总请求恰为 3；每次尝试可追踪 |
| 模型持续失败 | 最多尝试 3 次，不无限循环，返回明确失败 |
| 参数错误、无权限 | 原样请求不会进入退避重试；越权执行次数为 0 |
| 在退避或队列中取消 | 取消被观察后不启动下一次请求，等待项被释放 |
| 任务剩余时间不足以继续 | 不启动超出准入规则的新调用；停止与收尾分别记录 |
| 模拟发送成功但丢失响应 | 通过同 operationId 查询或幂等重提确认；真实发送效果恰为 1 |
| 同 operationId 换收件人或正文 | 后端拒绝，不复用原批准 |
| 总预算 100，并发申请两份 60 | 恰一份获准；结算 50 后可用为 50，不启动另一份 60 |
| 请求取消但计费结果未知 | 保守占用不提前释放，状态能进入后续对账 |
| 降级或资料读取失败 | 最终输出明确标注范围与缺失，不伪装完整成功 |

给 Coding Agent 的任务卡应明确：错误分类、最大尝试口径、deadline、幂等保证、预算原子性与清理责任。要求提交请求 / 发送计数、操作状态和账本快照，不只提交“测试全绿”。
